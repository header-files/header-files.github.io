    一、为什么要研究 Agent

    Prompt 能表达意图，却不能执行意图。Agent 补上的是模型与现实之间那条缺失的闭环——而这条闭环，正是 LLM 从演示走向生产的必经之路。

    你让模型帮你处理一批数据：读进来、清洗、去重、算几个指标、导出成表。它答得头头是道，步骤清晰，连该用哪个函数都替你写好了。然后它停住了。剩下的活，还是你去做。

    过去两年，我们大部分关于“LLM 应用”的努力，本质上都在解决这个停顿。Agent 是这轮解法里最有分量的那个名字——不是因为它听起来更高级，而是因为它换了一个问题：与其让模型把答案说得更好，不如让它自己去把事办完。

    01、Agent 这个词很老，是 LLM 让它重新有用

    在人工智能的教科书里，agent 指的是一个能通过传感器感知环境、并通过执行器作用于环境的实体。按这个标准，空调的恒温器也是 agent——它感知温度，然后决定压缩机开还是关。所以我们今天讨论的显然不是这个词本身，而是它在这两三年突然变得可用的原因。

    真正变的是“决定下一步做什么”这件事的归属。以前它必须由人写死：状态机、规则表、启发式函数，一套一套地堆。现在它可以交给一个通用模型现场判断。这个迁移听起来轻巧，实际意义是：Agent 从“每个领域单独建造一次”变成了“可以用一套通用骨架承载”。 在这之前，没有人谈论”通用 agent”，因为它的成本结构不允许。

    所以站在工程角度，我给一个尽量小的定义：

    Agent ＝ 一个 LLM 控制器 ＋ 一组工具 ＋ 一个循环 ＋ 一份可持久化的状态，在真实环境中反复行动，直到目标达成或判定失败。

    这四个部件缺一个，退化成什么形态是可以精确说出来的：没有工具，模型只能吐文本，它就是 Chatbot；没有循环，就只剩下一次函数调用；没有状态，上下文一被压缩，任务当场失忆；没有明确目标，它不知道何时该停，会一直“继续”下去直到烧完预算。工程上遇到的大多数莫名其妙的问题，最后都能对应到这四个里面少了一块。

    写成伪代码，Agent 和一次普通调用的差别一眼就看得出来：

    # 一次 LLM 调用
text = llm(prompt)

# 一个 Agent
state = init(task)
while not done(state) and steps < budget:
    action = llm(state.context, tools)   # 决策
    result = execute(action)             # 行动
    state = update(state, result)        # 观察与记忆
return state.artifacts

    这里面最关键的其实是 execute 那一行。它意味着模型的行为开始有后果——这是 Agent 和“会聊天的模型”之间真正的分水岭，也是后面所有麻烦的来源。

    02、为什么恰好是这几年

    如果只允许用一句话回答，那就是：不是哪一个突破，而是几条原本互不相干的曲线恰好凑到了同一时刻。

    • 模型这一侧，2022 年 ReAct 那篇论文已经把“边推理边行动”的思路讲清楚了，但当时工具调用还得靠 Prompt 里约定 JSON 格式、再拿正则去解析，脆得像纸。真正的转折点是 2023 年 6 月函数调用变成原生能力——工具选择从“祈愿式解析”变成了受约束的解码。之后结构化输出、长上下文、带显式推理过程的模型依次到位，每一步都在往下压 Agent 的失败率，而不是往上抬它的上限。

    • 需求这一侧的道理更朴素。写一段文案，省的是人几分钟；把一件事从头办完，省的是那件事本身的钱。企业愿意为前者付一杯咖啡，为后者付的可能是一部分人力成本。需求其实一直都在，只是过去没人接得住——复杂流程的自动化只能靠 RPA 加硬编码规则，维护成本高到不划算。与此同时 token 变得便宜，”多花十倍 token、多想几步、多验一遍”从一个奢侈策略变成了常规操作，架构上原本不可行的方案突然变得可行了。

    • 再往下是接口和度量两件事。2024 年 11 月 MCP 开源之后，工具接入从“每个应用各写一遍”变成“一次实现、多处复用”。这看着像工程细节，其实决定了生态能不能长出来——一个需要为每个客户端重写 N 遍适配层的能力，是长不出生态的。而 SWE-bench、GAIA 这类基准，把“到底行不行”从感觉变成了可比较的数字。一个领域开始有排行榜，通常就是它从概念走向工程的信号。

    不过，把这五条线摆在一起，也能得到一个反向的判据：如果你的问题恰好不落在它们的交集里，Agent 可能还不是正确答案。 这一点在后面还会再回来。

    03、从“帮我写”到“帮我做完”

    回头看，“然后它停住了”这件事是一级一级被解决的，而每一级改变的都不只是体验，还有谁在为正确性负责。

    • 最早 LLM 就是一个文本函数，输入什么就回什么。所有编排都在人身上：自己想、自己复制、自己粘贴、自己判断、自己跑到别的地方去执行。模型的输出没有后果，它只提供建议。

    • 后来有了多轮上下文和角色设定，交互自然多了，可责任结构一点没变，执行的人还是你。ChatGPT 帮你把 SQL 写好了，你得自己粘到数据库里跑；帮你把行程理顺了，机票还得你自己订。模型始终停在“世界的描述层”，从不触碰世界本身。

    • 到第三级，模型开始自己决定调什么工具、按什么顺序、失败了怎么办。它第一次接触到未经自己修饰的现实。

    但模型一旦开始接手执行，真正难解决的问题也变了：以前只需要保证“说的对”，现在还要保证“做的对”。生成错了，人一眼就能看出来，成本通常只是重生成一次；执行错了，可能要等到十几步之后才暴露，而那时被删掉的文件、被发出去的邮件、被写坏的生产数据已经回不来了。于是工程重心也跟着挪：从“怎么写出一段更好的 Prompt”，变成“怎么验证、怎么回滚、怎么观测、怎么限权”。

    评价指标随之换了一套。 我们不再问模型回复的好不好，而是问：任务成功率多少？平均要走几步、烧多少 token、花多长时间？失败集中在哪一类步骤上——是工具选错、参数填错，还是整条路走岔了？失败了能不能回到上一个正确状态接着跑？

    04、差别不在智能，在权限

    很多人习惯用“智能程度”来区分 Chatbot、Workflow 和 Agent。这个区分方法很容易误导架构决策，它们的真正差别是决策权和执行权分别落在谁手里，以及人是站在回路里面还是外面。

    Chatbot Workflow Agent
    谁决定下一步 人。模型只负责应答当前问题 代码。流程由开发者预先编排 模型。运行时自主决定
    谁执行 人。模型不产生副作用 系统。按照预设流程执行 模型通过工具调用执行
    人的位置 回路中，同步参与 回路外，通常无需逐步参与 回路外，通常只在必要时介入或事后审计
    作用域 对话文本 预先定义的任务流程和工具 真实系统：文件、API、数据库、浏览器等
    执行路径 人决定下一步 代码决定下一步 模型根据当前状态决定下一步
    失败成本 很低，重问一次即可 可预测，通常可以针对固定路径测试和回滚 不确定，可能连续执行多步后才暴露
    典型形态 客服问答、知识助手 文档处理流水线、RAG 流程、数据处理流程 自动修 Bug、批量数据清洗、跨系统同步

    三者可以简单理解成：

    • Chatbot：人决定怎么做，模型负责回答。

    • Workflow：代码决定怎么做，模型负责完成其中某些步骤。

    • Agent：模型决定怎么做，并通过工具把决定执行出去。

    这也是为什么 Workflow 和 Agent 经常被混在一起。它们都可能使用 LLM，也都可能调用工具，但控制权不同。Workflow 的调用路径是开发者提前定义好的：什么时候调用模型、什么时候检索、什么时候调用工具、什么时候判断结果，都已经写进流程里——模型可以参与某个节点的决策，但不能随意改变整个流程。Agent 则相反。开发者提供目标、工具、规则和运行环境，具体下一步做什么由模型在运行时决定。它可能先查资料，再调用工具；发现结果不对，又换一种方法；工具失败了，还可能重新规划。

    因此，两者的核心区别不是“有没有 LLM”，甚至也不是“智能程度高低”，而是执行路径是预先确定的，还是运行时生成的。这会直接影响成本和可靠性。Workflow 的路径相对确定，因此更容易测试、预测和定价；Agent 的路径由运行时状态决定，灵活性更高，但执行步数、Token 消耗、工具调用次数和失败位置都存在更大的不确定性。

    所以，架构选择时有一个很实用的判断：如果任务流程本身是确定的，就优先考虑 Workflow；如果任务需要根据中间结果不断判断“下一步该做什么”，才真正需要 Agent。

    例如：

    用户上传一份合同 → 提取文本 → 分段 → 向量化 → 写入数据库 → 返回结果

    这是典型的 Workflow。每一步基本都是确定的，没有必要让模型自己决定下一步。

    而：

    “帮我找出这个项目里的 Bug，并修好它。”

    就更适合 Agent。因为它可能需要自己搜索代码、理解调用关系、修改文件、运行测试、分析报错，再决定下一步怎么处理。

    Agent 的价值并不是把 Workflow 做得更“智能”，而是把原本需要人不断做决策的部分交给模型。

    因此，真正应该问的不是“这个任务够不够智能，要不要上 Agent”，而是：

    下一步到底应该由谁决定？

    如果答案始终是代码，那么是 Workflow。如果答案经常需要根据运行时情况临时判断，而且这种判断可以安全地交给模型，那么才有必要引入 Agent。

    05、为什么只靠 Prompt 解决不了复杂任务

    到这里通常会有人提出一个合理的反驳：模型再强一点、Prompt 再写好一点，不就行了吗？不行。而且原因不是能力问题，是结构问题——这两者的区别很重要，因为它决定了你该等模型升级，还是该动手改架构。

    先看上下文。一个长任务会产生大量中间产物：读到的文件内容、接口返回、报错堆栈、已经确认过的事实。这些都得进上下文，而上下文窗口是有限的。更麻烦的是，就算塞得进去，模型对长上下文的利用效率也会明显下降，“中间遗忘”和长上下文退化都是已经被反复观察到的现象。而 Prompt 工程没有办法创造外部存储，它只能请求模型“记住”，可模型的记忆在一次压缩、一次截断之后就静默消失了——没有状态，就没有长任务。

    其次，模型看不见现实。文件存不存在、接口是不是返回 500、代码能不能编译、这条 SQL 跑不跑得通，它一概不知。没有工具，它对世界的一切判断都建立在“根据训练数据推测”之上。这一点经常被低估：幻觉的一个重要成因，不是模型爱编，而是它没有获得反馈的渠道。 一个永远收不到“你错了”的系统，只能一直自信下去。

    还有更根本的一层。一次前向传播只能做一个决定，而复杂任务需要 n 个决定，第 k 个还依赖前 k−1 个的真实结果。把它压进一次生成，等于要求模型在不知道任何中间结果的前提下，把整条路一次性猜对。误差会累加：哪怕单步正确率有 95%，三十步之后整体只剩两成左右。这不是靠“想得更仔细”能补回来的，这是概率算术。

    于是它也无法验证自己。没有执行器，模型只能靠“看起来对不对”来判断自己的输出，无法运行测试、无法比对数据、无法确认副作用。而如果你试图用 Prompt 把控制流补上，很快就会撞到另一堵墙：重试、循环、分支、超时、限流、事务、幂等，这些全都是运行时的活。你当然可以在 Prompt 里写“如果失败就重试”，但你没法强迫模型真的重试第二次；也可以写“确保操作是幂等的”，可幂等是代码属性，不是文字属性。

    所以：Prompt 是意图的表达，不是执行的机制。

    复杂任务的失败，大多数时候不是因为模型不够聪明，而是因为架构里缺了东西：没地方存状态、没通道感知现实、没机制强制执行、没来源判断对错。Agent 要补的正是这些缺件——它补的不是智力，是结构。

    06、那多出来的东西到底是什么

    不是更长的 Prompt，也不是更花哨的提示词模板。是把五个部件补进系统，再用一条循环把它们串起来。

       目标  ──▶  决策  ──▶  行动  ──▶  环境
             (LLM)     (工具)    (文件/API/DB/浏览器)
               ▲                     │
               └──── 观察结果回流 ─────┘
                        （反馈）

   底部支撑：  状态 / 记忆          约束 / 权限
              （跨步骤持久化）     （沙箱、最小权限、人工审批）

    工具是模型的动作空间，但它带来的东西比”能做更多事”更微妙：它把模型不擅长的确定性计算外包了出去。算术、检索、精确的格式转换、类型检查，交给代码执行正确率是百分之百，而让模型心算，正确率永远只是一个概率。工具不只是扩展边界，它同时在削掉模型最不可靠的那一部分。

    状态则容易被想得太简单。它其实分好几层：当前任务的中间结果、历史轨迹、外部知识库，以及真实世界里的那些对象——文件、数据库记录、工单。这里有一个必须建立起来的心智模型：上下文是缓存，状态才是真相。 上下文可以被压缩、被摘要、被丢弃，而状态必须始终能恢复。把这两者搞混的人，几乎一定会遇到“跑到第四十步，突然忘了自己在干什么”这类问题，而且在很长一段时间里找不到原因。

    规划也不是“先输出一份完美计划再照着执行”。真实环境里，第三步的结果随时可能推翻第二步的假设，所以计划必须可修正：先给出粗略路径，执行中根据观察动态重排。ReAct 的交替推理、Plan-and-Execute 的先规划后执行、Tree-of-Thoughts 的多路径搜索，本质上都在处理同一个矛盾——在信息不完整时做决策，并在拿到新信息后改掉它。

    剩下的两个，执行和反馈，才是真正的分水岭。只有执行才能改变世界，也只有执行才能换来关于世界的真实信息；而工具返回的结果就是 ground truth——编译器的报错、测试的通过与否、接口的返回码、对账的差额。这些信号第一次让“自我修正”从一句口号变成了机制。没有反馈，模型的一切自我评估都是自说自话；有了反馈，循环才有一个收敛的方向。

    如果把这几件事压成一句话：Prompt 给的是知识和表达，Agent 给的是知识和表达，外加感知、记忆、行动和纠错。

    07、它现在还做不好什么

    对 Agent 保持清醒比对它热情更重要。现在真正能跑通的场景，几乎都满足同一个条件：存在廉价、客观、而且及时的验证信号。 有了它，模型能自己发现错了、自己改；没有它，循环只是在原地绕圈。

    当前比较成立

    • 信息聚合：多源检索、交叉验证、汇总成报告
    • 结构化转换：非结构化文本变成结构化字段，跨格式搬运
    • 可验证的编码任务：改代码、编译、跑测试，反馈免费且客观
    • 长流程重复操作：批量处理、跨系统同步、表单填报
    • 可探索的排障任务：调试、定位异常、数据探查

    需要非常慎重

    • 反馈缺失或严重延迟：长期效果类决策，没有客观标准的创作质量评判
    • 错误不可逆且代价高：生产环境写操作、资金操作、对外发送
    • 目标本身模糊：需求还在探索中，需要反复和人对齐意图
    • 依赖隐性经验：组织协作、人际沟通，需要读取大量没被记录的背景
    • 极长任务链：误差累积和上下文腐化仍然是两堵最硬的墙

    有一条粗糙但很好用的直觉，值得记住：

    端到端可靠性 ≈ 单步可靠性 ^ 步数 × 验证覆盖率

    它给出的其实只有两条改进路径，但这两条恰好是工程上最有价值的。第一条是减少步数：不是所有事情都该拆细，一个本来能一次做完的子任务拆成五步，只是把单步错误率乘了五次。设计工具粒度时该问的问题是“哪一层最容易被验证”，而不是“哪一层粒度最优雅”。第二条是提高验证覆盖率：尽量给每一步接上可校验的信号——类型检查、schema 校验、单元测试、断言、人工确认点。每加一个自动验证点，就等于给误差设了一道闸。

    08、为什么这件事最后变成了工程问题

    一个很自然的反驳是：模型会越来越强，这些工程复杂度会不会自己消失？不会。因为它解决的绝大多数问题，本来就不是模型能力问题，而是系统问题。

    最直观的一类，是可靠性。重试与退避、幂等设计、检查点与恢复、状态机、补偿事务、超时与熔断——任何一次“跑到一半崩了”的 Agent 任务，都会把你拽回分布式系统那一整套老问题里。再加上调度、并发、持久化和崩溃恢复，你会发现这一层和后端工程几乎同构。

    其次是信息该怎么组织。什么内容该进上下文、什么时候压缩、怎么分层、检索回来的东西怎么放、整个预算怎么分——这一组问题的总和，业界叫 Context Engineering，它正在取代 Prompt Engineering 的位置。原因很直接：真正的杠杆不在“这句话怎么写”，而在“这一刻模型看到了什么”。同一层逻辑也适用于工具：工具切多细、参数 schema 怎么定义、报错信息写成什么样，都直接决定上限。“参数缺失”和“缺少必填字段 user_id，请先调用 get_user 获取”，对模型来说是完全不同量级的信息。

    再往下，是评测和可观测性，也是最容易被放到最后、却最不该被放到最后的两件事。没有 eval 就没有迭代——因为你没法判断一次改动到底让 Agent 变好了还是变差了。而 Agent 的调试体验，更接近调试一个分布式系统：你要回答的是“它为什么在第七步选了这个工具”，而不是“这段话读起来为什么不顺”。

    最后是安全。最小权限、沙箱、关键节点人工确认、成本和速率上限，这些还算常规；Agent 真正新增的攻击面是：提示词注入会经由工具返回的内容进来。 模型读到的一段网页文本、一份文档、一条搜索结果，都可能是载荷，而 Chatbot 时代根本不存在这个威胁模型。

    本质：Agent，就是用 LLM 当控制器的分布式系统。

    所以它的工程问题大多与后端系统同构，只是多了一个新的不确定性来源：控制器本身是概率性的，行为不可完全预测，也无法用断言穷举。把“一个不可预测的控制器”和“一个必须确定的结果”塞进同一个系统，就是 Agent Engineering 的全部难度。

    还有一个更务实的理由。模型会换、框架会换、协议也会换，但这套方法论会留下来。今天学某个编排框架，明天可能就换成别的了；而“怎么给一个会自动执行的系统加上检查点、评测和权限”这件事，十年后依然成立。研究 Agent 的长期回报，恰恰在于它沉淀下来的不是某个 API，而是一种设计能力。

    09、学习路线：八层台阶

    这条路线不是并列的知识清单，而是逐层依赖的——每一层都是下一层的前提。跳着学最典型的结果，是会用框架，但说不清楚为什么框架要这样设计。

    1. LLM（基础）
      别急着上框架，先搞清楚大模型到底怎么工作：token 怎么切、采样为什么会带来随机性、上下文窗口为什么是硬边界、幻觉从哪里冒出来。这一层最容易被跳过，而跳过的人往往在后面最基础的地方反复吃亏——比如想不通模型为什么会编出一个根本不存在的函数名。

    2. Context（上下文工程）
      上下文是模型唯一的信息通道，你对它的一切控制最终都走这条路：system prompt 怎么写、少样本示例给几个、历史什么时候压缩、检索到的内容怎么注入、预算怎么分。这一层比 Prompt Engineering 更接近真正的杠杆。
      过关标志：能精确控制“模型此刻看到了什么”。

    3. Tool（工具调用）
      从函数调用的协议入手，但重点不在协议，而在接口设计。工具切多细、参数 schema 怎么定、报错信息写成什么样，这些细节比模型选型更能决定成败，也是最快见效的优化点。

    4. MCP（接入标准）
      工具接入的标准化协议。它的价值不在这条协议本身，而在于把“连接”从业务代码里解耦出来：一件事情只实现一次，任何兼容的客户端都能接上。
      过关标志：写出一个自己的 MCP server。

    5. Skill（能力封装）
      把“做某类事”的领域知识和流程打包成一个可复用单元：指令、脚本、附带资源、判定规则。这一步的意义是把原本只存在某个人脑子里的隐性经验，变成团队可复用、可审查的显式资产。

    6. Agent（循环与规划）
      到这里才开始碰真正的循环：规划、状态管理、多步执行、中断与恢复。建议先用裸循环写一遍，别急着上编排框架——你会更清楚框架替你做了什么，以及在哪些地方帮了倒忙。
      过关标志：能稳定跑完 10 步以上的任务。

    7. Runtime（运行时）
      让 Agent 真能上线的那一层：持久化、并发、沙箱、超时、成本控制、权限体系、多 Agent 编排。判据很实在——任务崩溃后能不能恢复，能不能同时跑上百个，成本是不是可预测。

    8. Eval（评测与验证）

      当 Agent 能够稳定运行之后，下一个问题就变成：**怎么知道它到底做得好不好？**Agent 的输出不再只是文本，而可能是一连串工具调用和最终任务结果。因此需要从“回答是否正确”转向“任务是否完成”：建立任务集、记录 Trace、自动评分、结果验证、回归测试。这一层最常被排到最后，也最不该被排到最后：缺了它，前面所有改动的好坏都只能靠感觉。
      过关标志：能建立一套 Agent 评测集，并通过 Trace 和自动评测判断一次改动是变好还是变差。

    三条建议：

    • 按层学，不要按框架学——框架是某一层的临时实现，会过时，层是稳定的认知结构，今天记住某个 API 的写法，价值大概只有半年
    • 每层都用一个最小可运行项目打通，尤其是第六层之前，先把裸循环写明白，再去看框架做了什么取舍
    • 以及，尽早把 eval 建起来，哪怕只有二十个用例，也远好过靠感觉迭代：评测不是终点，它是让你前面每一步都能被验证的前提。

    10、回到最初的问题

    Agent 到底解决了 LLM 应用里的什么问题？

    它解决的，不是“模型不够聪明”。它解决的是——模型与现实之间缺少闭环。

    LLM 本质上是一个封闭的函数：给它文本，它回文本。它不知道自己错了，无法让世界发生任何变化，也做不完一件需要跨越很多步骤的事。Prompt 只能把更多信息喂进去，但喂得再多，闭环依然不存在。

    Agent 做的，是在模型和现实之间接上了四根线。一根感知线，通过 RAG 和工具获取外部知识与环境信息，让它不再只依赖模型参数中的知识；一根记忆线，用状态做持久化，让任务不因上下文耗尽而失忆；一根行动线，通过工具执行产生副作用，让输出第一次有后果；还有一根纠错线，用反馈带回真实信号，让它第一次能发现自己错了。

    接上之后，LLM 从一个会说话的模型，变成了一个能做事的主体。而这四根线带来的所有新问题——可靠性、状态一致性、权限边界、成本控制、评测体系、可观测性——正好就是 Agent Engineering 的全部内容。

    所以，研究 Agent 的理由是：它是 LLM 从演示走向生产的必经之路。

    而研究 Agent 的本质，是研究如何让概率性的智能，在确定性的系统里可靠地工作。

    这个问题不会随着模型变强而消失。模型越强，我们越会放心地把更重要的任务交给它；任务越重要，系统的可靠性、可观测性和可控制性就越关键。这是一道会长期存在的工程命题。
