    四、上下文管理与优化

    上一篇拆的是“每一轮怎么把上下文拼起来”，这一篇要回答的是更实际的问题：拼不下、装太多的时候怎么办。 上下文管理做得好不好，衡量的不是“装下了多少”，而是“扔掉了多少不该装的”。

    01、管理上下文的三件事

    前面说过，上下文是一种边际收益递减的稀缺资源。而Agent 循环会不断追加工具结果、历史消息和状态信息，使上下文越来越大；当信息量超过模型能够有效利用的范围后，噪声、成本和延迟都会开始成为问题。于是所有管理手段都可以归到三类：

    • 压缩：内容已经装进去了，怎么把它变小而不失真；
    • 预算：地方就这么大，怎么决定谁占多少；
    • 优化：跳出单次请求，从结构和机制上让每一轮更省。

    三者关注的是不同层面：

    • 压缩：对已经产生的上下文做减法；
    • 预算：给有限的 Context Window 划定边界；
    • 优化：从获取、组织、隔离、缓存等机制上减少不必要的上下文消耗。

    02、上下文压缩：把内容变小

    压缩的本质是一个有损变换：把大量原始内容变换成小得多的表示，同时尽量保住“对后续步骤有用的信息”。它一定丢信息，所以所有压缩技巧的核心问题都是同一个——丢什么、留什么。

    2.1 历史摘要

    历史摘要是长对话和长周期 Agent 中常见的上下文压缩方式：接近预算上限时，把之前所有轮次交给模型总结，用摘要替换原始历史，从精简后的状态继续工作。它有效的前提是摘要“留对了东西”。Anthropic 在描述 Claude Code 的压缩机制时给出过参考答案：保留架构决策、未解决的 bug、实现细节这类会持续影响后续判断的信息，丢弃重复的工具输出和过程性对话。做完压缩后，agent 带着摘要和最近访问的几个文件继续，用户感知不到中断。

    两个实践要点。第一，摘要的粒度要“决策级”：写“改了 A 文件”价值有限，写“因为 B 约束所以选了 A 而不是 C”才有用——隐含决策丢了，后面就会重蹈覆辙或做出矛盾行为。第二，压缩过猛会丢掉当时看不出重要、后来才关键的细节，Anthropic 在介绍 compaction 时建议把压缩提示当成需要专门调校的工程产物：先保证召回率，把相关信息全部留住，再逐步收紧。

    还有一个容易被忽略的时机问题：在一些长任务中，可以考虑把压缩安排在任务自然断点，而不是等到上下文几乎耗尽；这样更容易选择合适的保留内容。但具体触发策略应根据任务和实现评估。

    2.2 工具结果压缩

    在 Agent 的上下文里，增长快的除了对话，还有工具结果。一次工具调用可能带回几千 token 的 JSON、一整页网页、一大段日志，如果不做清理或压缩，这些工具结果会继续留在后续上下文中，并不断增加输入规模。对应的压缩手段由几层组成：

    • 源头收敛：让工具本身就返回精炼结果——只返回必要字段、做分页、支持裁剪，这是最根本的一层，也是工具设计的核心要求之一；
    • 抽样代替全量：处理大文件、大结果集时不整体加载，用 head、tail 这类命令先看头尾，用针对性查询代替全表扫描；
    • 事后清理：调用完成、结论提取之后，把过大的原始输出替换成结论或摘要。

    2.3 信息去重

    去重处理的是一种结构性浪费：同一条信息以不同形态出现在多个位置。 项目说明既在环境快照里、又被检索命中了一次、还写进了记忆；同一段代码因为两次文件读取而在历史里存了两份；系统提示里讲过的规则，又在用户消息里复述了一遍。

    去重的原则在之前就埋下了：关键事实保留单一可信源，其余位置只放指针。 实践上可以按三个步骤检查：找出重复项、指定权威来源、把其余出现替换为引用。与摘要相比，去重通常可以在不改变主要信息内容的情况下减少重复，但前提是能够确认重复内容具有相同语义和相同有效性——所以凡是发现重复，优先去重，而不是先急着压缩。

    2.4 Map-Reduce

    前面三种手段都作用于“一个上下文内部”。当单份上下文根本装不下要处理的内容时，就要换思路：分而治之。 把大内容切块，每一块在独立的上下文里处理（Map），只把精炼结果带出来，最后汇总（Reduce）。

    多智能体系统可以采用 Map-Reduce 的组织方式，每个子 Agent 在自己的上下文里读完大量资料，只向主 Agent 返回一千到两千 token 量级的精炼结论，主agent基于这些结论做综合。Cognition 对这类架构的提醒也要记着：子agent之间的上下文是割裂的，各自基于各自的部分信息做决策，容易出现彼此冲突的隐含决策——所以 Map-Reduce 适合“各块相互独立、结果可合并”的任务（如大规模检索、批量分析），不适合各部分强耦合的工程任务。

    2.5 滑动窗口

    滑动窗口是最简单的历史控制手段：只保留最近 N 轮，更早的直接丢掉。它实现成本几乎为零，适合闲聊型应用。但在 Agent 场景里它有致命缺陷：被丢掉的信息里可能藏着后续必需的约束。 任务第 3 步定下的关键决定，到第 40 步可能正是需要遵守的——滑出窗口就等于忘了。在需要长期保持任务约束的 Agent 中，单纯滑动窗口存在明显的信息遗失风险，因此通常需要配合摘要、外部状态或 Memory 等机制：窗口外的内容不是直接丢，而是先沉淀成摘要或外部笔记，窗口内保留近期原文。这也正是“滑动窗口 + 记忆回灌”成为常见组合的原因——窗口负责控制体积，记忆负责保住连续性。

    03、上下文预算：分配的艺术

    3.1 Token 预算

    预算思维的第一步是把账算清楚。一次调用里，上下文要同时容纳以下几类内容，而且它们互相挤占：

    • 系统提示词与工具定义（常驻成本，每轮重发）；
    • 项目与任务指令；
    • 对话历史与工具结果（增长成本）；
    • 检索与记忆注入的内容（可变成本）；
    • 留给模型输出的空间——这一项最容易被忘掉：Context Window 通常同时受到输入和输出 token 的限制，具体上限取决于模型和 API，预留不足，长回复会被截断。

    很多实现提供了查看占用构成的手段（例如 Claude Code 的 /context 命令可以按类别显示各层占了多少）。养成先看账再调优的习惯，比凭感觉删内容有效得多——你经常会发现，占大头的是某个没有做源头收敛的工具，而不是自以为冗长的系统提示。

    3.2 不同信息的优先级

    算清总量之后是分配。分配需要一张优先级表，优先级主要取决于当前任务的必要性、信息可靠性和时效性；变更频率则更多影响它应该如何缓存、更新和注入。综合起来，一套常见的分配次序是：

    1. 不可妥协的：安全约束、当前任务目标、刚才做出的关键决策——丢了它们，后面全错；
    2. 高价值常驻的：系统提示词、工具定义——它们决定了模型“会什么”，但可以通过精简控制体积；
    3. 按需进出的：检索内容、记忆、技能正文——用指针和触发机制控制，用时再进；
    4. 可牺牲的：历史中的过程细节、被取代的旧方案、探索性尝试的中间输出——压缩和截断主要发生在这里。

    这张表的用法不是背下来，而是在每次“装不下”的时候问一遍：现在在窗口里的东西，有哪些属于第四类？ 十有八九，问题出在那里。

    3.3 动态截断

    静态预算管不住动态增长，所以需要动态截断：给不同类别的信息设置上限，超限就按规则裁剪。几个常见的截断点：

    • 工具结果超长时截断并提示“已截断”（让模型知道可以去分页取）；

    • 历史超过阈值时触发压缩；

    • 单条注入的检索内容限量，超出部分只给标题列表。

    截断设计里有一个容易做错的细节：截断要留线索。 直接静默裁掉，模型会以为看到的就是全部，基于残缺信息继续推理；正确做法是明确告知“此处截断，完整内容可通过某工具获取”，把截断变成一次渐进披露，而不是一次静默丢失。

    3.4 长上下文控制

    前三小节都是单点手段，长上下文控制是把它们组合成一套随长度变化的策略。一个实用的分层是：

    • 短任务：什么都不用做，正常追加；
    • 中等任务：开始收紧——工具结果源头收敛、及时去重、历史按需摘要；
    • 接近预算：触发压缩，摘要 + 最近文件重开窗口；
    • 超出预算的任务：转入外置模式——状态写进笔记和文件，上下文里只留指针，靠回灌维持连续性；必要时拆分成多个独立子任务。

    要说明的是，各实现在“接近预算”时的具体阈值和触发方式各不相同（有的自动触发压缩，有的需要手动），这是实现细节而非协议规定，以所用工具的文档为准。但策略分层本身是通用的：长度每上一个台阶，就应该多启用一层管理手段。

    04、上下文优化：从机制上省

    压缩和预算都是在“内容已经很多”之后补救，优化则从结构上让问题变少。

    4.1 选择：从源头少装

    选择是优化手段里杠杆最大的一条：不该进的，从一开始就不进。 它的工程落点是检索链路——查询改写、重排序、相关性过滤、时效过滤——以及“即时上下文”：预先只放轻量标识符，运行时按需加载。

    4.2 排序与优先级布局

    同一批内容，放的位置不同，效果和成本都不同。这一条在之前已经展开（静态在前、动态在后），这里只补一个预算视角：位置布局也是预算工具。 根据模型和任务特点，把高价值内容放在更容易被模型利用的位置；对于长上下文，可以通过实验验证开头、中间、结尾不同位置的效果，而不是机械套用固定排序。布局一次做对，后面每一轮都在受益。

    4.3 隔离：别让所有信息挤在同一个窗口里

    隔离的原则是：每个模型调用只看到完成当前任务所需的最小上下文。 它有两个主要形态。

    一是子Agent：让独立的上下文去做调查、试错这类“过程脏活”，只把结论带回主上下文。好处是主上下文的轨迹可以跑得更长，坏处是子Agent看不到全局背景——子 Agent 更适合上下文边界清晰、可以相对独立完成的子任务；需要综合全局状态的最终决策通常仍应由能够看到足够全局信息的协调 Agent 完成。Cognition 则从反面给出了更强的警告：多个Agent并行决策时，各自的行动带着各自的隐含假设，容易互相冲突；默认情况下应该排除不满足“共享完整轨迹”原则的架构。

    二是任务切换时的上下文重置：换一个不相干的任务就清空重来，而不是让上一个任务的残留混进下一个任务——这既是预算问题，更是冲突问题。

    05、什么时候用哪一招

    最后把三类手段收拢成一张决策表：

    症状 首选手段 关键动作
    历史把窗口撑满了 历史摘要 决策级摘要 + 最近文件，断点处触发
    单次工具调用拖垮预算 工具结果压缩 源头收敛优先，抽样与清理兜底
    同一事实到处出现 信息去重 单一可信源，其余放指针
    内容总量超过单个窗口 Map-Reduce 切块独立处理，只带结论回来
    简单场景想省事 滑动窗口 必须配摘要或记忆，否则丢关键约束
    输出被截断 Token 预算核算 别忘了给输出留位置
    装进去的大多没用上 选择收紧 重排、过滤、即时加载

    这张表读起来像工具箱，但底层只有一句话：上下文管理的所有手段，都是在一个有限预算内，持续地决定“什么该被模型看见”。 压缩是事后减法，预算是事前分配，优化是让这两件事的需要变少。
