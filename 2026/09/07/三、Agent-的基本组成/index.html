    三、Agent 的基本组成

    从LLM到Agent > Agent简介 LLM Agent

    Agent 不是”会调工具的聊天模型”。把 LLM、Prompt、Workflow、MCP、Skill、Runtime、Harness 这几个词混着用的团队，通常会在三个时刻发现自己做的不是 Agent：第二次对话它忘了前面所有事，第一次工具报错它直接卡死，第一次需要跨天续跑任务它从零开始。这三个时刻分别指向三样缺失的东西——Memory、Loop 的错误恢复、以及一个真正的状态层。

    这两年”Agent”被反复重定义，几乎每个厂商、每个框架、每篇公众号都在给它加零件。加到最后，一个 CRUD 应用套上几层提示词也敢叫 Agent，一个壳里包着一堆 if-else 的流程编排也敢叫 Agent。

    所以”一个最基本的 Agent 到底由哪些部分组成”这个问题，值得从零回答一次。它不只是概念洁癖：你对组成的划分方式，直接决定了你会把工程精力投在哪里，也决定了当模型升级时，你手上这套东西是跟着变强，还是变成技术债。

    本文要回答以下两个问题：Agent 的组成部分各自解决什么问题；哪些属于 Agent 本身、哪些只是外围基础设施。

    01、结论先行

    一个 Agent 的最小组成是五个零件：

    Agent
├── LLM          负责理解、推理、决策、生成
├── Context      负责让 LLM 在每一步看到该看的信息
├── Tool         负责让 Agent 能作用于外部世界
├── Memory       负责保存跨轮次、跨会话需要留下的信息
└── Agent Loop   负责把 Observe → Decide → Act 串成持续执行

    而让这套东西能在生产环境真正跑起来，还需要两圈外围工程能力：

    外围工程能力
├── Runtime      它在哪里跑、能碰什么（进程、沙箱、文件系统、权限、隔离）
└── Harness      它是怎么被装配和驱动的（提示词装配、上下文管理、编排、可观测性）

    一句话概括两者的关系：五个零件定义”它是不是 Agent”，外围两圈决定”它能不能用”。 下面逐个拆开。

    02、从一个最小 Agent 开始

    先看骨架。几乎所有 Agent 框架——不管它包装成 LangGraph、AutoGPT 还是某个自研 DSL——剥到最后都是这张图：

                        ┌──────────────┐
                    │     LLM      │
                    └──────┬───────┘
                           │
                       Agent Loop
                ↙          ↓          ↘
        ┌────────────┐ ┌──────────┐ ┌────────────┐
        │  Context   │ │   Tool   │ │   Memory   │
        └────────────┘ └──────────┘ └────────────┘

    不要把它读成”LLM 连着四个模块”，那样会看不懂工程实现。正确的读法是：中间是一条循环，LLM 是循环里唯一的决策者，而 Context、Tool、Memory 是循环在每一轮要处理的三类资源。

    把一轮循环摊开在时间轴上，是这样的：

      ┌─────────────┐
  │ 1. Observe  │  把 Context 装配好（系统提示 + 历史 + 工具定义 + 记忆召回）
  └──────┬──────┘
         ▼
  ┌─────────────┐
  │ 2. Decide   │  LLM 推理：直接回答？还是要调工具？
  └──────┬──────┘
         ▼
  ┌─────────────┐
  │ 3. Act      │  执行工具 / 写入记忆 / 更新状态
  └──────┬──────┘
         │  结果回灌
         └──────────► 回到 1，直到满足停止条件

    这个形状不是某家厂商发明的。2022 年底的 ReAct 论文第一次把”推理（Thought）”和”行动（Action）”交错在同一个循环里，让模型可以在行动后根据观察（Observation）调整下一步推理，而不是一次性把计划写死。今天所有 Agent 都能追溯到这条脉络。

    一旦把它看成循环，一个结论就出现了：Agent 的能力上限由模型决定，但能力的下限由外围决定。 模型再强，如果每一轮只看得到最近三条消息、工具报错时直接抛异常终止、跨会话没有任何状态，那么这个 Agent 的表现会稳定地差，而且差得和模型无关。

    03、LLM：系统里唯一在做决策的东西

    LLM 在 Agent 里负责四件事：理解任务、推理、决策、生成。但要真正理解它的位置，重点是它不负责什么：它不执行任何操作，不读写文件，不调用 API，不改变任何状态。它输出的永远只是一段文本——或者一段结构化的”我想调用这个工具、参数是这些”的意图。

    这个区分在工程上极其重要，因为它意味着一条硬规则：

    模型输出的是意图，效果由外部执行。 所以任何”模型说了就等于做了”的设计都是错的。

    由此可以推出几个实践结论。

    第一，模型不做的事，不要指望它做。它不会替你校验参数合法性，不会记得你昨天给过的授权，不会自动知道哪个命令危险。这些必须由工具层和 Runtime 层兜住。

    第二，模型侧真正值得优化的是三件事：选对工具、给对参数、知道什么时候该停。这三件事都不发生在模型权重里，而发生在你给它的 Context 里。这也解释了为什么同一个模型放进不同的 Agent 框架里表现差异巨大——差异不在权重，在它每一步看到的东西。

    第三，别把”模型能力强”当成”Agent 能力强”。前沿模型的通用推理已经很好，Agent 做不好任务，绝大多数时候是 Loop、工具描述、上下文装配的问题。

    04、Context：模型每一步能看到什么

    Context 是这一轮推理中，模型能看到的全部 token 的集合。

    这里最容易犯的错误，是把 Context 理解成”那份提示词”。并不是！Context 是一个每轮都要重新组装的缓冲区，里面通常包含：

    Context（第 N 轮的装配结果）
├── 系统提示词          身份、行为边界、输出约定
├── 工具定义            每个工具的名字、描述、参数 schema
├── 会话历史            之前的用户消息、模型回复、工具调用与结果
├── 外部知识            检索到的文档、代码片段、数据
├── 记忆召回            从 Memory 里取出来的相关片段
├── 当前任务状态        计划、进度、待办列表
└── 本轮输入            用户刚说的话，或上一个工具刚返回的结果

    看清这张清单，三件事就明白了。

    其一，Prompt 只是 Context 的一个子集，而且是静态的那一小块。 把提示词写得再漂亮，也只影响了这块清单里的一行。这就是为什么”提示词工程”单独存在已经不够，行业把它升级成了上下文工程：管理的对象从”这段话怎么写”变成了”这一步该给模型看什么、不该给模型看什么”。

    其二，Context 是有限且昂贵的资源。 窗口再大也有边界，而且成本随长度上涨。更麻烦的是它并非越大越好：长上下文中间部分的信息容易被模型忽略，无关内容会稀释注意力，行业里把这种现象叫上下文腐化（Context Rot）。一个塞满历史记录的 Agent，往往比一个只带关键信息的 Agent 表现更差。

    其三，Context 的组装是有策略的，不是拼接。 什么时候做摘要压缩、什么时候把工具结果截断、什么时候把老消息换成结论、什么时候从 Memory 里召回、召回多少条——这些决策合起来构成了 Agent 最核心的一层工程，也是同样模型跑出不同效果的主要原因之一。

    一句话记法：Context 不是 Agent 的输入，Context 是 Agent 每一轮现做的菜。

    05、Tool：Agent 伸向外部世界的手

    Tool 是 Agent 用来访问外部系统、执行操作的能力接口。

    一个工具由三部分构成，而它们的可见性完全不同：

    ┌─────────────────────────────────────────────┐
│ 模型可见的部分                                │
│   名称        get_weather                   │
│   描述        "查询指定城市当前天气，仅支持   │
│               中国大陆城市，参数为中文城市名" │
│   参数 schema { city: string }              │
├─────────────────────────────────────────────┤
│ 模型不可见的部分（执行体）                     │
│   HTTP 调用、鉴权、重试、超时、错误码映射       │
├─────────────────────────────────────────────┤
│ 回到 Context 的部分（返回值）                  │
│   "杭州：晴，26℃，东南风 2 级"               │
└─────────────────────────────────────────────┘

    这份结构里藏着一个被严重低估的事实：工具的描述文本，是决定 Agent 成败的关键代码。 它不是注释，它是给模型看的 API 文档。模型只能通过名字、描述和参数 schema 判断”该不该用这个工具、参数怎么填”。描述含糊、命名相近、参数语义不清，模型就会选错工具——而这类错误不会出现在任何日志里，只会表现为”这个 Agent 有点笨”。

    实践中，工具层最常见的改进不是把函数体写得更优雅，而是：

    • 给每个工具写清”什么时候该用、什么时候不该用”；
    • 把工具数量控制在合理范围，必要时做分组或延迟加载（先给模型一份工具名索引，确定要用时再取完整 schema）；
    • 工具报错时，把可读的错误原文回灌进 Context，让模型有机会自我修正，而不是直接终止循环。

    工具按作用方向大致可以分四类：读类（检索、查询、读取文件）、写类（发消息、写文件、提交变更）、计算类（跑代码、跑测试、格式化）、交互类（操作浏览器、点击界面）。这个分类在权限设计上很有用——写类、计算类和交互类天然需要更严的管控，因为它们才真正改变外部世界。

    最后一点必须说清：工具是攻击面。 只要外部内容能进入 Context（网页、文档、邮件、其他人写的代码），它就可能在文本里夹带指令，诱导模型去调用工具。这就是提示注入，也是为什么工具的权限、沙箱、人工确认不能等到”上线前再补”。

    06、Memory：让状态活过一轮对话

    Memory 保存 Agent 在当前任务或长期运行过程中需要保留的信息。

    要理解 Memory，先把它的时间尺度分层：

    长期记忆      跨会话     用户偏好、项目约定、历史结论、组织知识
会话记忆      跨轮次     对话历史、已确认的事实、未完成的待办
工作记忆      跨步骤     当前任务的中间结果、计划、草稿

    有一类东西常被误当成 Memory，需要单独拎出来：文件系统、数据库、外部知识库。它们确实是状态的载体，但它们对模型不可见——模型要通过工具去读写它们。所以它们更准确的归类是”外部状态源”。

    由此可以得出 Memory 最重要的一条性质：

    Memory 是存储，Context 是装载。 记忆本身不产生任何效果，只有被检索进 Context 的那一部分才真正影响决策。

    这条性质解释了两个常见失败：一是”我明明存了记忆，它怎么还是不知道”——因为没召回；二是”记忆库越堆越大，效果却越来越差”——因为召回了太多无关内容，把 Context 稀释了。

    另一个常被忽略的是写入策略比读取策略更难。读只要相关性排序，写要回答一堆问题：这一轮里哪些信息值得留下？和已有记忆冲突了怎么办？同类记忆该合并还是新增？什么时候该遗忘（过期、纠错、隐私删除）？一个没有遗忘机制的 Agent，长期运行后记忆库必然退化成噪音堆积。

    07、Agent Loop：把 Observe → Decide → Act 串起来

    Loop 是让 Agent 从”应答”变成”执行任务”的那个结构。

    最小形态大概是十几行：

    def run(goal, tools, memory, llm):
    ctx = Context()
    ctx.add_task(goal)
    ctx.add_memories(memory.recall(goal))
    ctx.add_tools(tools)

    for step in range(MAX_STEPS):
        action = llm.decide(ctx.render())        # Decide

        if action.type == "final":               # 停止条件之一
            return action.content

        result = execute(action, tools)          # Act
        ctx.add_observation(result)              # Observe，回到循环

        memory.maybe_write(ctx.recent())         # 沉淀
        ctx = compact_if_needed(ctx)             # 上下文管理

    raise BudgetExceeded(MAX_STEPS)

    看这段代码，你会发现真正的难点几乎全在循环的边界上，而不是循环本身。

    • 停止条件是最难的。 表面上”模型说完成就完成”，但模型很容易过早宣布完成，也很容易陷入无限重试。生产环境里通常要同时挂几个条件：模型给出终止信号、步数上限、token 或金额预算、时间上限、外部校验通过（测试跑了、构建过了、格式校验过了）、以及需要人工确认时暂停。行业里大量 Agent 失败案例，本质是验收标准没定义好——任务做完了 80%，卡在”谁来判断这算不算完成”。
    • 错误恢复决定它能不能连续工作。 工具超时、参数非法、外部服务 429、网络抖动，这些在真实环境里是常态。一个循环如果遇到错误就退出，它只能在演示视频里存在。正确做法是把错误当成一种观察结果回灌给模型，同时设置重试上限，避免用错误喂养出死循环。
    • 可中断与可恢复决定它能不能干长活。 长任务会被打断：人需要中途确认、进程会被部署重启、机器会宕机。所以每一步的状态要能持久化（checkpoint），重启后能续上，而不是从第一条消息重放。这也是 Loop 实现里最容易被低估、又最影响体验的一环。

    顺带把 Loop 和 Workflow 的界线说清：路径是写死的，还是模型选的。 Workflow 里 LLM 和工具沿着预先编排好的代码路径运行，控制流由工程师决定；Agent 里由模型自己决定下一步做什么、用哪个工具、什么时候停。这不是高低之分——大多数业务场景用 Workflow 更便宜、更稳、更好调试；只有在路径无法预先枚举（依赖运行时反馈、需要探索、任务开放性高）时，Agent 才真正划算。

    08、合起来看：Agent 本体的边界

    把五个零件放回去，并且检查”抽掉一个会怎样”：

    抽掉的部件 结果 还算 Agent 吗
    Loop 变成单次调用，一问一答 不是
    Tool 只能说话，不能改变任何状态 不是，是聊天机器人
    Memory 每一步都从零开始，无法续跑 不是，是无状态函数
    Context 模型没有输入，概念上不成立 不是
    LLM 没有决策者，退化成固定流程 不是，是 Workflow

    五缺一都不是 Agent，这就是”本体”的定义方式。

    但要注意，这五个零件是逻辑组成，不是物理模块。真实系统里它们经常落在同一段代码里：一个循环函数里同时做上下文装配、工具派发和记忆写入；一个提示词模板里同时承载系统提示和记忆召回。逻辑上分得清，物理上糊在一起，是常态，也是可以接受的——只要你知道自己在哪一层做决策。

    反过来，也有一类东西看起来像零件、其实不是，最典型的是 Skill 和 MCP。它们分别扩大的是”Context 里能装什么知识”和”Tool 从哪里接进来”，属于能力供给方式，不是新的组成部件。

    09、外围工程能力：Runtime 与 Harness

    到这里，Agent 的本体已经完整了。但它还跑不起来——或者说，只能在你本机的一个 Python 脚本里跑起来。要落地，还需要两圈外围。

    Runtime：它在哪里跑。

    Runtime 是执行环境，回答”在哪里跑、能碰什么、出事怎么办”：

    • 进程与容器隔离、沙箱；
    • 挂载哪些文件系统、要不要给网络；
    • 权限与凭证托管（工具拿的是谁的权限，密钥放哪）；
    • 资源限制（CPU、内存、时长、并发）；
    • 生命周期（启动、心跳、超时、优雅退出、断点恢复）。

    Harness：它怎么被装配和驱动。

    Harness 是包裹在模型外围的整套工程脚手架，回答”怎么跑得稳、跑得可观测、跑得可迭代”：

    • 系统提示词的装配与版本管理；
    • 工具、Skill、MCP 的注册、描述与按需注入；
    • 上下文管理（压缩、裁剪、召回策略）；
    • 编排逻辑（子 Agent、任务交接、模型路由）；
    • hooks 与中间件（在确定性的位置做压缩、续写、lint、校验）；
    • 可观测性（每一步的输入输出、工具调用链、成本与延迟）；
    • 评测体系（同一套任务集回归，判断改动是变好还是变坏）。

    业界对 Harness 有一种更宽的定义：它是除模型本身之外的所有代码、配置与执行逻辑。在这个口径下，Harness 把 Loop、工具执行、记忆、护栏、日志全包了进去，于是有了那个流行的等式”Agent = Model + Harness”。

    顺便说清 Harness 里两类东西的分工，这个框架很好用：一类是引导，指系统提示、工具规格、输出格式这些”先把路划出来”的约束；一类是传感，指日志、测试结果、lint、评测这些”行动之后告诉你偏在哪”的反馈。引导和传感都做得好，Agent 才可能稳定；只加引导不加传感，系统会越来越像一堆没人敢改的规则。

    关于外围能力，最后提醒一句反向风险：Harness 每加一层，都编码了一个”模型自己做不好这件事”的假设。模型在变强，这些假设会过时。所以做 Harness 的团队除了问”还能加什么”，也得定期问”现在能删什么”——否则一层层补丁会从护栏变成噪音，从安全垫变成技术债。

    10、所以，一个 Agent 最小需要什么

    回到最初的问题，现在可以给一个不留模糊地带的答案。

    第一层：缺一不可的组成。

    1. 一个能推理和决策的 LLM；
    2. 一套每轮为它装配信息的 Context 机制；
    3. 一个能改变外部状态的 Tool；
    4. 一个能把关键状态留存下来的 Memory；
    5. 一个把上述四者循环起来、并且定义了停止条件的 Agent Loop。

    第二层：怎么判断某个东西属于 Agent 还是外围。

    • 改变它，会不会改变”这个 Agent 会做什么决策”？会，属于本体。
    • 能不能用一个通用组件替换它，而不改变 Agent 的行为语义？能，属于外围。
    • 它编码的是”任务本身的逻辑”，还是”运行的秩序”？前者本体，后者外围。

    按这三条过一遍，边界就很清楚了：

    Agent 本体（决定它会做什么、怎么做）
├── Loop 的决策协议与停止条件
├── 工具集的选择与每个工具的描述
├── Context 的装配策略（什么进、什么不进、怎么压缩）
├── Memory 的写入与召回策略
└── 任务级的系统提示与输出约定

外围基础设施（决定它跑得多稳、多安全、多可迭代）
├── Runtime：沙箱、隔离、权限、凭证、资源限制、生命周期
└── Harness：编排、hooks、可观测性、评测、模型路由、成本控制

    第三层：最小可行清单。

    如果你现在要写第一个 Agent，最小可用形态是：一个循环（带步数上限和终止判断）、三到五个描述清晰的工具、一个把历史做摘要压缩的上下文策略、一份最朴素的记忆写入规则（比如把每轮结论追加到一个文件里，下轮开头读回来），以及一份日志。这五样加起来不到几百行代码，却足以让一个 Agent 真正”跑起来”，而不是”演起来”。

    而在模型能力快速变化的当下，这套划分还有一个更实际的用处：它告诉你哪些东西值得投入。 会随模型升级而过时的，多半是外围里那些为了弥补旧模型缺陷而加的补丁；而工具怎么设计、上下文怎么装配、记忆怎么写、什么算任务完成——这些编码的是你的业务秩序与判断标准，模型换了它们依然成立，也是别人抄不走的部分。

    所以判断一个东西叫不叫 Agent，最终只需要看一件事：决策权是否交给了模型，并且它有没有能力把这个决策兑现成行动。 满足这一条，哪怕只有五个零件；不满足，零件再多也只是工作流。
