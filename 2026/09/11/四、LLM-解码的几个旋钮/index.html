    9. 09、回到最初的问题

    同一句 prompt 发两遍，模型给出两个不同的答案。多数人的第一反应是“这模型不稳定”。但更准确的说法是：模型本身是确定性的——真正把随机性引进系统的，是我们在解码的最后一步主动加进去的那一次抽样。

    先看一个具体场景。

    你让 Agent 生成一段 SQL，第一次跑通了；第二次同样的指令，它漏掉了一个 WHERE 条件。你把 temperature 调到 0，输出确实稳定了，却开始变得死板、爱复读，偶尔还会在长对话里绕不出来。于是你面对几个旋钮——Temperature、Top-K、Top-P——却不知道它们各自在改什么，也不知道该不该一起调。

    要回答这个问题，必须把“一次前向传播”到“输出一个 token”的完整路径走一遍。模型的输出从来不是一个词，而是一整个概率分布；我们看到的那个词，是这条链路后半段被“挑”出来的结果。所有采样参数改的都不是模型，而是“怎么从分布里挑”。

    本文按这条路径展开：先看 logits 和 softmax 给出什么，再看采样做了什么，最后把几个参数放进 Agent 的真实场景里。

    01、从 Logits 到 Token 概率

    Transformer 不输出文字。最后一层 hidden state 之后再经过一次线性投影（LM Head，实践中常与词嵌入矩阵共享权重），得到一个长度等于词表大小的实数向量。这就是 logits。

    输入 “今天晚上天气”
        ↓
   Transformer（N 层）
        ↓
   LM Head 线性投影
        ↓
   Logits  z ∈ R^|V|      ← 几万到几十万个分数
        ↓
   Softmax（先除以 T）
        ↓
   Token 概率分布

    logits 是“未归一化的分数”：可正可负、没有上界，绝对值本身没有概率含义，只有相对大小有意义。

    对上例，假设词表某几个 token 的 logits 是 [8.4, 7.6, 6.9, 6.1, 5.5, ⋯ ]，经过 softmax 之后变成：

    晴    0.50
好    0.30
不错   0.10
凉    0.05
⋯     其余几万个候选合计 0.05

    softmax 做的事只有一件：把实数向量压成概率分布，每个分量落在 0 到 1 之间，所有分量之和恒为 1。

    这里有两个容易忽略的点，后面理解 temperature 时都要用到。

    • 候选空间比直觉大得多。词表有几万到几十万项，但绝大多数 token 的概率小到不可见。分布真正的“决策区域”往往只有几十个候选，剩下全是长尾。长尾里塞满了错别字变体、乱码片段、语法上“接得上”但语义上没意义的词——它们就是后面要处理的东西。
    • softmax 是保序的。它不改变谁大谁小：概率最高的 token，永远是 logits 最大的那个 token。

    02、Sampling：分布如何变成一个确定的词

    拿到分布之后，有两条路。

    贪心（Greedy / argmax）：每一步都选概率最高的那个 token。

    采样（Sampling）：按概率随机抽一个。

    两者的差别不是“谁更准”，而是“你要不要多样性”。

    贪心是确定性的，同样输入理论上给同样输出，适合分类、抽取、结构化输出。代价是它非常容易陷入退化：因为每一步都选“最安全”的词，生成结果会变得重复、死板，在开放生成里甚至会出现整段循环。这也是很多模型在 temperature 过低时“看起来像变笨了”的真实原因——不是能力下降，是它在每一步都拒绝冒险。

    采样则把随机性引了进来：同一个分布，两次运行可能抽到不同的 token。关键在于，一次抽样的差异会写回上下文，成为下一步的输入。第一步从“晴”变成“好”，第二步面对的分布就完全不同了。差异被逐步继承和放大，最终就是两个不一样的答案。这才是“LLM 输出不确定”的主要来源。

    这里有一个很常见的误解值得明确纠正：贪心是“每一步局部最优”，不等于“整句概率最高的序列”。要逼近整句最优需要 beam search，而 beam search 在开放生成中往往产出更乏味、更重复的文本，所以现在主流大模型服务几乎不默认开启它。也就是说，你在 API 上看到的默认行为，多数是“采样”而不是“搜索”。

    实际工程里，线上主流 LLM API 的默认几乎都是采样路径：OpenAI Chat Completions 默认 temperature=1.0，Anthropic Messages 默认 temperature=1.0，Google Gemini 默认 temperature=1.0 配 top_p=0.95。也就是说，你拿到的 API 默认回复，每一次都是从分布里“抽”出来的，不是“挑”出来的；想切回贪心，需要把 temperature 显式设成 0。但是，Hugging Face transformers.generate() 函数的默认值是 do_sample=False，即贪心——这是因为它面向的是研究者和离线推理脚本，目标是稳定可复现；而线上推理框架（vLLM / SGLang）默认反过来，采样。同一套模型库，对外和向内默认截然相反。

    03、Temperature：把分布压尖还是摊平

    Temperature 只做一件事：在 softmax 之前，把 logits 除以 T。

    pᵢ = exp(zᵢ / T) / Σⱼ exp(zⱼ / T)

    T 的取值直接决定分布的形状：

    • T < 1：logits 之间的差距被放大，分布更尖，输出更确定
    • T = 1：模型原生的分布
    • T > 1：差距被压缩，分布更平，输出更随机
    • T → 0：退化成 argmax，也就是贪心
    • T → ∞：退化成均匀分布，等于在词表里瞎猜

    图里三条曲线用的是同一组 logits，只改了 T。可以清楚看到两件事：T 变小，顶部 token 几乎吃掉全部概率；T 变大，原本没戏的 token 也开始有机会。

    以及一件更关键的事：三条曲线的排序完全一致。Temperature 是保序的，它改变的是概率之间的差距，不是谁排第一。所以 temperature = 2 配上 top_k = 1，行为依然是贪心；随机性永远来自采样那一步，temperature 只是调节随机性的幅度。

    这里需要纠正一个常见说法：温度不是“直接对概率做缩放”，而是作用在 softmax 之前的 logits 上。虽然数学上它等价于先归一化再做 p^(1/T)，但工程实现都在 logits 阶段完成。如果你去看代码，不要跑到 softmax 之后去找它。

    工程上的取值区间大致是（属于经验值，不同模型和厂商有差异，以官方文档为准）：

    • 0 ~ 0.3：代码补全、SQL、JSON、分类抽取、工具调用
    • 0.6 ~ 0.8：常规对话、RAG 问答
    • 0.9 ~ 1.2：文案、头脑风暴、创意写作
    • > 1.5：只用于特殊探索，主流模型在这个区间会明显跑偏

    值得补充的一点研究结论：有实证工作用九个大模型、五种提示技术、温度从 0.0 逐步加到 1.6 做过对照实验，发现在 0.0 到 1.0 区间内，温度对解题类任务的表现没有统计上显著的差异。这提示我们：温度主要影响的是输出的多样性与稳定性，而不是模型的“聪明程度”。指望靠调温度把准确率抬上去，大概率是白费力气。

    04、Top-K：一刀切掉长尾

    Top-K 的机制很直白：按概率排序，只保留前 K 个 token，其余全部置零，然后重新归一化再采样。

    100000 个 token
      ↓
  按概率降序排列
      ↓
  Top-K = 50
      ↓
只在前 50 个候选里采样

    它的作用是砍掉长尾。前面说过长尾里都是低质量的“能接上但没意义”的候选，一旦被抽中就会显著伤害输出质量。Top-K 给了一个硬性的质量下限。

    但 Top-K 有一个结构性缺陷：K 是固定的，而分布的“形状”每一步都在变。

    • 当分布很尖时，比如 1 + 1 = 之后，前三个 token 可能就占了 99% 的概率。这时候再保留 50 个候选，等于给噪声开了 47 扇门。
    • 当分布很平时，比如一个句子刚刚开头，前 50 个候选可能都不够用，一些本来很好的续写选项被直接砍在门外。

    一刀切的 K 无法同时适配这两种情况。这个缺口，就是 Top-P 出现的动机。

    05、Top-P：让候选数量自己浮动

    Top-P（Nucleus Sampling，核采样）换了一个切法：不再数个数，而是按累计概率划线。

    做法是：把 token 按概率从高到低排列，从前往后累加，取“最小的、累计概率刚好达到 p 的那个集合”，这个集合就是“核”（nucleus）。核外的概率置零，核内按原始概率的相对比例重新归一化后采样。

    举例，设 p = 0.90：

    A   0.60   →   累计 0.60
B   0.20   →   累计 0.80
C   0.10   →   累计 0.90   ✓ 达标，在这里截断
D   0.05   →   丢弃
E   0.03   →   丢弃
⋯

    最终保留 A、B、C 三个候选，并且是在它们原本 6:2:1 的相对比例下采样。

    它最关键的特点是：候选数量是动态的。分布越确定，留下的候选越少，极端情况下只留一个，行为自动退化成贪心；分布越平，留下的候选越多。这正好补上了 Top-K 的缺口——需要收紧时收紧，需要放开时放开，不需要人手动去猜一个 K。

    图里对比了两种分布下的表现。分布陡峭时，Top-K = 3 和 Top-P = 0.90 都留下 3 个候选，覆盖 93.2% 的概率，两者一致。分布平坦时，差距就出来了：Top-K = 3 虽然覆盖了 52.6%，却砍掉了另外 47.4% 的合理候选；Top-P = 0.90 则自动放宽到 7 个候选，覆盖 95.3%。

    工程上常用的取值是 p = 0.9 ~ 0.95。p = 1.0 等于不截断。

    06、Frequency / Presence Penalty：按历史扣分

    OpenAI 的 Chat Completions API（Google Gemini 等后来跟进的厂商也跟了同样的命名）除了 Temperature、Top-P 之外另开了一组参数：frequency_penalty 和 presence_penalty。它们和前三个不在同一层——前三个改的是整条分布的形状，这两个改的是”已经选过的 token”的得分。

    机制：两个参数都在 logits 阶段对历史里出现过的 token 扣分，差别在曲线：

    • presence_penalty：只要 token 在已生成序列里出现过，就把它的 logit 减去一个固定值。和出现次数无关，只关心”出现 vs 没出现”。
    • frequency_penalty：按 token 已出现次数成比例扣分。出现 n 次就扣 n × penalty，曲线是线性递增，重复越多单次惩罚越重。

    OpenAI 的取值范围是 -2.0 ~ 2.0。0 表示不干预；正值抑制重复；负值反向激励重复——基本没人这么用。

    一个容易被忽略的细节：OpenAI 的这两种 penalty 是减法（直接从 logit 减），而 Hugging Face 同族思路的 repetition_penalty 是乘法（把已出现 token 的 logit 除以一个大于 1 的系数）。减法更线性、调起来更直观；乘法对高频词压制更狠，但容易把”the”、”的”、”是”这类功能词一起罚掉，导致输出磕巴。

    什么时候需要。 前三者解决的是”从哪里挑”——分布的形状与候选集的范围。penalty 解决的是”不要重复上一次”，尤其是前三者无法触及的场景：

    • 长对话里模型开始兜圈（”那么 那么 那么”），截断与温度都救不了，penalty 能治。
    • 命名实体、引用编号、列表项这种”不能重”的输出。
    • 摘要、改写任务里输出与输入的复述比例过高——压一压能让输出更凝练。

    典型取值（属于经验值，不同模型/厂商有差异，以官方文档为准）：

    • 0：默认，不干预。
    • 0.3 ~ 0.6：轻度抑制，让显著重复的词被压制，但不影响正常用词。
    • 0.6 ~ 1.0：中度抑制，适合摘要、改写、长问答。
    • 1.0 ~ 2.0：强抑制，多用于命名、编号场景；但容易把功能词也压掉，输出会变生硬。
    • 负值：基本不碰。

    几个常被忽略的注意事项：

    1. penalty 和 Temperature / Top-K / Top-P 完全正交，可以叠加使用，不冲突。它们在 logits 处理管线里的位置不同——Temperature 是除法，Top-K / Top-P 是截断，penalty 是针对历史 token 的定向减分。
    2. 强 penalty 会让模型为了”不重复”而换成冷僻词，反而降低连贯性。如果输出开始出现生硬词，往往不是该继续调 penalty，而是该查上下文检索质量或换更好的提示词。
    3. Tool Calling 与结构化输出场景一般保持 penalty 为 0。重复调用同一个工具（比如反复查同一个状态）有时是合理的，强行压反而损害能力。

    07、五个采样参数的关系与执行顺序

    把五者放在一起看：

    参数 作用对象 控制什么 典型取值
    Temperature logits 分布的尖锐 / 平坦程度 0 ~ 1.2
    Top-K 排序后的概率 候选数量的硬上限 0（关闭）/ 20 ~ 100
    Top-P 累计概率 候选集的概率范围 0.90 ~ 0.95
    Frequency Penalty 已出现 token 的 logit 按出现次数扣分 0 ~ 1.0
    Presence Penalty 已出现 token 的 logit 出现过就扣固定分 0 ~ 0.6

    一句话概括：Temperature 调“随机程度”，Top-K 调“候选数量”，Top-P 调“候选概率范围”，Frequency / Presence Penalty 调“不要重复”。前三个是“在分布上动刀”，后两个是“在历史里动刀”，两者正交。

    执行顺序在工程上很重要，而且常被忽略。以 Hugging Face 的 logits processor 管线为例，顺序是：

    logits
  → 除以 temperature
  → top-k 截断
  → top-p 截断
  → multinomial 采样

    顺序有实际后果：先缩放再截断，和先截断再缩放，得到的候选集是不一样的。自己实现解码循环时不要颠倒这两步。

    还有两条实践经验值得记住。

    • Top-K 和 Top-P 通常不要同时开。两个过滤器叠加时，真正生效的是更严格的那一个，调参会变成猜谜。如果你确实需要一个硬性的下限来兜底，用 min-p 会比用 top-k 更好调——它按“最大概率的相对比例”划线（阈值 = 最大概率 × min_p），在模型确信时自动收紧、在模型犹豫时自动放宽，比固定 K 更贴合分布的真实形状。
    • temperature 和 top_p 只调其中一个。这是主流 API 文档给出的建议。原因是这两个参数都会改变候选集的形状，同时调的话，你无法判断变化来自哪一个。

    顺带一提，除了这五个主参，工程上还有几类常用手段：typical sampling（保留信息量接近分布熵的 token，即“既不意外也不无聊”的那一类）、min-p（按最大概率的相对比例截断，比固定 K 更自适应）。它们解决的是同一类问题的不同侧面，不必全开，按需挑一个即可。重复抑制类的需求（frequency / presence / repetition penalty）已经在前一小节讲过，这里不再重复。

    08、对 Agent 的影响

    Agent 的特殊之处在于，它在一次任务里反复切换任务类型。

    8.1　精确任务

    SQL 生成、JSON 输出、Tool Calling、分类抽取、格式转换。这类任务的正确答案是“唯一”的，不需要任何多样性。

    • temperature 压到 0 ~ 0.2
    • 比温度更重要的手段是结构化输出：用 JSON Schema 或语法约束解码，把输出格式限制在解码阶段，而不是靠 prompt 祈祷模型听话。约束解码的原理是在每一步把不符合语法的 token 概率直接置零，格式正确率从“概率意义上的正确”变成“语法意义上的必然”
    • 如果模型或框架不支持约束解码，退而求其次：把目标格式写进 prompt 的示例里，并配合低温度

    一个反直觉的观察是：当分布本身很确定时（比如模型刚写完 { 之后），temperature 调低对稳定性的帮助其实有限，真正把错误挡在外面的是截断和约束。温度管的是“采样多样性”，不是“格式正确性”。

    8.2　创造任务

    文案、命名、创意发散、多方案对比。这类任务需要的是多样性。

    • temperature 给到 0.8 ~ 1.2
    • 更有效的做法不是把温度继续往上推，而是一次生成多个候选再挑选（n > 1）。温度拉到 2 以上，模型往往不是变得更有创意，而是开始跑偏、失去连贯性；而多采样几次再排序，可以在不牺牲单条质量的前提下拿到多样性

    8.3　Agent 场景的两难

    Agent 的每一步调用几乎都在这两类任务之间切换：

    • Tool Calling 需要稳定、需要严格遵循格式。这里追求的是可复现，温度要低；有条件就上约束解码。一次格式错误可能导致整条链路失败或产生错误副作用，这个代价远高于多样性带来的收益。
    • Reasoning 需要适度的探索能力，用来跳出局部思路。但要注意，专门训练过的推理模型通常已经把探索过程内化到训练和内置采样配置里，手动改 temperature 反而可能破坏它的表现。对这类模型，优先遵循厂商建议、不要手调。

    落到实践上，有一条原则比任何具体数值都好用：把随机性放在“想”的阶段，不要放在“做”的阶段。 让模型在规划、推理、方案比较时有探索空间，但在真正落地成一次工具调用、一条 SQL、一段配置时，把随机性关掉。

    09、回到最初的问题

    回到开头那两个问题。

    LLM 输出的不确定性从哪里来？

    第一层，也是主要来源，是采样。模型给出的是一个概率分布，采样把分布变成具体的 token，这一步本身就是随机的——除非你用贪心。参数里的 Temperature、Top-K、Top-P 都不是随机性的来源，它们只是改变了分布的“形状”，让随机性变大或变小。Frequency / Presence Penalty 同样不引入新的随机，只是对历史里出现过的 token 做了定向扣分。真正的随机性永远只来自最后那一步采样。

    第二层，是上下文放大器。一次抽样的差异会写回输入，被后续所有步骤继承和放大。第一步选错了词，第二步面对的分布就已经不同了。这也是为什么长链条任务对早期 token 的敏感度远高于我们的直觉。

    第三层，是工程实现层面的残余不确定性。这一层经常被忽略：浮点加法不满足结合律，(a + b) + c 和 a + (b + c) 在线性精度下结果可能差最后一位；而 Transformer 的前向计算本质是一连串的归约操作（矩阵乘、LayerNorm、Attention），归约的分块方式会随 batch 大小、GPU 数量、GPU 型号变化。也就是说，同一个请求被放进不同 batch，得到的 logits 可能在最后几位就不同了。当两个候选 token 的概率接近时，这一点点扰动就足以翻转 argmax。有实验用同一个推理模型做贪心解码，把同样的 prompt 重复 1000 次，得到了 80 种不同的输出；在推理模型上，仅改变 GPU 数量或评估 batch 大小，就能带来约 9 个百分点的准确率波动。

    结论是明确的：temperature = 0 只保证了“不再从分布里抽样”，并不保证跨批次、跨机器、跨版本的完全可复现。 如果你真的需要严格复现，需要同时固定 seed（在支持的 API 上）、固定 batch 配置、尽可能固定硬件与推理框架版本。而且第一次输出不同之后，后续轨迹就完全分叉了——错误的累积速度快到超乎预期。

    工程上如何控制？

    • 先分清任务性质。 精确任务用低温度 + 结构化输出；创造任务用中高温度 + 多候选挑选。这是唯一真正重要的分工。
    • 一次只调一个旋钮。 要么动 temperature，要么动 top_p。同时调两个，等于放弃了归因能力。
    • 不要用调参掩盖 prompt 问题。 输出格式不稳定，优先上约束解码；答案漂移、事实错误，优先查上下文和检索质量。温度解决不了这两类问题。
    • 接受不可消除的那部分。 把采样视为系统的一个输入，而不是一个待修复的 bug。配套的做法是用多次运行来评估——看通过率和方差，而不是看某一次的输出。单次运行的结论在随机系统里没有统计意义。
    • 在 Agent 里按节点分配温度。 规划节点给一点探索空间，工具调用节点压到最低，最终输出节点按任务性质决定。用一个全局温度覆盖整条链路，几乎一定在某些环节上是错的。

    模型的确定性在 logits 里，随机性在采样那一步，而你手上能控制的，就是这条链路后半段的每一个旋钮。
