    Chat Completions 的全部秘密，其实就是“发一段对话，收一段回答”：输入是一个 messages 数组加几十个可调参数，输出要么是一次性 JSON，要么是一串 SSE chunk。把这两条路径吃透，你在任何一家大模型厂商的 API 文档里都不会迷路。

    如果你接过 OpenAI、Azure OpenAI、vLLM、Ollama、DeepSeek、通义千问或者任意一家大模型服务的接口，你会发现它们的请求体长得几乎一模一样。这不是巧合——大家都在兼容 OpenAI 在 2023 年推出的 Chat Completions 协议。它已经成了大模型时代事实上的“HTTP”：换厂商只需换 base_url 和 api_key，业务代码一行不用改。

    01、Chat Completions是什么

    Chat Completions 是一个 HTTP POST 接口，典型路径是 POST /v1/chat/completions。你把一段对话历史（messages 数组）和一些可选参数打包成 JSON 发过去，服务端返回模型的回答。

    一个最小可用的请求长这样：

    curl https://api.openai.com/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d '{
    "model": "gpt-4o",
    "messages": [
      {"role": "user", "content": "北京今天天气怎么样？"}
    ]
  }'

    服务端会返回一个 JSON，核心信息在 choices[0].message.content 里：

    {
  "id": "chatcmpl-9xK…",
  "object": "chat.completion",
  "created": 1726567890,
  "model": "gpt-4o-2024-08-06",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "抱歉，我无法获取实时天气。"
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 18,
    "completion_tokens": 12,
    "total_tokens": 30
  }
}

    把 stream 字段设为 true，响应就从“一次性 JSON”变成“一串 SSE 事件流”，这就是本文要重点展开的两条路径。值得注意的是，两条路径的服务端生成逻辑完全一样——都是自回归地一个 token 一个 token 往外吐，区别只在于“攒齐了再给”还是“吐一个给一个”。

    02、请求：客户端发什么

    请求体只有两个字段是必填的：model 和 messages。其余都是可选项，按功能可以分组。先把 messages 讲透，再逐组过参数。

    2.1　model 与 messages

    model 是模型 ID，不同厂商的命名规则不同，部分模型会提供带日期的快照版本（如 gpt-4o-2024-08-06），固定具体版本可以减少模型升级带来的行为变化。

    messages 是一个消息对象数组。不同 role 支持不同字段；content 是最常见的消息内容字段，assistant 消息还可以通过 tool_calls 发起工具调用。

    role：

    消息通过 role 区分消息来源和用途。常见角色包括 system、user、assistant 和 tool。

    role 谁在说 典型用途
    system 系统设定 定人设、定规则、定输出格式
    user 用户 用户输入
    assistant 模型 模型历史回复，也可手工伪造做 few-shot
    tool 工具执行结果 回填函数调用结果，需带 tool_call_id

    Chat Completions 本身是无状态的，不会自动维护多轮对话状态。应用需要根据需要把历史消息组织到 messages 中发送。这也是为什么多轮对话会越聊越贵——历史消息越长，通常需要处理的输入 token 越多，因此多轮对话的输入 token 消耗通常会随历史累积而增长。

    content：

    content 大多数时候是字符串：

    {
  "role": "user",
  "content": "北京今天天气怎么样？"
}

    在支持多模态的模型中，content 也可以是数组，每个元素通过 type 表示内容类型，常见的包括：

    • text：文本；

    • image_url：图片，支持 URL 或 base64 data URL；

    例如：

    {
  "role": "user",
  "content": [
    {
      "type": "text",
      "text": "这张图片中的表格第二列加总是多少？"
    },
    {
      "type": "image_url",
      "image_url": {
        "url": "https://example.com/table.png"
      }
    }
  ]
}

    图片输入会产生额外的输入 token 消耗，具体消耗量与模型和图片处理方式有关；高分辨率或多图片输入可能显著增加输入成本。

    tool_calls：

    tool_calls 用于表示模型发起的工具调用请求，出现在 assistant 消息中。

    每个工具调用通常包含：

    参数 说明
    id 本次工具调用的唯一 ID
    type 工具类型，常见为 function
    function.name 要调用的函数名称
    function.arguments 模型生成的函数参数，通常是 JSON 字符串

    例如：

    {
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_123",
      "type": "function",
      "function": {
        "name": "get_weather",
        "arguments": "{\"city\":\"北京\"}"
      }
    }
  ]
}

    这里模型只是提出工具调用请求，并没有真正执行函数。客户端收到 tool_calls 后，根据其中的函数名和参数找到对应工具并执行，然后将结果以 role=tool 的消息重新发送给模型：

    {
  "role": "tool",
  "tool_call_id": "call_123",
  "content": "{\"temperature\":25,\"weather\":\"晴\"}"
}

    2.2　采样与生成

    这一组参数控制“token 怎么选”，是调优手感的主战场：

    参数 类型 说明
    temperature number，0~2 温度，越大越随机
    top_p number，0~1 核采样，只从累积概率前 top_p 的 token 里选
    n integer 一次生成几条候选，choices 数组就会有几条
    logprobs boolean 是否返回每个输出 token 的对数概率
    top_logprobs integer，0~20 每个位置额外返回概率最高的前 N 个候选 token
    presence_penalty number，-2~2 正值鼓励提新话题，负值鼓励反复围绕同一主题
    frequency_penalty number，-2~2 正值按出现次数惩罚重复，负值鼓励重复
    logit_bias map token ID 到 -100~100 的偏置，-100 基本禁用该 token
    stop string 或 array 指定停止序列，命中后停止生成；具体支持形式和限制取决于模型
    seed integer 用于尽可能复现相同输入和参数下的输出，但不保证绝对确定性

    两个容易踩的坑：

    • OpenAI 官方建议 temperature 和 top_p 不要同时调整，二者都在改采样分布，叠加调节很难定位效果来自哪个参数。
    • seed 主要用于尽可能复现相同输入和参数下的输出，但不提供绝对确定性保证。模型版本、后端配置以及底层数值计算等变化，都可能导致结果发生变化；system_fingerprint 等信息可用于辅助判断后端配置是否发生变化。

    2.3　长度、格式与推理

    参数 说明
    max_tokens 旧字段，限制最大生成 token 数
    max_completion_tokens max_completion_tokens 用于限制 completion 可使用的最大 token 数；对于支持 reasoning 的模型，其限制可能同时覆盖可见输出和 reasoning tokens。max_tokens 属于较早的参数，在部分模型/接口中仍存在兼容语义，但新代码应根据目标模型和 API 文档选择对应参数。
    response_format.type text（默认）/ json_object（要求输出合法 JSON）/ json_schema（要求输出遵循给定 JSON Schema）
    response_format.json_schema 配合 json_schema 使用：name + schema（JSON Schema 定义）+ strict（是否严格模式）
    reasoning_effort 部分推理模型支持，用于控制推理投入程度；具体可选值由模型决定，通常值越高意味着更多推理投入以及更高的延迟和输出 token 消耗

    json_schema 配合 strict: true 可以让模型输出遵循指定 JSON Schema 的结构，适合需要稳定结构化输出、直接对接下游程序的场景。但 strict 模式并不支持 JSON Schema 的全部关键字，需要遵循 API 对 Schema 的限制。

    2.4　工具调用

    参数 说明
    tools 工具清单，每项包含 type 和 function，其中 function 可包含 name / description / parameters / strict
    tool_choice none（禁用）/ auto（模型自行判断，默认）/ required（要求模型进行工具调用）/ {"type":"function","function":{"name":"xxx"}}（强制调用指定工具）
    parallel_tool_calls 是否允许一次返回多个 tool_calls，默认 true
    function.name 要调用的 function 名称
    function.description function 的功能描述，供模型理解何时以及如何调用该 function
    function.parameters function 的输入参数，以 JSON Schema 对象描述
    function.strict 函数级 Schema 严格校验开关

    工具签名用 JSON Schema 描述，description 写得越清楚，模型选择和传参越准。strict: true 会让服务端按 Schema 约束生成参数，大幅降低传参幻觉。

    2.5　流式控制

    参数 说明
    stream false（默认，一次性返回）/ true（走 SSE 流式）
    stream_options 子字段 include_usage：设 true 时服务端会在流末尾额外推一个只含 usage 的 chunk；include_obfuscation：是否对流式 chunk 做混淆（部分实现支持）

    2.6 运维与元数据

    参数 说明
    user 终端用户标识，用于滥用监测与用量归因，不参与鉴权
    metadata 自定义键值对，用于给请求附加业务元数据，便于检索、统计等
    safety_identifier 滥用监测标识，与 user 类似但更偏安全侧

    2.7　已废弃字段

    参数 说明
    functions 旧的函数声明方式，已被 tools 取代
    function_call 旧的调用控制，已被 tool_choice 取代

    这两个字段在大量老代码和教程里仍然常见，绝大多数兼容服务也会继续支持，但新项目建议用 tools / tool_choice。

    03、非流式响应：一次拿到全部

    3.1　顶层结构

    非流式响应是一个完整的 JSON 对象，object 字段固定为 chat.completion：

    • id：本次调用的唯一标识，排查问题时先要这个；
    • object：对象类型；
    • created：Unix 时间戳；
    • model：实际使用的模型版本；
    • choices：候选数组，长度等于请求里的 n；
    • usage：token 计费依据；
    • system_fingerprint：后端配置版本指纹；
    • service_tier：本次调用实际使用的服务层级。

    3.2　choices 与 message

    每个 choice 包含：

    • index：在候选数组中的序号；
    • message：assistant 的最终回复；
    • logprobs：token 级概率（需请求开启 logprobs，否则为 null）；
    • finish_reason：停止原因。

    message 里除了 role 和 content，还有：

    • refusal：模型拒答时的说明，正常回答时为 null。程序化处理时必须同时检查 content 和 refusal

    • tool_calls：模型决定调用工具时的调用列表，每项含 id、type、function.name、function.arguments

    注意 content 可能为 null——当模型决定调用工具时，正文为空、信息全在 tool_calls 里。

    3.3　finish_reason

    为什么停，比“停了没有”更重要。四种取值：

    取值 含义 工程上怎么办
    stop 自然结束，或命中 stop 序列 正常情况
    length 达到 max_tokens 或上下文上限，被截断 正文不完整，要么调大限制要么做续写
    tool_calls 模型想调工具，等你回填结果 走工具调用的往返流程
    content_filter 命中内容安全策略 输出被拦，别把它当正常结果入库

    生产代码里对 length 和 content_filter 的处理最容易漏。前者会导致下游解析到半截 JSON，后者如果不检查，被拦截的空回复会混进数据里。

    3.4　usage 与 token 计费

    usage 是计费的唯一依据：

    • prompt_tokens：输入消耗，包含 system、全部历史、图片/音频折算；
    • completion_tokens：输出消耗；
    • total_tokens：两者之和；
    • prompt_tokens_details.cached_tokens：命中前缀缓存的部分，计费打折；
    • prompt_tokens_details.audio_tokens：输入中的音频 token；
    • completion_tokens_details.reasoning_tokens：推理模型“思考”消耗的 token，看不见但计费；
    • completion_tokens_details.audio_tokens：输出中的音频 token；
    • completion_tokens_details.accepted_prediction_tokens / rejected_prediction_tokens：配合 prediction 使用，统计预测命中与未命中的 token 数。

    3.5　logprobs

    请求里开 logprobs: true 并设置 top_logprobs 后，choices[].logprobs.content 会返回每个输出 token 的概率明细：token、logprob、bytes，以及 top_logprobs 列表（该位置概率最高的前 N 个候选）。用途主要是三类：置信度评估、分类任务校准、知识幻觉检测（概率低但很笃定的内容要警惕）。

    04、流式响应：边生成边下发

    4.1　SSE 是什么

    请求里设 stream: true，响应头变成 Content-Type: text/event-stream，服务端用 Server-Sent Events（SSE）协议持续下发数据。SSE 报文的格式很简单：每条消息以 data: 开头，空行分隔，最后一条是 data: [DONE]。

    data: {"id":"chatcmpl-9xK…","object":"chat.completion.chunk","choices":[{"index":0,"delta":{"role":"assistant"},"finish_reason":null}]}

data: {"id":"chatcmpl-9xK…","object":"chat.completion.chunk","choices":[{"index":0,"delta":{"content":"今天"},"finish_reason":null}]}

data: {"id":"chatcmpl-9xK…","object":"chat.completion.chunk","choices":[{"index":0,"delta":{"content":"北京 24℃，晴。"},"finish_reason":null}]}

data: {"id":"chatcmpl-9xK…","object":"chat.completion.chunk","choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}

data: [DONE]

    4.2　chunk 的结构

    每个 chunk 的 object 字段是 chat.completion.chunk，和 chat.completion 的关键区别是：choices[].delta 替代了 message。delta 只包含增量——第一个 chunk 通常只有 role，中间的 chunk 只有 content 的一小片，最后一个 chunk 的 delta 为空对象、finish_reason 有值。

    4.3　拼接规则

    客户端侧的拼装逻辑就三行：

    1. 收到 chunk，取出 choices[0].delta.content（可能不存在，要判空）；
    2. 追加到本地缓冲区，同时把新增量推给前端渲染；
    3. 收到 [DONE] 或 finish_reason 非 null 后结束。

    注意 choices 数组在个别情况下可能为空（比如只推 usage 的那个 chunk），取 choices[0] 之前要判空，这是很多 SDK 老版本的隐藏 bug。

    4.4　流式下的 usage

    usage 要等所有 token 生成完才能统计，所以流式响应默认不携带 usage。要拿到它，在请求里加：

    {
  "stream": true,
  "stream_options": {"include_usage": true}
}

    服务端会在 finish_reason chunk 之后、[DONE] 之前，额外推一个所有 choices 为空数组、只有 usage 有值的 chunk。

    4.5　tool_calls 的流式分片

    工具调用的参数也会被流式分片：delta.tool_calls 数组里的每一项带 index（标识是第几个调用）、id 和 function.name（通常只在第一个分片出现）、function.arguments（JSON 字符串的增量片段）。客户端要按 index 把 arguments 逐段拼接，收完后再 parse。这是流式 + 工具调用组合里最容易写错的地方。

    05、工具调用：一次往返讲清楚

    5.1　模型不执行函数

    新手最常见的误解是以为服务端会帮你执行函数。实际上 Chat Completions 的工具调用分工是这样的：模型只决定“调哪个、传什么参数”；真正的执行在客户端；执行结果要以 role: "tool" 消息回填，再发一次请求，模型才能基于结果继续回答。

    四步走：

    1. 客户端在请求里声明 tools，附带用户问题；
    2. 模型返回 finish_reason: "tool_calls" 和 message.tool_calls（此时 content 为 null）；
    3. 客户端解析 function.name 和 function.arguments（JSON 字符串，要自己 parse），执行本地函数，把结果作为 {role:"tool", tool_call_id:"…", content:"…"} 追加到 messages，重新发起请求；
    4. 模型读到工具结果，返回 finish_reason: "stop" 的自然语言回答。

    tool_call_id 必须严格对上：并行调用多个工具时，服务端就是靠它把结果和调用一一配对的。

    5.2　并行与强制

    parallel_tool_calls: true（默认）时，第 2 步可能一次返回多个 tool_calls（比如“北京和上海的天气都查一下”）。客户端要逐个执行、逐个回填。

    tool_choice: required 适合“必须走某个工具”的场景（如“把这句话翻译成 SQL 并执行”）；tool_choice: {"type":"function","function":{"name":"get_weather"}} 则完全跳过模型的选择环节，强制调用指定工具，适合确定性流程。

    06、工程实战的五个坑

    6.1　什么时候用流式

    一条经验法则：面向人的场景默认流式，面向程序的场景默认非流式。聊天界面、IDE 补全必须流式——用户对首字延迟极其敏感；而后端之间的调用（数据抽取、分类、批处理）用非流式更省心，出错了重试也简单。流式的代价是客户端要维护拼接逻辑、处理断流重连、实现半截结果的丢弃。

    6.2　超时与断流

    非流式的坑在总时长：长回答生成可能要几十秒，HTTP 客户端的默认超时（常见 30 秒）会直接掐断一个本可以成功的请求，务必把读超时调大。

    流式的坑在中间断：代理、负载均衡、服务端滚动发布都可能让 SSE 流中途断掉，且已生成的 token 不退费。生产代码要做两件事：一是记录已收到的内容，断流时至少能知道进行到哪；二是区分“收完 [DONE] 的正常结束”和“连接断开的异常结束”，别把半截回答当完整结果入库。

    6.3　max_tokens 与推理模型

    给推理模型（o 系列、DeepSeek-R1 等）设 max_completion_tokens 时要记住：这个额度包含思考消耗的 reasoning tokens。设小了会出现“finish_reason 是 length、content 为空或很短、账单照扣”的情况。对推理模型要么给足额度，要么不设。

    6.4　temperature 与 top_p 二选一

    前面提过，这两个参数都在改采样分布。实践建议：先用 temperature 单独调，遇到“偶尔冒出怪词”再考虑加 top_p；代码生成、结构化抽取这类要稳的场景，temperature 直接给 0 到 0.3。

    6.5　多厂商兼容性

    兼容层大约分三档：vLLM、Ollama、DeepSeek 等对通用子集兼容得很好；Azure OpenAI 走自己的鉴权与部署模型（api-version 查询参数、deployment-name 替代 model）；各家网关（OpenRouter 等）则是在标准字段之上加自己的扩展字段（如路由偏好）。写跨厂商代码时，最稳的做法是把请求体收敛到“必填 + 采样 + 工具 + 流式”这个通用子集，专有字段用特性开关按需打开。
