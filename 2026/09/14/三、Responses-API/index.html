    Chat Completions 是把“模型当成函数调用”，Responses API 是把“模型当成会干活的 Agent”：前者把工具执行、文件检索、上下文状态全部丢给客户端自己管，后者把这些收进协议本身。理解这个定位差异，整篇文档就通了。

    Chat Completions 已经成为当前大模型应用中广泛采用的一种对话 API 形式。它以 messages 为核心，通过一次请求生成一次回答；工具调用、历史管理和多轮 Agent 循环，则主要由客户端负责。随着 Agent 应用的发展，模型调用逐渐从“输入一段文本、返回一段文本”变成“理解任务 → 调用工具 → 获取结果 → 继续推理 → 再调用工具 → 最终完成任务”。在这个过程中，仅靠 messages、tool_calls 和客户端循环来表达整个执行过程，会让应用层承担越来越多的状态和编排工作。Responses API 正是在这个背景下出现的。它没有简单地给 Chat Completions 增加几个字段，而是重新定义了请求输入、响应输出、工具调用和流式事件的组织方式，使一次模型调用可以更自然地表达一个包含多种步骤的任务执行过程。

    01、为什么需要 Responses API

    先看 Chat Completions 在 Agent 场景下的四个具体痛点，Responses API 的每个设计几乎都能对应回去。

    痛点一：无状态导致每轮都全量重发。 Chat Completions 的 messages 数组要求客户端每次带上完整历史，聊得越久 prompt_tokens 越高，而且多轮工具调用时客户端要自己维护“哪次调用对应哪个结果”。Responses API 用 previous_response_id 解决：客户端只传本次新增的输入，服务端自动续接上一轮的完整上下文。

    痛点二：工具调用是两段式的哑协议。 Chat Completions 里模型返回 tool_calls，客户端执行完再把结果以 role: "tool" 塞回去。整个过程对模型来说只是“消息里多了一条 tool 消息”，协议本身不知道这是一次工具往返。Responses API 把 function_call 和 function_call_output 升级为一等公民的 item 类型，工具往返在协议里有明确语义。

    痛点三：常用能力要自己集成。 联网搜索、文件检索、代码执行、屏幕操控——这些 Agent 高频能力，Chat Completions 只给了 tools 这个通用插槽，剩下的（接搜索引擎、搭检索系统、跑沙箱）全是客户端的活。Responses API 直接内置了这些工具，声明一下就能用。

    痛点四：流式协议语义太薄。 Chat Completions 的流式响应主要以 chat.completion.chunk 为单位，通过 choices[].delta 表达内容增量；相比之下，Responses API 把响应生命周期、output item、文本增量、工具参数等拆成了更细粒度的事件类型。

    一句话总结：Chat Completions 是“对话补全”的抽象，Responses API 是“任务执行”的抽象。Agent 需要后者。

    02、请求与响应

    Responses API 的调用入口是 POST /v1/responses。整体风格和 Chat Completions 相似——POST 一个 JSON、拿回一个 JSON、可选 SSE 流式——但字段结构差异很大。

    2.1　请求体的核心字段

    {
    "model": "gpt-4o",
    "input": "北京今天天气怎么样？",
    "instructions": "回答要给出来源，不确定时明确说明。",
    "tools": [
        {
            "type": "web_search"
        },
        {
            "type": "file_search",
            "vector_store_ids": [
                "vs_abc123"
            ]
        },
        {
            "type": "function",
            "name": "get_weather",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {
                        "type": "string"
                    }
                },
                "required": [
                    "city"
                ]
            }
        }
    ],
    "previous_response_id": "resp_9xK…",
    "store": true,
    "truncation": "auto",
    "temperature": 0.7,
    "top_p": 1,
    "max_output_tokens": 2048,
    "reasoning": {
        "effort": "medium",
        "summary": "auto"
    },
    "parallel_tool_calls": true,
    "metadata": {
        "trace_id": "trace-7e2b"
    },
    "stream": true
}

    逐个说明：

    字段 说明
    model 模型 ID，语义同 Chat Completions
    input 输入内容，可以是纯字符串、一个 input item、或 input item 数组（见 2.2）
    instructions 替代 system 消息，作为“系统级指令”注入，优先级高于 input 里的用户内容
    tools 工具清单，既可以是自定义 function，也可以是内置工具类型（见 03 节）
    previous_response_id 用于将当前 Response 与上一 Response 串联起来。服务端可以根据 response 链继续使用此前的上下文，因此客户端通常不需要再次提交已经包含在链路中的历史输入
    store 是否在服务端留存这次响应（配合 previous_response_id 使用时通常要开）
    truncation 上下文超长时的策略：auto（自动截断最早的内容）/ disabled（默认，超长直接报错）
    temperature / top_p 采样参数，语义同 Chat Completions
    max_output_tokens 输出上限（含推理模型的思考 token），对应 Chat Completions 的 max_completion_tokens
    reasoning 推理模型参数：effort（minimal/low/medium/high）+ summary（是否返回思考摘要）
    text 输出格式控制，内含 format 字段（text / json_object / json_schema），对应 Chat Completions 的 response_format
    parallel_tool_calls 是否允许一次返回多个工具调用，默认 true
    metadata 最多 16 组自定义键值对
    stream 是否走 SSE 事件流
    include 指定额外要返回的内容片段，如 reasoning.encrypted_content、file_search_call.results
    user 终端用户标识
    safety_identifier 滥用监测标识
    service_tier auto / default / flex
    prompt_cache_key 前缀缓存路由提示

    注意几个与 Chat Completions 的命名差异：max_tokens 没了（统一为 max_output_tokens）、response_format 变成了 text.format、system 消息变成了 instructions、presence_penalty / frequency_penalty / logit_bias / seed / stop 这组经典采样参数在 Responses API 里没有对应字段——这是刻意的：OpenAI 认为这些“微调采样”的旋钮在 Agent 场景里价值有限，收掉了。

    2.2　input：typed items

    input 不再是简单的 messages 数组，而是类型化条目（typed items）的列表。每个 item 有 type 字段：

    item type 说明
    message 对话消息，role 可以是 user / system / developer；content 可以是字符串或多模态数组
    function_call 模型发起的一次工具调用（含 call_id、name、arguments）
    function_call_output 客户端回填的工具执行结果（含 call_id、output）
    reasoning 推理模型的思考过程（含 summary 列表，或加密态的 encrypted_content）
    item_reference 引用服务端已存的一个 item，用于跨响应复用
    file_search_call / web_search_call / code_interpreter_call 等 内置工具的调用记录，可以塞回 input 复现上下文

    message 的 content 数组元素类型也换了名字：Chat Completions 用 text / image_url / input_audio / file，Responses API 统一为 input_text / input_image / input_audio / input_file，且 image_url 里支持 image_url 字符串或 file_id 引用已上传文件。

    最关键的差异是 function_call / function_call_output / reasoning 这三种类型：在 Chat Completions 里它们被“伪装”成消息塞进 messages，在 Responses API 里它们是有明确语义的 item。这意味着客户端可以精确地重放、裁剪、引用任何一次工具往返或思考片段。

    2.3　output：多类型 items

    响应对象的核心字段：

    {
  "id": "resp_9xK…",
  "object": "response",
  "created_at": 1726567890,
  "status": "completed",
  "model": "gpt-4o-2024-08-06",
  "output": [
    {
      "type": "reasoning",
      "id": "rs_…",
      "summary": [ { "type": "summary_text", "text": "用户问天气，我需要先查一下。" } ]
    },
    {
      "type": "web_search_call",
      "id": "ws_…",
      "status": "completed"
    },
    {
      "type": "message",
      "id": "msg_…",
      "role": "assistant",
      "content": [ { "type": "output_text", "text": "今天北京 24℃，晴。", "annotations": [...] } ]
    }
  ],
  "output_text": "今天北京 24℃，晴。",
  "usage": { "input_tokens": 42, "output_tokens": 18, "total_tokens": 60 },
  "error": null,
  "incomplete_details": null,
  "metadata": { "trace_id": "trace-7e2b" }
}

    要点：

    • object 是 response（不是 chat.completion）；
    • output 是数组，元素类型有 message、reasoning、function_call、web_search_call、file_search_call、code_interpreter_call、image_generation_call、computer_call 等——内置工具的调用过程会作为独立 item 出现在这里，而不是被折叠成一条消息；
    • output_text 是 OpenAI 额外提供的拼接好的纯文本，等于把 output 里所有 output_text 拼起来，省去客户端遍历；工具调用、纯 reasoning 响应等场景它会是空串，别拿它当唯一判断依据；
    • status 是状态机：queued / in_progress / completed / incomplete / failed / cancelled；incomplete 时 incomplete_details.reason 会说明原因（如 max_output_tokens 截断）；
    • usage 的字段名也变了：input_tokens / output_tokens / total_tokens（对应 Chat Completions 的 prompt/completion/total），明细同样在 input_tokens_details / output_tokens_details 里（含 cached_tokens、reasoning_tokens）。

    2.4　流式：事件流

    stream: true 时返回的还是 SSE，但事件语义完全不同。每个事件有 type 字段，按响应生命周期依次出现：

    事件类型 含义
    response.created 响应对象已创建
    response.in_progress 开始生成
    response.output_item.added 一个新的 output item 开始（如一段 reasoning、一次工具调用、一条消息）
    response.content_part.added item 内新增一个 content part
    response.output_text.delta 文本增量
    response.output_text.done 一段文本完成
    response.output_item.done 一个 output item 完成
    response.function_call_arguments.delta / .done 工具参数的增量 / 完成
    response.completed 整个响应完成
    response.failed / response.incomplete / response.cancelled 异常终态

    对比 Chat Completions 只有 delta 一种语义，Responses API 的事件流可以直接驱动 Agent 的状态机：收到 output_item.added 就知道“开始调工具了”，收到 response.completed 就能拿到完整响应对象。response.output_text.delta 里的 delta 字段才是真正的增量文本，别和 Chat Completions 的 delta 混为一谈。

    03、内置工具

    Responses API 最大的增量价值在这一节。tools 数组里除了自定义 function，Responses API 还支持多种托管工具，例如 web search、file search、code interpreter、computer use以及 MCP 等。具体工具类型和参数应以当前 API Reference 为准。

    工具 type 作用 关键参数
    web_search 联网搜索，模型自行决定搜什么、引用结果 search_context_size（low/medium/high）、user_location
    file_search 在已上传的向量库里语义检索 vector_store_ids、max_num_results、ranking_options
    code_interpreter 在服务端沙箱里跑 Python container（指定代码执行容器，可自动创建）
    computer_use_preview 操控浏览器或桌面（截图、点击、输入） environment（browser/mac/windows）、display_width/height
    mcp 连接外部 MCP 服务器，把远端工具列表并入本次调用 server_label、server_url、allowed_tools
    function 自定义函数，语义同 Chat Completions 的 tools name、description、parameters、strict

    几个使用要点：

    • 内置工具是服务端执行的。你声明 { "type": "web_search" } 之后，联网请求由 OpenAI 基础设施发起，检索结果以 web_search_call item 出现在 output 里，并在正文里带来源 annotations。你不需要写任何爬虫或调搜索引擎的代码。
    • file_search 需要先建向量库。通过 Files API 上传文件、建 vector store、把 vector_store_id 传进 file_search 工具，之后模型在需要时自动检索。这是 RAG 的“托管版”，代价是把数据和索引放在了 OpenAI 侧。
    • mcp 工具让外部工具集即插即用。只要对方提供一个符合 MCP 规范的 server URL，声明 {"type":"mcp","server_url":"..."} 后，该 server 暴露的工具就并入了本次调用的可选工具集。这是 Responses API 与 MCP 生态最直接的打通点。
    • 计费方式不同。自定义 function 的调用本身不额外收费（和 Chat Completions 一样按 token 计），但内置工具按使用计费——web_search 按次、code_interpreter 按会话时长、file_search 按存储与查询量。上量前要把这部分成本算进账单模型。
    • 工具组合可以叠加。一次请求可以同时声明 web_search + file_search + 自定义 function，模型按需选择，output 中会包含模型在本次响应过程中产生的相应 tool call items，客户端可以根据 item 类型和状态处理工具调用过程。这是 Chat Completions 时代要靠 LangChain 之类框架编排才能做到的事。

    04、Responses API 与 Chat Completions 的区别

    把两边的核心差异摆在一起看：

    维度 Chat Completions Responses API
    设计目标 通用对话 Agent 原生
    状态管理 无状态，客户端拼 messages 有状态，previous_response_id 续传
    输入字段 messages 字符串消息数组 input typed items（含 reasoning / function_call_output）
    输出结构 choices[].message.content output[] 多类型 items + output_text 拼接字段
    工具生态 用户自定义 tools 为主 自定义 + 内置（联网 / 文件 / 代码 / 电脑 / 生图 / MCP）
    上下文控制 max_tokens / max_completion_tokens truncation：auto 或 disabled
    响应类型 object: chat.completion object: response，含 status 状态机
    流式事件 SSE chunk（只有 delta 增量一种语义） 事件流（created / output_item.added / text.delta / completed …）

    再补几个表格装不下的细节：

    响应生命周期。 Chat Completions 的典型交互模型是一次请求对应一次 completion；多轮状态通常由客户端在请求之间维护。Responses API 的 response 是有生命周期的资源：GET /v1/responses/{id} 可以随时回查，DELETE 可以删除，cancel 可以取消进行中的响应（长任务 Agent 的刚需）。

    多轮上下文。 Chat Completions 完全靠客户端拼 messages；Responses API 有三条路：previous_response_id 链式续传（最省事）、conversations API 显式管理会话（POST /v1/conversations 建、往里 append item）、或者仍然手动拼 input items（兼容旧习惯）。

    输入内容的组织方式。 Chat Completions 的 messages 是“对话”的抽象，所有东西都要包装成一条消息；Responses API 的 input 是“事件序列”的抽象，消息、工具调用、工具结果、思考过程平铺在一个数组里，顺序即时间线。

    错误处理。 Chat Completions 的错误要么在 HTTP 层（4xx/5xx）要么在响应体 error 字段；Responses API 为 response 和部分 output item 提供更细粒度的状态信息，客户端可以据此判断响应或特定操作的执行状态。

    05、Responses API 对 Agent 应用的影响

    这是 Responses API 真正的价值所在，也是本文想强调的落脚点。

    5.1　Agent 框架的职责被部分替代

    一个典型的 Chat Completions Agent 框架要自己实现：消息历史管理、工具注册与 schema 描述、tool_calls 解析与分发、结果回填、多轮循环控制、流式拼接、错误重试。LangChain、LlamaIndex 的很大一部分代码就是在填这些坑。

    Responses API 把其中一半直接收进了协议：历史靠 previous_response_id，工具往返是原生 item，内置工具省掉自建集成，事件流天然驱动状态机。OpenAI 自家的 Agents SDK 就是建立在 Responses API 之上的——Responses API 把部分原本需要由 Agent 框架自行实现的底层能力下沉到了 API 层，但复杂 Agent 的状态管理、工作流编排、人工介入、持久化和业务策略仍然需要框架或应用层解决。

    5.2　可观测性和调试体验的跃迁

    Chat Completions 时代做 Agent 轨迹分析，你要自己解析消息流、按 role 和 tool_call_id 拼装出“模型先想了什么、调了什么工具、拿到什么结果、最后怎么答”的完整链路。Responses API 的 output 数组天然就是这条链路——每个 item 有独立 id、类型、status，工具调用还带耗时与引用。配合 store: true 和 GET /v1/responses/{id}，轨迹可以直接回查、对比、回放，不用自己搭观测层。

    对做评估（evals）的团队，这个改变尤其大：以前 eval 脚本要自己从 messages 里抠工具调用序列做 diff，现在直接 diff 两个 response 的 output 数组就行。

    5.3　Agent 能力的上限被抬高

    内置工具让“Agent 能做什么”的天花板直接抬了一截：

    • web_search 让模型可以实时获取信息，不再被训练数据截止日期困住
    • computer_use_preview 让 Agent 直接操作 GUI，把“浏览器自动化”从外挂工具变成协议能力
    • mcp 让你接第三方工具不再需要写 glue code，符合规范的 server 直接接入

    这些能力在 Chat Completions 里都能做，但每个都要自己搭一遍集成、自己处理鉴权与限流、自己维护沙箱。内置工具把它们变成“一行配置”，Agent 迭代的节奏会因此明显加快。

    5.4　代价与风险

    三个必须正视的问题：

    厂商锁定。 前面说过，Responses API 的内置工具、item 类型、conversations API 都是 OpenAI 私有。一旦用上，换模型的成本不只是换 model 字符串，而是要重写工具调用层。对模型可移植性有硬需求的团队，要么把 Responses API 隔离在适配层后面，要么继续留在 Chat Completions。

    数据边界。 file_search 和 code_interpreter 意味着你的数据和代码会在 OpenAI 的基础设施上被处理和存储。合规敏感的场景要仔细评估数据协议、区域选择（store 的留存范围、vector store 的区域）和删除策略。

    成本结构变化。 内置工具按次/按时长计费，Agent 一次任务可能触发多次工具调用，账单结构从“纯 token”变成“token + 工具使用”。Agent 的设计要在“多调几次工具换准确性”和“控制工具调用次数”之间做权衡，上量前要压测单任务的平均成本。

    06、工程实战的四个建议

    6.1　什么时候迁移

    三条经验法则：新项目直接上 Responses——除非你有明确的跨厂商需求；存量项目按需迁——如果你在自建检索、自跑沙箱、自己拼 messages 历史，迁移的 ROI 明显为正，如果只是简单的单轮问答，Chat Completions 足够用，不值得动；多厂商混合的场景分层处理——把 Responses API 的能力放在适配层后面，核心业务逻辑保持协议无关。

    6.2　内置工具的取舍

    内置工具不是免费午餐。判断标准是“数据的敏感度”和“是否已有自建设施”：已经有自建 RAG（向量库 + 检索服务）的团队，继续用自定义 function 把自家检索服务暴露给模型，比迁到 file_search 更稳；没有自建能力、想快速上线的团队，file_search 和 web_search 能省下几周工程时间；code_interpreter 适合“让模型自己验证答案”的场景，但要注意沙箱里跑的是你的数据。

    6.3　与 Chat Completions 共存

    OpenAI 明确表示 Chat Completions 会继续支持，不是弃用关系。两个协议共用同一套模型与鉴权，你可以在同一个应用里按场景选用：对话类、多厂商兼容的场景走 Chat Completions，Agent 类、需要内置工具的场景走 Responses API。store 字段两边都有，但 previous_response_id 是 Responses 独有的——跨协议不共享上下文，不要指望在两个接口之间接力。

    6.4　先想清楚状态归属

    Responses API 最诱人的是“服务端管状态”，但状态放服务端意味着：会话续期、数据删除、跨区域迁移都要走 API。强烈建议在接入前就想清楚：哪些状态允许放服务端（比如可以随时删除的对话历史）、哪些必须留在自己手里（比如用户身份数据、业务敏感上下文）。把 store 和 previous_response_id 的组合用对——长期会话用 conversations API，短链路任务用 previous_response_id，一次性任务干脆 store: false。
