    二、Prompt 的技巧

    提示词技巧不是一串能背下来的咒语，而是一组按需取用的杠杆：有的负责消除歧义，有的负责提供示范，有的负责把输出的形状锁死。用错杠杆，比不用更费力。

    上一篇拆开了 Prompt 的零件，也讲了它对模型的输出施加影响的三条机制。但知道零件不等于会组装——真正落地时，你会遇到另一类问题：模型理解得对，但风格不对；风格对了，但推理不到位；推理到位了，格式又解析不了。这篇文章把这些具体麻烦对应的方法整理成一张地图：零样本、少样本、角色提示、思维链、任务分解、输出格式约束与结构化输出，最后回到最容易被忽视的一层——上下文该如何组织。

    01、一张方法地图

    在逐个展开之前，先给这些方法分个类，后面就不会把它们当成互斥的选项。按作用方向看，常见方法大致作用在三个方向：

    • 减少歧义。零样本提示、角色提示属于这一层。它们不改变模型的能力，只试图让你想表达的意思更少被误解——通过更明确的指令措辞，或更具体的身份设定。
    • 提供示例。少样本提示、思维链、任务分解属于这一层。它们通过给模型看例子、看推理路径、看任务切分方式，把你要的行为模式“示范”出来，让模型在新输入上延续这个模式。
    • 约束输出。输出格式约束和结构化输出属于这一层。它们不关心模型怎么想，只关心输出长什么样，能不能被下游程序或人稳定消费。

    而“上下文组织”不属于以上任何一个方向，它是编排层：决定了前面三类信息在 Prompt 里的位置、顺序和主次。同一个方法，组织方式不同，效果可能差别很大。

    需要说明两点。第一，这份清单列的是最常见、最重要的一组方法，不构成完整枚举——提示词领域每年都在长出新的技巧，遇到没见过的名字，先按“它属于哪一层”归位，比记忆名字更有用。第二，本文写于 2026 年 9 月，涉及具体模型行为的部分（尤其是与具体模型绑定的推理类技巧），请以你使用模型时的官方文档为准。

    02、Zero-shot：不举例，只说清楚

    Zero-shot，零样本提示是最基础的用法：不给任何示例，直接用自然语言描述任务，让模型完成。它成立的前提，是模型经过指令微调，已经具备“听懂任务描述”的能力——这在早期的语言模型上是行不通的，那时候不给例子模型几乎不会做事。

    零样本的成败几乎完全取决于指令质量，所以它更像是把上一篇讲的指令写法做到极致的检验：动词明确、对象清晰、边界清晰。一个实用的自检方法是，把 Prompt 交给一个不了解背景的同事看，如果他读完能一次性知道该做什么、输出是什么样，模型通常也能。

    它的优势是短、便宜、可读，适合高频调用、任务简单、格式要求不高的场景。它的局限也明显：当任务带有隐含的判断标准（什么是“好的标题”？什么算“相关的段落”？），而这些标准又难以用一两句话说清楚时，零样本会开始不稳定。这时候该往上走一层，给例子。

    03、Few-shot：给模型看几个例子

    Few-shot，少样本提示是在 Prompt 里带上若干“输入—输出”示例，让模型照猫画虎。它在 GPT-3 论文里被系统验证过：模型不更新参数，仅凭上下文中的少量示例就能在新任务上表现明显提升，这一现象被称为上下文学习（In-Context Learning）。

    少样本的收益来自模式示范，所以示例的“质量”比“数量”重要得多。几个实操要点：

    • 示例中要有你想让模型学会的那个判断。分类任务里，如果示例全是容易区分的正例，模型学到的是“大概都能判成正类”；带上两个边界样本，它才学到你的标准。
    • 格式必须严格一致。模型会忠实模仿示例里的一切，包括你不想要的瑕疵——示例里输出带一句解释，正式输出也会带。
    • 注意示例里的分布偏差。如果示例的标签明显偏向某一类，模型会倾向于多输出那一类，这是少样本的常见陷阱。
    • 数量存在收益递减。从 2 个加到 5 个示例通常有提升，从 20 个加到 50 个通常没有，反而挤占上下文预算。

    还有个容易被忽略的收益：少样本同时是一种格式约束手段。你不需要用文字描述输出结构，示例本身就是结构说明。

    04、Role Prompting：设定身份

    Role Prompting，角色提示是给模型设定一个身份——“你是一位资深数据库工程师”“你是一位面向零基础读者的科普作者”。它有时写在系统提示词里（对整个应用生效），有时写在单次输入里。提示主要影响语言风格、术语密度、叙述口吻和关注点：同一个问题，用“儿科医生”和“医学期刊审稿人”的身份提问，答案的用词和详略程度会明显不同。

    但它不会凭空带来知识或能力。让模型扮演“顶级律师”，它并不会因此变得更容易答对具体的法条细节；角色不是知识库，也不是能力开关。因此更稳妥的用法是：用角色提示来锚定风格和视角，用上下文和资料来提供事实，两者别混为一谈。另外，角色设定越具体，收益越明显——“你是一位写技术文档的工程师”远不如“你是一位为内部开发者写 API 使用说明的工程师，读者已经熟悉基本概念”来得有效。

    05、Chain-of-Thought：让推理过程显式展开

    Chain-of-Thought，思维链提示属于“提供示范”：不直接要答案，而是要求模型先给出推理步骤，再给结论。它的经典形式是在示例里展示完整推理过程（少样本思维链），后来也发展出只需一句“让我们一步步思考”的零样本形式。

    它为什么有效？因为对需要多步推理的任务（数学、逻辑、多约束判断），模型在自回归生成时是一步一步产生的——把中间步骤写出来，等于给后续生成更多的中间结果作为条件，减少了一步跳错、后面全错的概率。更进一步的做法是自洽性（Self-Consistency）：让模型用不同路径推理多次，再对最终答案投票，用采样的多样性换取稳健性。

    使用时需要注意以下几点：

    • 思维链不是万能增幅器。对于检索事实、格式转换这类没有推理链的任务，强行要求分步思考只会增加 token 成本和延迟，甚至让模型在无关细节上自我纠缠。
    • 它与模型特点强相关。部分较新的模型中内置了思考过程，模型自己会决定展开多少推理——对这类模型，显式要求“一步步思考”的收益会明显下降，是否仍然需要、以及该用哪种形式，请以目标模型的当期文档为准。
    • 思维链要不要展示给用户是产品决策。内部推理过程往往冗长且不适合终端阅读，常见做法是要求模型按“先分析后结论”的结构输出，或只输出结论，把过程留在模型内部。

    06、Task Decomposition：把大任务拆成多次调用

    Task Decomposition，任务分解是把一个复杂目标拆成若干子任务，分步完成——既可以拆成一次 Prompt 内的多个步骤，也可以拆成多次模型调用，让上一步的输出成为下一步的输入。

    它和思维链的区别在于粒度：思维链是在一次调用内展开推理，任务分解是把任务本身切开，每一步都更小、更可控、更容易检查。当任务里出现“先抽取再归类再改写”这类异质环节时，拆开几乎是必然选择——因为不同环节需要不同的指令、不同的输出格式，硬塞进一次 Prompt 只会互相干扰。

    两个实用模式：一是流水线式，步骤有明确先后依赖，逐级传递结果；二是从易到难式，先解决简单子问题，再把简单问题的结论作为上下文去攻难的部分。前者更常见，后者适合需要积累中间结论的任务。

    任务分解的额外价值是可验证性。每一步输出都可以单独校验、单独重试、单独缓存。当一次调用失败时，你只需要重跑失败的那一步，而不是整个流程。代价是调用次数和延迟上升，以及错误可能在步骤间传递——所以每一步都要有格式和内容上的检查点。

    07、输出格式约束与 Structured Output

    7.1　输出格式约束

    严格来说，格式约束属于上一篇讲的“输出格式”的强化版：不只是说明要什么格式，而是用可执行的方式把格式钉住。常用手段有三种——给出目标结构的样例、逐字段说明类型和取值范围、明确禁止多余内容（比如“只输出 JSON，不要代码块包裹，不要任何解释文字”）。

    这里有个反复出现的经验：正向表述比负向表述有效。与其写“不要输出太长”，不如写“不超过三句话”；与其写“不要用术语”，不如写“用日常词汇解释，术语第一次出现时附一句说明”。模型对“做到什么”的执行力，普遍好于对“避免什么”的规避力。

    还要预期失败模式。自然语言约束始终是概率性的：模型可能加上一句“好的，以下是结果”，可能用 markdown 代码块把 JSON 包起来，可能在数组末尾多一个逗号。所以任何自动解析的链路都必须有容错——剥离代码块围栏、跳过前导文本、解析失败时重试并收紧约束。指望“写清楚了就 100% 稳定”，是在给系统埋雷。

    7.2　Structured Output：由协议保证的形状

    如果你需要的是“语法层面保证合法”的结构化数据，那就不要只靠自然语言约束，而应该使用模型服务商提供的结构化输出能力。目前主流大模型厂商都提供了这类机制，但形态不同：有的提供 JSON 模式（保证输出是合法 JSON，但不保证字段符合你的 schema），有的支持用 JSON Schema 声明字段与类型并对生成过程施加约束（即约束解码，让模型在每一步只能生成符合 schema 的数据），还有的通过“让你声明工具及其参数 schema、由模型填充参数”的路径达到类似效果。

    使用时注意几点：

    • schema 越严，越要写全。字段是否必填、枚举取值、是否允许额外字段，这些信息不写清楚，模型只能自由发挥。枚举类字段建议列全取值，同时客户端仍应保留对未知值的兼容分支。
    • 语法合法不等于语义正确。约束解码保证的是结构合规，不保证内容正确——字段填错了值，解析照样成功。校验必须做在业务层。
    • 能力名称与启用方式会变。同一个厂商的不同模型对结构化输出的支持程度不同，部分能力初期以 beta 形式提供、需要额外请求头或参数，写法也随版本演进。请以当期官方文档为准，不要照抄旧文章里的字段名。
    • 宽容解析。即使有 schema 约束，下游仍应对未知字段和未知枚举值保持宽容，避免上游一次小改动打挂整条链路。

    08、Prompt 中的上下文组织

    8.1　位置决定权重

    前面三类方法讲的都是“放什么”，这一节讲“放在哪”。原因在之前提到过的注意力机制：长上下文里，不同位置的信息获得的注意力并不均等，开头和结尾通常更受关注，中段容易被稀释，这就是所谓的“Lost in the Middle”。

    由此有两条被广泛采用的实践：把重要的指令和最终的问题放在开头或结尾，而不是埋在材料中间；在长材料场景里，先给文档、后给问题，让问题紧贴生成位置。前者是通用原则，后者是常见做法——不同模型对顺序的偏好并不一致，必要时用几条真实样本做 A/B 测试，比照搬结论可靠。

    另一种有效的组织手段是显式分区：用 XML 标签、三引号、标题或分隔线把 Prompt 切成指令区、资料区、输入区、示例区。这既帮助模型区分“要处理的材料”和“处理的要求”，也降低了材料本身含有指令样式文字时的混淆风险。当资料是一整篇文档时，还可以用“先给一句摘要、再给全文”的方式降低模型在长文中丢失重点的概率。

    8.2　指令、数据与示例如何组织

    把三者放在一起看，一个稳定的组织骨架通常是这样的顺序：

    1. 角色与总目标：一句话交代身份和要达成的目标，让模型先建立语境。
    2. 资料与数据：紧跟着给上下文材料，用标签包裹并说明它是什么。长材料放前面。
    3. 任务指令：明确要做什么、怎么做，指向上面的资料标签。
    4. 示例：给出一致格式的少样本示例，示范判断标准和输出形状。
    5. 约束与输出格式：把长度、禁止项、字段结构集中说明，避免散落各处。
    6. 输入与收尾提醒：给出本次要处理的具体内容，并在最后用一两句重申最关键的一两条约束。

    这个骨架有两个设计意图。一是就近原则：最关键的要求离生成位置最近，权重最高。二是分区原则：指令、数据、示例各有归属，不互相污染——这也是为什么把用户输入和系统指令混在同一段里是危险的：一旦输入里出现指令样式的文字，模型可能把它当作要求执行。

    组织顺序不是教条。不同厂商的官方指南对“长文档在前还是问题在前”的建议存在差异，不同模型的长上下文特性也在变，所以更稳妥的态度是：把上面这套骨架作为默认起点，然后用你自己的真实任务做几组对照实验，把结论固定在你的 Prompt 模板里。
