    MCP 的原理：从连接、发现到调用

    上一篇停在“MCP 是什么”，这一篇走进协议内部。前面反复说“客户端问服务器有哪些工具、哪些数据、哪些提示模板”，可“问”这件事本身是怎么发生的——消息长什么样、连接怎么建立、清单怎么传到模型手里、一次调用怎么走完——这些问题一直悬着。这一篇把它们一个个落到消息和方法上，落到具体的字段上。

    先给这一篇立一条主线，后面所有小节都回扣它：MCP 可以从三个层次理解——连接、发现、调用。连接解决消息怎么传，发现解决能力描述从哪里来，调用解决具体能力如何执行。三者在典型使用路径上通常依次出现，但要先说清一点：在 2026-07-28 的 modern era 里，“发现”并不是“调用”之前的强制步骤——协议没有握手机制，客户端完全可以跳过发现、直接对已知的能力发起调用。把三个词当理解框架，不要当成严格的协议状态机。

    注意：本文写作于 2026 年 9 月，以协议版本 2026-07-28 为准。MCP 的协议版本用日期字符串标识，且会把某些特性标记为 Deprecated。文中反复出现的两个词需要先交代：官方按“怎么协商版本、怎么建立连接”把协议版本分成两代——modern era 指 2026-07-28 及之后的版本（无握手，每个请求自己携带版本与能力），legacy 指 2025-11-25 及更早的版本（连接建立时先做 initialize 握手）。这一篇涉及生命周期、能力协商这些与版本强绑定的内容，正文里会明确区分“协议里稳定的结构”和“某一代版本的具体写法”。凡方法名、字段名与版本行为，请以所用版本对应的官方规范为准；文中产品名只作举例。

    01、进入协议层：消息长什么样

    上一篇讲过三个角色、数据层和传输层，那是站在“链上有哪些东西”的高度看。这一章往协议层走一步，把两件事讲透：消息的确切结构，以及消息怎么从一端送到另一端。先记住一个不变的前提：MCP 的消息全部是 JSON-RPC 2.0，无论跑在哪种传输上，消息的语义都不变——传输只决定消息怎么送，不决定消息是什么意思。

    1.1　JSON-RPC 的三类消息

    一个 MCP 连接上，来回跑的只有三种消息：request、response、notification。

    Request（请求）。客户端发给服务器，用来发起一个操作。规范要求的结构是四个字段：jsonrpc（固定字符串 "2.0"，协议标识）、id（本请求的唯一标识）、method（方法名，如 "tools/call"）、params（可选，参数对象）。

    {
  "jsonrpc": "2.0",
  "id": string | number,
  "method": string,
  "params": { ... }
}

    id 上有三条硬约束：它必须是字符串或整数；与基础 JSON-RPC 不同，它不允许为 null；它不能与发送方已发出但尚未收到响应的任何其他请求的 id 重复。这三条合在一起，保证了 id 能在“请求—响应”这一对关系里做唯一的路由键。

    Response（响应）。服务器发给客户端，对应某个 Request，id 必须与它回应的那个请求完全一致。它分两种结局，二选一。

    成功时带 result 字段：

    {
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "resultType": "complete",
    ...
  }
}

    在 2026-07-28 modern era 中，result 里要求一个 resultType 字段，用来声明这次结果的类型——"complete" 表示请求成功完成、结果是最终内容；"input_required" 表示请求未完成、还需要客户端补充输入（这是上一篇讲的 Elicitation / MRTR 机制在响应里的落点）。规范允许扩展新增 resultType 值，客户端遇到不认识的值必须按非法处理。要分清版本边界：resultType 是 modern wire protocol 的必需字段，早期版本里根本没有这个字段；对着旧版本服务器交互时的兼容行为，由对应版本的协议和 SDK 处理。

    失败时带 error 字段：

    {
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32602,
    "message": "Unknown tool: get_wheather",
    "data": { ... }
  }
}

    error 的结构是 code（整数，必填）、message（字符串，一句话简述，必填）、data（任意类型，可选，用来塞附加信息）。error 和 result 互斥，一个响应只能带其中一个。

    Notification（通知）。没有 id，接收方不得回任何响应，发出去就完。它承载“不需要对方答复”的信息：进度更新、清单变化、取消一个还在执行的请求。规范只允许两个字段：jsonrpc 和 method（外加可选 params）：

    {
  "jsonrpc": "2.0",
  "method": "notifications/tools/list_changed"
}

    一个结构上的要点值得单独说：在 2026-07-28 modern era 中，消息的方向是固定的——客户端发送 Request 和 Notification，服务器返回 Response、并通过协议规定的订阅流发送相关 Notification；服务器不再直接向客户端发起 JSON-RPC Request。服务器需要客户端提供额外信息时，通过 input_required 结果进入多轮请求流程（后面 4.2 展开）。这不是 MCP 一直以来的样子：2025-11-25 及以前的版本里，服务器确实可以反过来向客户端发 Request（采样、根目录、Elicitation 的旧实现都走这条路），2026-07-28 把这条反向通道移除了。这一条把“谁主动”定死了，是理解后面所有交互的钥匙。

    1.2　错误码

    错误码不是随便填的整数，规范把它管得很细。通用协议故障用标准 JSON-RPC 2.0 错误码，五个：-32700（Parse error，收到无法解析的 JSON）、-32600（Invalid Request，消息结构不符合请求对象要求）、-32601（Method not found，方法不存在或未宣告对应能力）、-32602（Invalid params，参数无效——工具场景里就是“未知工具名或非法参数”）、-32603（Internal error，接收方内部错误）。

    在这个之上，MCP 把 JSON-RPC 预留的 -32000 到 -32099 区间做了划分：-32000 到 -32019 是 legacy 保留区，历史上曾被不同实现使用，新实现不应再依赖其中具体错误码。需要特别注意“资源未找到”这个错误：早期版本用过 -32002，但在 2026-07-28 里已经统一用标准 JSON-RPC 的 -32602（Invalid params）——对着旧服务器互操作时才需要考虑 -32002。-32020 到 -32099 保留给 MCP 规范专用，实现只能发射规范已定义的码，且必须按规定的语义用。目前规范在这一段定义了三个：-32020 HeaderMismatch（HTTP 头与请求体不一致）、-32021 MissingRequiredClientCapability（处理请求需要客户端未声明的能力，data 里列出缺的能力）、-32022 UnsupportedProtocolVersion（不支持的协议版本，data 里给出 supported 和 requested）。

    这个划界值得记住，因为它回答了一个常见问题：遇到错误时先看 code 落在哪一段，就能大致判断是 JSON-RPC 层的故障、还是 MCP 协议层定义的特定错误。

    1.3　_meta：协议元数据的固定位置

    2026-07-28 modern era 的请求通过 params._meta 携带协议元数据——注意位置，_meta 不是 JSON-RPC 消息的顶层字段，而是挂在请求参数里的。键名格式是“可选前缀 + / + 名字”，前缀推荐用反向 DNS 记法（如 com.example/）；第二段是 modelcontextprotocol 或 mcp 的前缀被协议保留，实现不能占用。

    modern era 里最关键的保留键有三个，都挂在 io.modelcontextprotocol/ 下，且其中两个是每个请求必填的。放进一个完整请求里看它们的位置：

    {
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": { "name": "ExampleClient", "version": "1.0.0" },
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

    三个键的分工：protocolVersion 必填，是本请求的协议版本；clientInfo 建议填，是客户端身份；clientCapabilities 必填，是本请求相关的客户端能力。

    规范的要求很硬：缺了必填字段的请求是畸形请求，服务器必须以 -32602（Invalid params）拒绝，HTTP 上响应状态必须是 400 Bad Request。服务器也不得依赖客户端没声明过的能力——如果处理某个请求需要一项客户端没在 clientCapabilities 里声明的能力，服务器必须返回 MissingRequiredClientCapabilityError（-32021），并在 data.requiredCapabilities 里列出缺哪几项。clientInfo 和后面会讲的 serverInfo 都是自报身份、协议不做校验，只用于展示、日志和调试，不该被拿来做行为分支或安全决策。

    这个设计支撑的是 modern era 的协议层无状态：服务器处理一个请求时，不需要依赖同一连接上此前请求建立的状态。注意边界——无状态的只是协议层，应用本身仍然可以保存业务状态；跨越多个请求的状态（比如长任务的句柄）由显式的标识符承载，客户端每次请求带上它，而不是靠连接隐式维持。

    02、消息怎么跑：两种传输的具体要求

    传输层管“JSON-RPC 消息怎么从一端送到另一端”。规范给了两种标准传输，协议语义完全一致。这一节把两者的具体要求都铺开，因为这是把 MCP 真正用起来时最先踩到的一层。

    2.1　stdio

    stdio 下，客户端把服务器拉成一个本地子进程，两端通过子进程的标准流通信。分帧规则一句话：消息以换行分隔，每条是一个完整的 JSON-RPC 消息，不得含嵌入换行。围绕这条规则，规范给了一串硬约束：

    • 服务器从 stdin 读消息、往 stdout 写消息；stdout 上只准写合法的 MCP 消息，不准写任何别的。
    • 客户端不准往服务器 stdin 写非 MCP 消息的东西。
    • 服务器可以往 stderr 写任意 UTF-8 日志（信息、调试、错误都行）；客户端可以捕获、转发或忽略这些输出，但不该把 stderr 有输出当成出错的信号。
    • 客户端只写 Request 和 Notification，不准写 Response；服务器只写 Response 和 Notification，不准写 Request。

    进程生命周期也被规范定义了。客户端发起的关闭顺序是：先关掉到子进程的输入流，等服务器退出，超时再按操作系统的方式强制结束（POSIX 上从 SIGTERM 升级到 SIGKILL）。服务器在 stdin 被关闭或读到 EOF 时应该尽快退出——这是唯一可移植的优雅关闭信号。如果服务器进程意外退出，客户端应该重启它；因为协议层是无状态的，正在执行中的请求会随进程终止而丢失，客户端如果需要继续执行，对着新进程重新发起即可。

    stdio 也有自己的取消方式。因为 stdio 是一条共享的双向通道、没有按请求划分的流，客户端要取消一个还在执行的请求，只能发一条 notifications/cancelled 通知、带上那个请求的 id；服务器应该尽快停止这个请求的工作，并且取消后不得再为它发任何消息。

    stdio 面向的是“同一台机器上的本地服务器”，典型情况是一对一服务一个客户端，没有网络开销。

    2.2　Streamable HTTP

    Streamable HTTP 面向远程服务器，是所有“一个服务器服务很多客户端”场景的选择。它的核心形状极简：每条 JSON-RPC 消息都是一个新的 HTTP POST，发往单一 MCP 端点。围绕这个形状，规范的要求分成几层。

    客户端 POST 的硬要求：必须带 Content-Type: application/json（请求体就是 JSON），并带 Accept 头、同时列出 application/json 和 text/event-stream 两种类型；请求体是单个 JSON-RPC Request，不准是 Response；每个 POST 都要带请求元数据头（见下）。要注意，modern era 的 Streamable HTTP 不再定义普通的客户端到服务器 Notification——stdio 上的 notifications/cancelled 在 HTTP 上没有对应物，取消的表达方式见本节末尾。

    服务器响应的两种形式：对 Request，服务器必须在两者中选一个返回——Content-Type: application/json（单个 JSON 对象），或 Content-Type: text/event-stream（一条 SSE 流）。客户端必须同时支持两种。SSE 流允许服务器在最终响应前先发与这个请求相关的通知（如 notifications/progress），但这些通知必须与原始请求相关，且最终响应应该结束这条流。

    协议版本与镜像头：每个 POST 必须带 MCP-Protocol-Version 头，值必须与请求体 _meta 里的 protocolVersion 完全一致，不一致就 400 Bad Request + HeaderMismatch。此外还有两个把请求体字段镜像到 HTTP 头的标准头，供负载均衡器、网关这类不解析请求体的中间件路由和检查：Mcp-Method（镜像 method，所有请求必填）、Mcp-Name（镜像 params.name 或 params.uri，tools/call、resources/read、prompts/get 必填）。服务器必须校验头与体一致，防止“负载均衡器按头路由、服务器按体执行”造成的安全漏洞。

    三道安全闸：其一，服务器必须校验所有入站连接的 Origin 头，防 DNS rebinding 攻击，Origin 存在但无效时返回 403 Forbidden；其二，本地运行时服务器应该只绑定 127.0.0.1，不要绑所有网卡；其三，服务器应该为所有连接实现适当的身份认证。

    一个容易被旧资料带偏的点：旧版 Streamable HTTP 里，客户端可以用 GET 打开一条接收服务器主动消息的事件流，Mcp-Session-Id 会话头也随之存在——这套机制是 2025-03-26 到 2025-11-25 的写法，2026-07-28 把两者都移除了。现代协议不再使用 Session/GET 模型：服务器收到 GET 或 DELETE 应该返回 405 Method Not Allowed；带 Mcp-Session-Id 的请求应该被忽略，服务器不再生成或回显会话 ID。这呼应了 modern era 的协议层无状态——不再有协议级的会话。

    取消的表达：客户端直接关掉那条请求的 SSE 响应流，服务器必须把这视为取消，尽快停止工作，取消后不得再为该请求发任何消息。对比 stdio 发 notifications/cancelled 的做法，这里连一条消息都不用发——断流本身就是信号。

    03、生命周期：连接怎么建立、怎么结束

    生命周期讲“一次连接从生到死经过哪些状态”。这里有一个必须说清的分界：握手式生命周期属于 2025-11-25 及更早版本；从 2026-07-28 起的 modern era 已经取消了握手。两代分开记，才不会被手上的旧示例带偏。

    3.1　握手式生命周期（legacy）

    旧版本里，一个连接要经过五个状态，最核心的是开头的一次 initialize 握手：

    Initialize（初始化）。客户端先发 initialize 请求，带 protocolVersion、capabilities、clientInfo；服务器回 initialize 响应，带 capabilities、serverInfo。

    Capability Negotiation（能力协商）。就发生在这个握手往返里：双方通过 initialize 请求和响应里的 capabilities 字段互相声明“我支持什么”，据此确定这次连接里哪些功能可用。

    Initialized（初始化完成）。客户端收到响应后发一条 notifications/initialized 通知，宣告握手结束。它没有 id、不期待回应，只是告诉服务器“可以进入正常工作了”。

    Normal Operation（正常工作）。之后进入常规交互：客户端发 tools/list、tools/call 这些请求，服务器按协商结果应答。

    Shutdown（关闭）。旧版本没有专门的关闭方法，结束就是结束传输：stdio 下子进程退出，HTTP 下连接断开。

    3.2　modern era：握手被拿掉之后

    从 2026-07-28 起，这五个状态里的“握手”被拿掉了，变化有三处：

    其一，没有 initialize 握手了。版本、能力、身份不再靠一次握手交换，而是随每一次请求携带——每个请求的 _meta 带上 protocolVersion、clientInfo、clientCapabilities（就是 1.3 那三个字段），服务器逐请求判断要不要接。

    其二，能力协商从“连接时一次谈妥”变成“逐请求携带”。没有一条建立起来的会话去承载“我们谈好了哪些能力”，每个请求自己带上当前的能力声明。需要某个客户端没声明的能力时，服务器用 -32021 拒绝。

    其三，server/discover 是服务器提供的发现入口，但不是客户端调用其他能力前的必经步骤。服务器必须实现它；客户端可以先调用 server/discover 获取服务器支持的版本、能力和身份，也可以跳过发现，直接对已知能力发起请求。它的请求不带业务参数（只有 _meta），响应结构是：

    {
  "jsonrpc": "2.0",
  "id": "discover-1",
  "result": {
    "resultType": "complete",
    "supportedVersions": ["2026-07-28"],
    "capabilities": { "tools": {}, "resources": {} },
    "_meta": { "io.modelcontextprotocol/serverInfo": { "name": "ExampleServer", "version": "1.0.0" } },
    "instructions": "This server provides weather utilities."
  }
}

    supportedVersions 是服务器支持的协议版本清单，capabilities 是它提供的能力，instructions 是服务器提供给客户端的自然语言使用说明——客户端可以根据需要把它提供给模型作为上下文，但协议没有规定这段话必须直接进模型。跳过发现直接发业务请求也完全可行：遇到 UnsupportedProtocolVersionError（-32022）就根据错误里的 supported 清单换一个版本重试。server/discover 的实际用途有两个：客户端想一次性展示服务器支持哪些能力时，不必分别探 tools/list、prompts/list、resources/list；以及在 stdio 上做新旧版本的兼容探测（没有 HTTP 状态码可依赖时，先 server/discover 探一下，探测失败再回退 initialize 握手）。

    04、工具的发现与调用

    工具是三类服务端原语里，通常由模型决定是否调用的一类（和上一篇建立的控制权概念对应：Tool 归模型、Resource 归应用、Prompt 归用户），也是从“能用”到“用上”路径最完整的一类。这一章拆成三步：先发现（tools/list），再调用（tools/call），最后回答一个常被跳过的细节——模型最终看到的到底是什么。

    4.1　发现：tools/list 把清单带回来

    客户端发 tools/list 请求，服务器回一个工具数组。请求可以带一个可选的 cursor 做分页；响应里除了 tools 数组，还可以带 nextCursor（还有更多）、ttlMs 和 cacheScope（缓存提示）。

    {
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {}
}

    响应里的一个工具，核心字段有：

    {
  "name": "get_weather",
  "description": "Get current weather for a location",
  "inputSchema": {
    "type": "object",
    "properties": { "location": { "type": "string", "description": "City name" } },
    "required": ["location"]
  },
  "outputSchema": { "type": "object", "properties": { ... } },
  "annotations": { "readOnlyHint": true },
  "title": "Weather Provider",
  "icons": [ { "src": "...", "mimeType": "image/png" } ]
}

    name 是唯一标识，调用时靠它定位；description 给模型看；inputSchema 是 JSON Schema，定义参数形状——这是模型填参数的依据，必须是合法 JSON Schema（无参数时用 { "type": "object", "additionalProperties": false }）。outputSchema 描述的是工具的结构化输出：服务器声明了它，就应提供符合该 schema 的结构化结果（放在 structuredContent 字段）；content 数组则是另一路，放给人或模型看的文本形态，两者不要混为一谈。title、icons 用于界面展示。

    annotations 是一组提示，描述工具的行为风险，帮助客户端决定要不要先让用户确认。规范明确：这些都是提示，不保证如实描述工具行为，客户端必须把来自不可信服务器的 annotations 当作不可信。四个布尔提示及默认值是：

    提示 含义 默认值
    readOnlyHint 为真表示工具不修改环境 false
    destructiveHint 为真表示可能做破坏性更新（相对只做新增） true
    idempotentHint 为真表示同参数重复调用无额外影响（仅在非只读时有意义） false
    openWorldHint 为真表示与外部“开放世界”交互（如联网搜索），为假表示域是封闭的 true

    默认值刻意偏保守：一个没写 annotations 的工具，被假定成“非只读、可能破坏性、非幂等、开放世界”——先做最坏假设，等服务器用 hint 来收窄。

    清单本身有几个性质：它可能为空，也可能随时间变化。变化的通知在 modern era 里走订阅流：客户端先通过 subscriptions/listen 打开一条订阅、声明自己要监听工具清单变化，服务器在清单变化时于这条订阅流上发 notifications/tools/list_changed，客户端收到后再重新调 tools/list 拿最新清单——服务器不会凭空向客户端推通知，通知总是落在客户端建好的订阅流上。对于需要缓存的清单，服务器还可以通过 ttlMs 和 cacheScope 提供缓存提示，客户端据此决定自己的缓存策略。一个容易被误解的点是——tools/list 返回的是工具的描述，不是工具本身，真正执行要等下一步的 tools/call。

    4.2　调用：tools/call 走完一条完整链路

    调用用 tools/call，请求带工具名和参数：

    {
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "location": "New York" }
  }
}

    服务器执行完回一个结果，内容放在 content 数组里，通常是文本块，也可以带结构化内容：

    {
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "resultType": "complete",
    "content": [ { "type": "text", "text": "Temperature: 72°F" } ],
    "isError": false
  }
}

    这里要分清两类错误，它们走完全不同的通道。一类是协议错误：工具名不存在、参数不合法——服务器返回 JSON-RPC error（-32602）。另一类是工具执行错误：工具本身跑挂了，比如后端服务超时、业务逻辑失败——这时服务器不返回 JSON-RPC error，而是返回一个正常的 result，但把 isError 置为 true，把错误信息放进 content。区分的意义在于：协议错误意味着这次请求没有形成一次成功的工具执行（请求可能已经送达服务器，只是在校验这一步被挡下）；而 isError 表示工具已经进入执行路径、在执行过程中发生了业务或运行时错误，模型应该把后者当成一次真实的工具反馈去理解、可能重试或换参数。

    把这次调用放到整条链上看：

    模型输出一个工具调用 → 应用翻译成 tools/call → 服务器执行实际的工具逻辑 → 结果沿原路返回 → 应用回填给模型。关键在“翻译”：模型侧说“我要调 get_weather，参数 New York”，和协议侧的 tools/call 消息不是一回事，中间是应用在做映射。

    一个执行上的细节：服务器可能一次执行不完，比如还缺一个参数。它回一个 resultType 为 input_required 的结果，说“我还需要 X”；客户端收集完输入后带着 inputResponses 重新发一次原请求，注意要用一个新的 id。重发时还要原样带上服务器给的 requestState——它由服务器生成、对客户端是不透明的，客户端只负责回传，不该去解析或修改它；它也不是客户端可以信任的业务状态。这个机制不只作用于 tools/call，prompts/get 和 resources/read 同样可能返回 input_required。这跟上一篇讲的 Elicitation 是同一套机制，方向始终是客户端发起、服务器响应。

    把发现和调用两条链路并排放在一张时序图上，差别就清楚了：

    两次请求两次返回，中间隔着“翻译”这一步：tools/list 只把描述带回来，tools/call 才真正让工具跑起来。

    4.3　模型最终看到什么

    从模型那一侧看，MCP 基本是隐身的。在标准的工具调用链路里，模型通常不会直接感知 MCP 服务器的存在——应用把 MCP 服务器返回的工具定义整理成模型可用的工具描述，模型看到的是一份工具清单，每个工具一个名字、一段描述、一份参数 schema，模型据此决定要不要调、调哪个、参数怎么填。

    所以“模型最终如何看到这些工具”的答案是：它看不到 tools/list 这个动作，也看不到 MCP 协议本身，它只看到这份清单作为自己上下文的一部分。对模型而言，一个通过 MCP 发现的远程工具，和一个应用本地实现的函数，长得一模一样。这正是 MCP 能“不打扰模型”就完成接入的原因——协议的复杂度被隔离在应用这一侧。

    这也带出一个判断：工具能不能被用好，瓶颈不在 MCP 协议，而在 name、description、inputSchema 写得清不清楚——这和第一篇讲“工具怎么声明给模型”是同一件事，MCP 只是把这套声明从“应用里写死”变成了“从服务器带回来”。

    05、资源与提示词的发现与调用

    工具之外的两类原语，共同点是“读”而不是“调”——它们不执行动作，只提供内容。区别在谁决定什么时候用：Resources 由应用决定放进上下文，Prompts 由用户显式选择。本章的示例为简洁起见省略了每个请求必带的 _meta 字段（结构见 1.3）。

    5.1　Resources：只读的上下文

    Resource 是服务器暴露的一段只读数据，用一个 URI 唯一标识——一份代码文件、一个仓库的 README、一段数据库 schema 都可以。和工具一样，取用分两步：先 resources/list 拿清单，再 resources/read 按 URI 读具体内容。

    第一步 resources/list 的请求，可以带 cursor 做分页：

    {
  "jsonrpc": "2.0",
  "id": 3,
  "method": "resources/list",
  "params": {}
}

    响应是资源清单，每项只有元信息（URI、名字、MIME 类型等），不含内容本身：

    {
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "resultType": "complete",
    "resources": [
      {
        "uri": "file:///project/src/main.rs",
        "name": "main.rs",
        "title": "Rust Software Application Main File",
        "description": "Primary application entry point",
        "mimeType": "text/x-rust"
      }
    ],
    "nextCursor": "next-page-cursor",
    "ttlMs": 300000,
    "cacheScope": "public"
  }
}

    第二步 resources/read 的请求，用清单里拿到的 URI 去读内容：

    {
  "jsonrpc": "2.0",
  "id": 4,
  "method": "resources/read",
  "params": { "uri": "file:///project/src/main.rs" }
}

    响应是这段数据本身——contents 数组，每项可以是 text（文本）或 blob（base64 的二进制），带 uri 和 mimeType：

    {
  "jsonrpc": "2.0",
  "id": 4,
  "result": {
    "resultType": "complete",
    "contents": [
      {
        "uri": "file:///project/src/main.rs",
        "mimeType": "text/x-rust",
        "text": "fn main() {\n    println!(\"Hello world!\");\n}"
      }
    ]
  }
}

    Resource 的定义字段有 uri、name、title、description、mimeType、size，外加可选的 annotations（audience 受众、priority 优先级、lastModified 修改时间）。这正是它和 Tool 的根本区别：Resource 是只读的内容，而 Tool 是可执行的能力——既可以是只读操作（查天气、搜索都是 Tool），也可以产生副作用；Tool 的产出是一次执行的结果，Resource 的产出是一段可以作为上下文材料使用的内容。

    Resource 还有两个工具没有的能力。一个是参数化模板：服务器可以用 URI 模板（RFC 6570）暴露一类资源，比如 file:///{path}，客户端填了 path 才得到具体资源，通过 resources/templates/list 列出模板。另一个是订阅：modern era 下，客户端通过 subscriptions/listen 建立订阅，资源发生变化后，服务器在这条订阅流上发 notifications/resources/updated，客户端据此重新读取对应 Resource；通知的 _meta 里带 subscriptionId，用来和是哪条订阅发出的相对应。

    5.2　Prompts：用户挑选的模板

    Prompt 是服务器提供的、可复用的指令模板，比如一个“审阅这段代码”的模板。它由用户显式触发（常见形态是斜杠命令），服务器定义内容、用户决定何时用——控制权在用户，这是它和 Tool、Resource 都不同的地方。

    获取也是两步：prompts/list 拿模板清单，prompts/get 取具体内容，请求里带参数把模板实例化。取回的不是可执行代码，而是一组消息——通常是 user 角色的一段文字，也可能是 assistant 角色，内容可以是文本、图片、音频，甚至内嵌一个 Resource 或指向资源的链接。

    第一步 prompts/list 的请求：

    {
  "jsonrpc": "2.0",
  "id": 5,
  "method": "prompts/list",
  "params": {}
}

    响应是模板清单，每项带名字、描述和它接受的参数：

    {
  "jsonrpc": "2.0",
  "id": 5,
  "result": {
    "resultType": "complete",
    "prompts": [
      {
        "name": "code_review",
        "title": "Request Code Review",
        "description": "Asks the LLM to analyze code quality and suggest improvements",
        "arguments": [
          { "name": "code", "description": "The code to review", "required": true }
        ]
      }
    ]
  }
}

    第二步 prompts/get 的请求，按清单里的模板名取内容，arguments 用来实例化模板：

    {
  "jsonrpc": "2.0",
  "id": 6,
  "method": "prompts/get",
  "params": {
    "name": "code_review",
    "arguments": { "code": "def hello():\n    print('world')" }
  }
}

    响应是一组消息——模板被参数实例化后的结果，每条消息带 role 和 content：

    {
  "jsonrpc": "2.0",
  "id": 6,
  "result": {
    "resultType": "complete",
    "description": "Code review prompt",
    "messages": [
      {
        "role": "user",
        "content": {
          "type": "text",
          "text": "Please review this Python code:\ndef hello():\n    print('world')"
        }
      }
    ]
  }
}

    返回的消息会被客户端整理后交给模型，作为对话的起点。所以 Prompts 解决的是“重复写同一段开场白”的问题：把一套常用的引导语沉淀成模板，用户一键调用。

    5.3　三者并排看

    三类原语放在一起，差别一眼就能抓住：Tool 是“能做什么”，Resource 是“能看到什么”，Prompt 是“该怎么说”。更本质的差别在控制权——谁决定它们何时被用起来：

    原语 是什么 谁决定何时用 发现与取用
    Tools 可执行的动作，有输入输出 schema 模型 tools/list → tools/call
    Resources 只读的上下文数据，有唯一 URI 应用 resources/list → resources/read
    Prompts 可复用的指令模板，带参数 用户 prompts/list → prompts/get

    三者共用同一套骨架：都提供“列表 → 取用”的标准发现路径，各自的 list 方法都支持分页（cursor / nextCursor），清单变化的通知也都走订阅流。但两点要说清：列表不是取用前的强制步骤——客户端已经知道某个工具名、资源 URI 或模板名时，可以直接调对应的取用方法，server/discover 也不是必经入口；另外现代协议为列表结果提供 ttlMs、cacheScope 这类缓存提示，客户端据此决定自己的缓存策略，这是提示而不是原语自带的能力。掌握这一套骨架，再看任何一个新原语，剩下的只是它“是什么、归谁管”的差别。

    从这张图能读出三个层次。最上面，模型只跟“工具清单 + 调用”打交道，它不知道下面是 MCP 还是本地函数。中间，应用承担了翻译：把模型的调用意图变成 tools/call，把 tools/list 的结果整理成模型看得懂的清单。最下面，协议把“接进来”这件事标准化了——服务器实现一次，就能被任何支持 MCP 的应用连上。

    再回头看这一篇开头的三个词，现在都有了落点：连接是第 03 节的生命周期，让两端对上话；发现是 tools/list、resources/list、prompts/list 这一族“问出来”的方法，让清单在运行时才成型；调用是 tools/call 这条从模型一路穿透到外部系统的链路。三个词不是三种并列的功能，也不是严格串行的三个阶段，而是理解 MCP 协议的一条主线：连接解决消息怎么传，发现解决能力描述从哪里来，调用解决具体能力如何执行。
