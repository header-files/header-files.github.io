    LLM 是一团概率分布,API 才是产品。当模型被装进一个 HTTP 接口,它就不再只是研究者的玩具,而是任何应用都能调用的能力。所有上层应用——聊天机器人、RAG、Agent、代码助手——都站在这个抽象层之上。

    对一个要落地的大模型应用来说,真正决定开发体验的从来不是模型论文里那几个数字,而是你每天打交道的接口长什么样、字段怎么填、流怎么接、结构化怎么约束、工具怎么调、多模态怎么塞。把 LLM API 当作一门”网络协议”去理解它,会比把它当作一个玄学的”黑盒”实用得多。

    01、什么是 LLM API

    LLM API(大语言模型应用程序接口)是模型对外暴露的一组网络端点。它接受结构化请求,返回模型生成的结果,中间把”加载权重、分词、推理、采样、解码”这些细节全部藏掉。对调用方来说,它就是一行 HTTP 请求加一段 JSON 响应。

    1.1　应用程序与模型之间的调用关系

    整个调用关系可以简化成三层:

    • 应用层:发起请求的客户端,可以是 Web 前端、移动端、后台服务,甚至是另一台服务器上的脚本。
    • 协议层:HTTP/HTTPS + JSON(少数厂商支持 gRPC 或 SSE),负责传输和编码。
    • 推理层:API 网关背后的模型推理集群,负责实际跑模型。

    应用层完全不需要知道推理层用了多少张卡、模型是 7B 还是 70B、用的是 vLLM 还是 TGI。它只看到一个能产出文字的函数。

    1.2　一次模型调用的基本流程

    非流式一次调用大致走过这些步骤:

    [Client]
  │  1. 构造 JSON,加上 Authorization 头
  ▼
[API Gateway]
  │  2. 鉴权、限流、配额检查
  ▼
[Scheduler]
  │  3. 选一个空闲的 worker,准备 KV cache 上下文
  ▼
[Inference Worker]
  │  4. prefill(把 prompt 跑一遍,初始化 KV cache)
  │  5. decode(自回归生成 token)
  ▼
[Postprocess]
  │  6. 采样、停止条件判断、计算 usage
  ▼
[Client]
     7. 收到完整 JSON 响应

    流式调用则在第 5、6 步之间每生成一个(或几个)token 就往回推一段,直到触发 stop 条件或到达 max_tokens。

    1.3　API 与直接运行模型的区别

    维度 API 调用 本地运行模型
    运维 无需关心 GPU、显存、并发 需要 vLLM/SGLang/TGI 等推理框架
    成本 按 token 计费,边际稳定 固定硬件 + 电费,量大便宜
    弹性 自动扩缩容,突发流量可扛 需要自己处理排队、扩缩容
    数据合规 数据离开本机 数据不出域
    定制化 受限于厂商开放的能力 可以微调、换底座、改采样策略
    模型升级 厂商灰度推送,不可控 需要手动拉权重、热加载

    什么时候选 API、什么时候本地部署,本质上是一个”成本-合规-控制力”的三角权衡。Agent 时代大多数团队都从 API 起步,等量起来再考虑私有部署。

    02、LLM API 的基本结构

    不管 OpenAI、Anthropic、Google、DeepSeek 还是开源生态里那些 OpenAI 兼容接口,一次 LLM API 调用的”骨架”基本一致。下面以最常见的 Chat Completion 风格为例拆解。

    2.1　Endpoint

    每个厂商有自己的基础 URL 和路径:

    POST https://api.openai.com/v1/chat/completions
POST https://api.anthropic.com/v1/messages
POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent
POST https://api.deepseek.com/chat/completions

    路径命名风格不一,但都遵循 RESTful 思路:一个模型族对应一组端点,操作类型(对话、补全、embedding、图片生成)分开。

    2.2　Authentication

    主流三种:

    • Bearer Token:Authorization: Bearer sk-xxx,OpenAI 风格。
    • 自定义 Header:x-api-key: sk-ant-xxx,Anthropic 风格。
    • OAuth 2.0:企业级场景,通过 token endpoint 换短期 token。

    2.3　Headers

    请求侧常见头部:

    • Content-Type: application/json
    • Authorization: Bearer <KEY> 或 x-api-key: <KEY>
    • x-request-id:链路追踪 ID,方便排查日志
    • 厂商特定头部,例如 Anthropic 的 anthropic-version: 2023-06-01

    响应侧常见头部:

    • x-ratelimit-remaining-requests
    • x-ratelimit-remaining-tokens
    • x-request-id(回显请求 ID)
    • retry-after(被限流时)

    2.4　Request

    Chat Completion 风格的请求体:

    {
  "model": "gpt-4o",
  "messages": [
    {"role": "system", "content": "You are a concise assistant."},
    {"role": "user", "content": "Explain KV cache in one sentence."}
  ],
  "temperature": 0.7,
  "max_tokens": 200,
  "top_p": 0.9,
  "stream": false
}

    字段含义下一节统一拆,核心点:请求就是”模型标识 + 一组消息 + 一些旋钮”。

    2.5　Response

    非流式响应体:

    {
  "id": "chatcmpl-AbCdEf",
  "object": "chat.completion",
  "created": 1737100000,
  "model": "gpt-4o-2024-08-06",
  "choices": [
    {
      "index": 0,
      "message": {"role": "assistant", "content": "..."},
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 24,
    "completion_tokens": 18,
    "total_tokens": 42
  }
}

    choices 是结果数组,默认只返回一个(由 n 控制);finish_reason 告诉你是自然停止、长度截断还是触发了工具调用。

    2.6　常见参数

    参数 作用
    model 模型标识符,如 gpt-4o、claude-3-5-sonnet、deepseek-chat
    messages / input 对话历史,Chat API 用数组,Anthropic 用 messages,Google 用 contents
    temperature 采样温度,0 接近确定性贪心,1 是默认分布
    max_tokens 限制最大输出长度,超过会截断并标 finish_reason=length
    top_p nucleus sampling,从累积概率达到 p 的最小集合里采样
    top_k 只保留概率最高的 k 个 token 后采样(Anthropic、Llama API 暴露)
    stop 停止序列,模型遇到该字符串即终止生成
    frequency_penalty / presence_penalty 抑制重复,OpenAI 风格
    n 一次返回多少个候选 completion
    seed 指定随机种子,试图让结果尽量可复现(不能 100% 复现)
    stream 是否开启流式返回
    tools / functions 工具描述,详见后文 Tool Calling 一节
    response_format 结构化输出约束,详见后文 Structured Output 一节

    2.7　Response 中的 Token 与 Usage

    Token 是模型处理的最小单元,大致对应一个常见的词片段或一个汉字。usage 字段是计费依据:

    • prompt_tokens:你这次 prompt 消耗的 token,按 prompt 单价
    • completion_tokens:模型输出消耗的 token,通常按比 prompt 贵的单价
    • total_tokens:两者之和

    Agent 类应用一定要在请求侧把 usage 累加,这是成本监控的基础。没有 usage 数据,你就是闭着眼睛烧钱。

    03、从 Completion 到 Chat API

    3.1　Completion API:补全文本

    最早期的 LLM API 是”补全”(Completion),给定一段 prompt,模型往后续写:

    {
  "model": "gpt-3.5-turbo-instruct",
  "prompt": "Translate the following sentence to French:\nHello, world.\n\nFrench:",
  "max_tokens": 20,
  "temperature": 0
}

    模型返回:"Bonjour, le monde."。它本质上是一个”文本接龙”接口,适合翻译、补全代码片段、写开头,但不太适合多轮对话。

    3.2　Chat Completion API:消息数组

    Chat Completion 把输入从”一段文本”换成”一组消息”:

    {
  "model": "gpt-4o",
  "messages": [
    {"role": "system", "content": "You are a translator."},
    {"role": "user", "content": "Hello, world."},
    {"role": "assistant", "content": "Bonjour, le monde."},
    {"role": "user", "content": "Now translate: Goodbye."}
  ]
}

    模型根据整段对话历史生成下一条 assistant 消息。请求和响应的语义都从”补全”变成了”对话中的一轮”。

    3.3　三种 Message 角色

    虽然各厂商命名略有差异,但核心都是三类:

    • System:设定模型人格、行为约束、上下文背景。多数情况下作为”系统级指令”对待,优先级高于 user。
    • User:用户输入,可能含多模态内容(文本、图片、音频等)。
    • Assistant:模型历史回复。在多轮对话里要把上一轮的 assistant 消息原样塞回去,模型才知道自己说过什么。

    Anthropic 多了一个 role: assistant 里的 tool_use / tool_result 区分;Google 的 contents 把 system 提示当作第一条 user 消息的特殊前缀。这些差异在跨厂商迁移时一定要小心。

    3.4　为什么从”补全文本”发展到”对话消息”

    迁移不是营销,是工程上绕不开的几件事:

    • 多轮上下文管理。Completion 要自己拼接多轮历史,容易出错;Chat API 把多轮结构化到 messages 数组里。
    • 角色分离。System 角色让指令遵循更稳定,user 和 assistant 角色天然分离。
    • 对齐数据更多。RLHF 阶段大量数据是 Chat 格式,Chat API 能更稳定地释放模型对齐能力。
    • 配套能力可扩展。Tool Calling、Structured Output、function calling 这些都是建立在”消息”这个抽象上的。

    3.5　Chat API 对 Agent 应用的影响

    Chat API 是 Agent 的天然状态机:

    • 一条 user 消息是触发器
    • 一条 assistant 消息是模型决策(可能包含 tool_calls)
    • 一条 tool 消息是工具执行结果
    • System 消息是 Agent 的行为契约

    LangGraph、AutoGen、Agno 这些框架内部的状态机本质上都是在维护一个 messages 列表,然后反复把它塞给 Chat API。理解了这一点,后续所有 Agent 框架的源码都看得懂一半。

    04、Streaming

    4.1　非流式调用

    默认模式。客户端发完请求,等服务端生成完全部 token 才拿到完整响应:

    response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Write a short poem about spring."}],
    stream=False,
)
print(response.choices[0].message.content)

    短回答问题不大,一旦输出几百上千字,用户就要面对一段尴尬的”读秒”。

    4.2　流式调用

    把 stream=True 打开,模型每生成一个(或几个)token 就往客户端推一段:

    stream = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Write a short poem about spring."}],
    stream=True,
)
for chunk in stream:
    delta = chunk.choices[0].delta.content or ""
    print(delta, end="", flush=True)

    delta 是这一段新增的文本,客户端拼起来就是完整回答。首 token 延迟可以压到几百毫秒,用户体验上立刻从”等结果”变成”边看边出”。

    4.3　SSE 基本原理

    主流厂商流式接口都走 SSE(Server-Sent Events),本质是 HTTP 长连接 + text/event-stream 内容类型。服务端持续推送形如这样的数据:

    data: {"id":"chatcmpl-AbCdEf","object":"chat.completion.chunk","choices":[{"delta":{"content":"春"}}]}

data: {"choices":[{"delta":{"content":"风"}}]}

data: {"choices":[{"delta":{"content":"拂"}}]}

data: [DONE]

    每条 data: 行是一个独立的事件,客户端用 EventSource API 或自己按换行解析。流结束标志通常是 [DONE] 或者 finish_reason 不为 null 的最后一条 chunk。

    Anthropic 同样走 SSE,但事件类型更细分(message_start、content_block_delta、message_stop),分别对应生命周期阶段。

    4.4　Token 增量返回

    流式响应的每条 chunk 只含”增量”——这一小段时间新增的 token 或工具调用片段。客户端有两种消费模式:

    • 只拼接文本:把 delta.content 累积成最终回答,用于聊天界面。
    • 解析中间状态:tool_calls 在流式下是分段到达的,name 先到、参数 JSON 字符串后到,需要做增量 JSON 解析,直到收到完整的 arguments 才能执行工具。

    后一种是 Agent 框架的痛点之一,这也是 Structured Output 越来越重要的原因。

    4.5　流式在 Chat / Agent 中的作用

    • Chat UX:打字机效果让人感觉”在思考”,显著降低感知延迟。
    • Agent 提前决策:模型刚生成 tool_call 就触发工具,不必等整段回答结束。
    • 长输出场景:几千字的文档生成、流式字幕、IDE 代码补全都依赖流式。
    • 可中断:用户随时取消,已经花的钱不会浪费。

    4.6　流式下的异常与连接断开

    流式不是”免费的延迟优化”,它带来了一堆边角问题:

    • 超时检测:没有”生成完毕”的明确信号,客户端要用 idle timeout(比如 30 秒没新 chunk 就报警)。
    • 断连重试:多数厂商不支持断点续传,只能整段重发。对长输出成本压力大。
    • 部分响应处理:已收到的 chunk 要保留,不能因报错就全清掉。
    • 错误传递:流式错误通常以特殊 SSE event(如 Anthropic 的 event: error)或 HTTP 非 200 状态码呈现,需要单独捕获。
    • 代理与网关:Nginx、CDN 默认可能缓存或缓冲 SSE 响应,要么关闭 buffering,要么直接走支持 streaming 的网关。

    05、Structured Output

    5.1　为什么需要结构化输出

    Agent 系统的下游消费方通常是代码,不是人:

    • 工作流引擎需要 {"action": "search", "query": "..."} 这种结构
    • 前端表单需要 {"title": "...", "fields": [...]} 这种结构
    • 数据库写入需要字段类型严格匹配的 record

    如果模型返回一段自然语言,Agent 还要再调一次 LLM 抽取,既慢又贵又脆。结构化输出就是让模型”一次返回就能直接被代码消化”。

    5.2　JSON Mode

    最基础的约束:保证模型输出是合法 JSON。OpenAI 的写法:

    {
  "response_format": {"type": "json_object"}
}

    模型被引导输出 JSON,但字段名、类型、嵌套结构都不保证。适合”我知道我要 JSON,但具体长什么样我自己解析”。

    5.3　JSON Schema

    用 JSON Schema 描述字段类型、必填项、enum:

    {
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "extract",
      "schema": {
        "type": "object",
        "properties": {
          "title": {"type": "string"},
          "tags": {"type": "array", "items": {"type": "string"}},
          "score": {"type": "number", "minimum": 0, "maximum": 1}
        },
        "required": ["title", "tags"],
        "additionalProperties": false
      }
    }
  }
}

    大部分厂商在这一步会用 prompt 工程 + 输出过滤来近似满足 schema,严格度有限。

    5.4　Structured Output

    OpenAI 在 2024 年推出的”约束解码”能力:在解码阶段把不合法的 token 概率置零,保证模型输出严格符合 schema,而不是”看起来像”。

    Anthropic 没有专门的 Structured Output ,但 tool use 能做同样的事——把”我想让模型产出的结构化对象”伪装成一个 tool,模型只要返回 tool_use 块,就等于产出了结构化数据。

    Google Gemini 通过 responseSchema 字段提供类似 JSON Schema 的约束。

    5.5　与 Agent 状态、Tool Calling 的关系

    • Tool Calling 是 Structured Output 的超集:工具调用本身就是一种”结构化输出”
    • 同一个约束解码技术既可以约束 JSON,也可以约束 tool_calls
    • Agent 框架(比如 Instructor、Pydantic AI、LangChain 的 with_structured_output)大量依赖 Structured Output,把模型输出直接映射成 Pydantic / Zod 对象

    工程上有一个经验法则:任何模型输出会被代码消费的环节,都应当走 Structured Output,不要让代码再调一次 LLM 解析自然语言。

    06、Tool Calling

    6.1　Tool Calling 是什么

    让模型在对话中”决定调用外部工具”,而不是直接给自然语言回答。模型输出形如:

    {
  "choices": [
    {
      "message": {
        "role": "assistant",
        "content": null,
        "tool_calls": [
          {
            "id": "call_001",
            "type": "function",
            "function": {
              "name": "get_weather",
              "arguments": "{\"city\": \"Hangzhou\"}"
            }
          }
        ]
      },
      "finish_reason": "tool_calls"
    }
  ]
}

    应用看到 finish_reason=tool_calls 就知道这次不能把 content 直接给用户,得先去执行工具。

    6.2　Tool Schema

    每个工具用 JSON Schema 描述:

    {
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "Get current weather for a given city.",
    "parameters": {
      "type": "object",
      "properties": {
        "city": {"type": "string", "description": "City name"},
        "unit": {"type": "string", "enum": ["celsius", "fahrenheit"], "default": "celsius"}
      },
      "required": ["city"]
    }
  }
}

    description 至关重要——模型靠它判断何时调用。写得含糊的工具永远不会被调到,写得清楚的工具几乎总能被正确使用。

    6.3　模型如何决定调用工具

    模型在推理阶段面对工具列表,大致遵循这样的决策:

    • 把 tools 转成”系统约束”,插入上下文
    • 模型在生成每个 token 时,实际在”该输出文本”和”该输出 tool_call”之间做选择
    • 一旦决定调用,就进入 tool_call 生成模式,依次产出 name、参数 JSON

    背后是训练阶段加入了大量 function calling 数据,使模型对工具 schema 有”语义级”理解,而不是简单关键词匹配。这也是为什么工具描述要写得像文档,不能像变量名。

    6.4　完整调用流程

    以”杭州今天天气怎么样”为例:

    1. 应用构造 messages + tools,请求模型
2. 模型返回 finish_reason=tool_calls,function=get_weather,args={"city":"Hangzhou"}
3. 应用执行工具(查天气 API),拿到 {"temp": 28, "condition": "sunny"}
4. 应用把结果以 role:"tool" 追加到 messages,tool_call_id 对齐
5. 应用再次请求模型
6. 模型整理回复:"杭州今天 28°C,晴天。"

    整个过程中 messages 数组不断增长,模型在”是否调用工具”和”是否直接回答”之间反复决策。这就是 ReAct / Function Agent 的最朴素形态。

    6.5　与传统 Function Calling 的关系

    “Function Calling”是 OpenAI 2023 年的命名,”Tool Calling”是 2024 年更通用的说法(支持多模态工具、并行调用、工具结果直接回传等)。本质上同一类能力,不同厂商命名习惯不同:

    • OpenAI:tool_calls、tool role
    • Anthropic:tool_use content block、tool_result content block
    • Google:functionCall、functionResponse

    理解其中之一,其它厂商的文档基本都能直接读。

    07、多模态 API

    7.1　Text

    最基础的一类,字符串 message,前面所有例子都是。

    7.2　Image

    主流支持三种输入方式:

    • 公网 URL:模型厂商自己去拉,简单但有公网访问与数据合规风险。
    • File ID:先调厂商的上传接口得到 file_id,再在消息里引用,适合大文件复用。
    • Base64 内联:小图直接编码进请求体,体积大,不推荐大图。

    OpenAI 风格的 image 输入:

    {
  "role": "user",
  "content": [
    {"type": "text", "text": "What's in this image?"},
    {"type": "image_url", "image_url": {"url": "https://..."}}
  ]
}

    GPT-4o、Claude 3.5、Gemini 1.5/2.0 等都支持 image 输入。

    7.3　Audio

    两类用法:

    • 转写:Whisper 系列,把语音转成文字,接口和 Chat Completion 是分开的。
    • 多模态对话:部分模型(GPT-4o audio、Gemini)支持把音频作为对话输入的一部分,直接出文字或音频回复。

    7.4　Video

    直接传视频流仍是少数派。主流做法:

    • 服务端抽帧,把若干帧作为 image 输入
    • Google Gemini 系列原生支持 video 输入(传 base64 或 File API)

    OpenAI 当前主流路径仍是”自己抽帧 → image 输入”,而不是传视频文件。

    7.5　多模态输入的 API 表达方式

    三种主流表达:

    • 多 content block:OpenAI 风格,同一 message 内 type 区分 text/image/audio。
    • inline_data:Google 风格,inline_data: {mime_type, data}。
    • 附件引用:先 upload 拿 ID,再在消息里引用。

    跨厂商迁移时,这种 schema 差异是最容易踩坑的地方。多数 Agent 框架用统一的 HumanMessage([...]) 接口屏蔽底层差异。
