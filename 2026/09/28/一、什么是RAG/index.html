    一、什么是RAG

    大模型在企业里翻车的多数场景，原因不是它不够聪明，而是它不知道该知道的事，也不知道自己不知道。RAG 要处理的，正是这件事。

    过去两年里，“让大模型读懂我们自己的文档”这类需求，最后几乎都落到同一个工程形态上：检索增强生成（Retrieval-Augmented Generation，RAG）。它听起来像一种模型技术，实际上更接近一套信息组织方式——把事实从模型的权重里搬出来，放回一个可以随时更新、随时核对的索引中，每次提问时再把相关的那部分递给模型。理解 RAG 的关键不在于记住某个框架怎么调用，而在于看清它替换掉了什么、又留下了什么，以及它并不负责解决哪些问题。

    01、RAG 到底解决什么问题

    要理解 RAG 的必要性，得先接受一个前提：大模型的能力与它的知识储备是两件事。它在语言组织与推理上的表现，和它在事实记忆上的可靠性并不成正比，而后者恰恰是绝大多数企业场景的硬要求——业务系统里一个流畅的错误答案，比一句“我不知道”代价高得多。

    1.1　LLM 的知识边界

    大模型的知识以参数形式压缩在权重里，这套机制有三个绕不开的边界。第一是时间，训练语料有截止点，之后发生的事情模型不知道。第二是覆盖，企业内部文档、私有代码库、小众领域的资料从来没有进入过预训练语料，模型对它们一无所知。第三是编辑性，想让模型改掉一条记错的事实，成本接近重新训练，而且改动会不可控地扩散到其他能力上——用一批事实数据去微调，往往会让模型在别的任务上莫名其妙地退化。

    幻觉是这些边界的直接后果。模型生成时的目标是给出最可能的下一个 token，而不是给出有依据的回答，所以在它不知道的时候，它会给出一个流畅、格式正确、但事实上错误的答案。这类错误比明显的胡说更危险，因为它看起来完全可信，而且往往要等到有人真的照着执行才会被发现。

    1.2　RAG 的基本思想

    RAG 的思路是把“记住”换成“查到”：保留模型的语言组织与推理能力，把事实性知识挪到外部索引，回答之前先检索出相关证据，再让模型基于证据组织答案。学术上通常把这两者称为参数化记忆与非参数化记忆——知识存在向量库、倒排索引或图结构里，而不是权重里。这个想法并不新，检索与生成结合的研究在 2020 年前后就已经成型，真正把它推成工程标配的，是大模型落地之后对私有知识的那一波需求。

    这个转换带来四个直接收益：

    • 知识可以随时更新，改文档就是改知识，不需要重训
    • 回答可以溯源，能引用到具体文档、章节甚至句子
    • 检索范围可以按用户裁剪，权限隔离在检索阶段完成，比生成之后再检查答案是否泄密要可靠得多
    • 成本结构也更友好，不需要 GPU 训练，只增加检索与更长上下文的推理开销。

    但必须认清它的边界：RAG 不保证正确，它保证的是“有据可依的概率更高”。如果检索没有召回相关材料，生成阶段就只能退回模型先验，而上下文里那一堆不相关内容还会进一步干扰答案，效果可能比不用 RAG 更差。换句话说，RAG 的效果上限通常由检索质量决定，而不是由模型决定。

    1.3　RAG 与模型微调

    RAG 与微调不是二选一，它们解决的是两类不同的问题，判断标准可以压缩成一句话：事实进索引，行为进权重。微调擅长改变“怎么做”——输出风格、领域语气、固定格式与结构、任务模式（分类、抽取、规范化改写）、把冗长的提示词固化进模型。它不擅长注入频繁变化且需要精确引用的事实：知识一变就要重训，小数据集上容易过拟合，还会带来灾难性遗忘。RAG 擅长处理“知道什么”——事实、时效信息、私域文档、需要标注出处的内容、需要按权限隔离的内容。

    两者结合往往比单独使用更好：用微调让模型学会如何使用检索结果、如何标注引用、找不到依据时如何明确说不知道，用 RAG 提供每一次回答所需的具体材料。也就是说，微调调的是模型的“使用说明书”，RAG 提供的是当次任务的材料。

    对比维度 RAG 的介入方式 微调的介入方式
    主要作用对象 事实性知识与引用依据 输出行为与风格模式
    知识更新成本 改文档并重建索引 重新训练并整体回归评估
    可解释性 可回溯到来源片段 通常不可回溯
    权限控制 检索阶段按用户裁剪 需为不同权限维护不同模型
    单次推理成本 检索开销加更长的上下文 无额外开销但模型更重
    典型适用场景 私域文档问答、时效信息、需引用 固定格式输出、领域语气、任务固化

    02、一套完整的 RAG 架构

    RAG 的系统形态可以粗分成三段：离线构建索引的 Indexing、在线获取信息的 Retrieval、最终产出答案的 Generation。这三段在延迟要求、失败模式与可观测指标上都不一样，分开看才能定位问题。

    2.1　Indexing：知识进入索引

    Indexing 是离线链路，把原始语料变成可检索的索引单元，依次经过采集、解析、清洗、切分、元数据标注、向量化与写入索引。它的特点是可批处理、可重跑、对延迟不敏感，也因此容易被当成一次性的脏活。但它决定了整条链路的召回上限：如果一段答案在解析时就被丢掉，或者在切分时被拦腰截断，后面无论用多好的检索器和多强的模型都找不回来。实际项目里最常被低估的就是这一步——大家愿意反复调检索参数，却不愿意花同等精力去修解析质量。

    2.2　Retrieval：从知识库检索信息

    Retrieval 是在线链路的第一步，输入是用户的问题（多轮场景下还包括对话历史），输出是一组候选片段。它内部还包含查询理解（改写、扩展、分解）、多路召回（向量、关键词或混合）、元数据过滤与重排。这一步对体验的影响最大，因为它是唯一直接决定“材料对不对”的环节，同时也是延迟最敏感的一环——用户在界面上感知到的等待，大部分发生在这里。

    2.3　Generation：基于检索结果生成答案

    Generation 把候选片段组织成上下文，交给模型产出答案。它要做的远不止拼接再调用：要在有限的 token 预算里决定放多少材料、按什么顺序放、如何处理互相矛盾的信息，还要在指令里约束模型只依据给定材料作答、标注引用、没有依据时明确说明。产出质量同时取决于材料质量和组织质量，把一段好材料塞在上下文中间、或者与十条噪声混在一起，效果都会明显下降。

    2.4　RAG 的完整链路

    把三段串起来，就得到一条完整的链路：离线侧从文档走到索引，在线侧从问题走到答案。

    这张图里有一条值得记住的性质：链路是串联的，整体效果由最短的那块板决定。检索器再强，也弥补不了索引里根本不存在的知识；模型再强，也不能从一堆无关片段里凭空推出答案。这意味着一套 RAG 系统的建设重点，往往不是把某一环换得更强，而是让每一环的失败都能被看见。

    环节 运行时机 主要产出物 延迟敏感度 典型失败表现
    Indexing 离线批处理 分块、向量、元数据、索引 低 解析丢内容、切分截断答案
    Retrieval 在线前置 候选片段与其分数 高 召回不到、召回到无关内容
    Generation 在线末尾 最终答案与引用 中 有材料却答错、引用错位

    03、关于 RAG 的三个常见误解

    上面这套架构本身不复杂，难的是它在落地时经常被简化成一个开关：接上向量库，跑通问答，就算做完。下面三个误解是最常见的简化方式，也是后续一系列工程问题的源头。

    3.1　上下文窗口够大就不需要检索？

    每隔一段时间就会流行一种说法：模型的上下文窗口已经能装下几十万甚至上百万 token，把资料全塞进去就行了，何必再做检索。窗口变大确实改变了很多事，但它改变的是上限，不是必要性。一段十万 token 的材料里，谁能保证关键的那三千 token 一定在里面？把整个知识库塞进上下文既不经济——每次提问都要为这些 token 付推理成本——也会因为信息密度过低而让模型抓不住重点。已有研究反复观察到，长上下文中的信息位置并不等价，位于中间的内容更容易被忽略。检索做的事情本质上是“在有限预算里挑出最该看的部分”，这件事不会因为窗口变大而消失，只会因为窗口变大而更容易被忽视。

    3.2　接了知识库就不会再幻觉？

    RAG 降低的是幻觉的发生率，不是把它降到零。模型仍然可能在没有依据时顺手编一个答案，也可能把检索到的材料读错、把两份文档的说法混在一起、或者把引用标到并不支撑该结论的段落上。真正能把幻觉压下来的，是“材料足够相关”与“指令足够明确”两件事同时成立：系统指令里要有“没有依据就明确说不知道”这条约束，上下文里要放真正对题的材料，而不是一堆语义相近但答非所问的段落。

    3.3　RAG 是更便宜的微调？

    这是一个方向性的误解。便宜只是 RAG 的副产品，它和微调解决的不是同一件事（见 1.3）：微调改变模型的行为方式，RAG 补充每次回答所需的事实。用 RAG 去教模型一种输出格式，就像用搜索引擎去学写作——检索到格式说明并不等于学会照着写；反过来，指望微调让模型记住每天都在变的业务数据，也会立刻撞上更新成本。两者配合的正确姿势是：把“怎么说”交给微调，把“说什么”交给检索。

    把这三条误解放回工程语境，会发现它们指向同一个结论：RAG 的价值不取决于某个组件的强弱，而取决于一条从文档到答案的完整链路是否每一环都站得住。这条链路上有解析、切分、嵌入、索引、召回、重排、上下文组装、生成与评估等多个环节，每一环都有自己的取舍与失败模式，也有大量默认做法值得怀疑——比如“块切 512 token 就是最佳实践”“向量检索一定优于关键词检索”“召回 top-k 越大越好”。这些说法在特定条件下成立，换个数据集就会反过来，而判断它们是否成立的唯一办法，是把链路拆开、把每一环的效果单独量出来。
