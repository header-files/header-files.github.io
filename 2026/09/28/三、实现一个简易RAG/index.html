    下面进入实战环境，实现一个大模型协议客户端，支持Chat Compleions等协议。由 Cursor 进行代码落地，代码已推送至 GitHub ，仓库地址：https://github.com/header-files/rag。下面简述一下过程。

    01、需求表述

    首先，向cursor描述需求：

    实现一个简易的RAG系统，具体要求如下：
1. 代码仓库https://github.com/header-files/llm已经实现了基模调用，把这个仓库clone下来之后在这个仓库的基础上继续开发，并且需要遵循这个仓库里面的技术规范（项目结构、文档更新、日志追踪等）。但是后面不要推送到这个远程仓库，远程仓库绑定这个：git@github.com:header-files/rag.git
2. embedding模型以及rarangk模型参照代码仓库https://github.com/header-files/llm，做好配置分离，涉及的参数也要适当的做好配置（文档切分长度、rerank是top的选择等等等等）
3. 向量数据库暂时放在内存中，也要做好分层设计，后续会支持opensearch等作为向量数据库
4. 输入来源需要支持txt、md等基础的文本文档，以及word、pdf等文档，因此需要支持不同文件类型的解析
5. 暂时不需要前端页面，只暴露后端接口就可以，然后实现一个命令行客户端，用户可以通过命令行进行操作（包括上传文档、对话等功能）

是否明白我的需求？如有问题直接提出

    02、技术方案生成

    经过几轮交互之后，最终生成的技术方案如下：

    1. 目标与边界

    1.1 目标

    在已有多协议大模型客户端基线上实现完整 RAG：

    • 文档解析、切分、向量化、FAISS 检索、默认重排、上下文组装、多轮问答
    • 统一 HTTP API（src/api）与命令行客户端
    • 配置、日志、链路追踪、文档与测试遵循现有工程规范

    1.2 本期不做

    • 产品前端
    • Redis / OpenSearch 等外部向量库
    • FAISS 索引落盘与重启恢复
    • 接口鉴权、多租户
    • 旧版二进制 .doc
    • 精确 tokenizer / token budget（第一版用字符数近似）
    • HNSW / IVF、候选放大倍数（RAG_RETRIEVE_CANDIDATE_MULTIPLIER 不进入第一期配置）
    • 推送到 header-files/llm

    1.3 仓库与远程

    • 基线：克隆 header-files/llm 后扩展
    • 远程：git@github.com:header-files/rag.git
    • 主分支：main
    • 仅在用户明确要求时 commit / push

    2. 总体架构

    2.1 核心链路

                      ┌─────────────┐
                  │   Ingest    │
                  └──────┬──────┘
                         │
            Parser → Chunker → Embedding
                                  │
                                  ▼
                         ┌────────────────┐
                         │ FaissVectorStore│
                         └───────┬────────┘
                                 │
Query ──→ Embedding ──→ Retriever
                         │
                    ┌────┴────┐
                    │ Filter  │
                    │ Rerank  │
                    └────┬────┘
                         │
                         ▼
                   ContextBuilder
                         │
                History + Context + Query
                         │
                         ▼
                     LLMClient

    HTTP / CLI 经 src/api 进入；SessionStore 向 QueryService 提供 History。

    2.2 模块职责

    模块 负责 不负责
    Parser 文件 → 文本 Chunk
    Chunker 文本 → Chunk Embedding
    Embedding 文本 → Vector 检索
    VectorStore Vector 存储 / 搜索 / 软删 / rebuild Query 编排
    Retriever Query → 有序 Hits（含过滤与可选重排编排） Prompt
    Reranker Hits 重排 Session
    ContextBuilder Query + Context + History → Messages LLM
    SessionStore History 生命周期 RAG 检索
    QueryService 串起问答流程 具体检索算法
    LLMClient 模型调用 RAG 业务逻辑
    src/api HTTP 工厂、trace、统一错误、挂载路由 业务算法
    CLI 调 HTTP 直连向量库

    2.3 包布局

    src/

  llm/             # 对话客户端（基线）

    vectorstore/   # VectorStore + FaissVectorStore
    retrieve/      # Retriever

    ingest.py
    query/         # QueryService

tests/
.env.example

    3. 公共能力

    3.1 配置（common.config）

    扁平 .env；密钥不进仓库，提供 .env.example。

    前缀 职责
    MODEL_* / DEFAULT_MODEL 对话模型
    EMBEDDING_* / DEFAULT_EMBEDDING Embedding
    RERANK_* / DEFAULT_RERANK Rerank
    RAG_* 流水线参数（在配置层统一校验）
    API_* HTTP 监听与 CLI 默认地址
    LOG_* 日志

    显式入参默认透传；不支持时下游报错归一，禁止静默丢弃。

    RAG_* 配置层校验（统一完成，业务代码不散落判断）：

    约束
    RAG_CHUNK_SIZE > 0
    0 <= RAG_CHUNK_OVERLAP < RAG_CHUNK_SIZE
    RAG_EMBED_BATCH_SIZE >= 1
    RAG_RETRIEVE_TOP_K >= 1
    RAG_RERANK_TOP_N >= 1
    RAG_RERANK_TOP_N <= RAG_RETRIEVE_TOP_K
    RAG_MAX_CONTEXT_CHARS > 0
    RAG_MAX_HISTORY_TURNS >= 0
    RAG_MAX_UPLOAD_BYTES >= 1
    RAG_VECTOR_STORE 本期仅允许 faiss（或实现时固定为 faiss）

    不合法时抛 ConfigError，在加载配置时失败，而不是运行到检索才发现。

    3.2 日志（common.logger）

    控制台 / 轮转文件；trace_id；API 回写 X-Trace-Id；不记密钥。

    3.3 公共 API（src/api）

    App 工厂、trace 中间件、统一错误体、GET /health、挂载各域 router。后续服务只贡献 router。

    4. 模型侧

    4.1 对话（src/llm）

    • 协议：openai-completions（默认）、openai-responses、anthropic-messages
    • Message.role 仅 system / user / assistant；不新增 role
    • 选型：RAG_CHAT_MODEL，空则 DEFAULT_MODEL

    4.2 Embedding / Rerank

    • Embedding：EMBEDDING_*，默认 openai-embeddings，批大小 RAG_EMBED_BATCH_SIZE
    • Rerank：RERANK_*，默认 cohere-rerank
    • RAG_RERANK_ENABLED 默认 true（完整链路展示）；文档标明一次问答至少 Embedding + Rerank + LLM 三次上游调用，联调可关

    5. 文档处理

    5.1 解析

    .txt / .md / .markdown / .docx / .pdf；文本解码 utf-8-sig → utf-8 → gb18030。

    5.2 切分

    递归分隔符 + 末级字符硬切；参数见配置校验。

    5.3 入库

    校验 → Parser → Chunker → Embedding → VectorStore.add_document

    空文本不入库；超 RAG_MAX_UPLOAD_BYTES 拒绝。

    5.4 记录模型

    DocumentRecord
  document_id
  filename
  media_type
  metadata
  created_at
  chunk_count          # 可选，便于列表展示

ChunkRecord
  chunk_id
  document_id
  chunk_index
  text
  faiss_id
  deleted: bool        # 软删标记（见 6.3）

    6. FaissVectorStore

    6.1 选型

    • 仅 faiss-cpu；不落盘
    • 索引：IndexFlatIP；写入前 L2 归一化，内积近似余弦

    6.2 对外接口

    add_document(document, records)   # records 含 text + vector；内部生成 chunk_id / faiss_id
search(vector, top_k, document_ids=None) -> hits
delete_document(document_id) -> bool
get_document(document_id) -> DocumentRecord | None
list_documents() -> list[DocumentRecord]
rebuild() -> None

    6.3 内部结构

    FaissVectorStore
├── index                              # faiss.IndexFlatIP
├── documents_by_id                    # document_id → DocumentRecord
├── chunks_by_faiss_id                 # faiss_id → ChunkRecord（含 deleted）
├── faiss_ids_by_chunk_id              # chunk_id → faiss_id
└── faiss_ids_by_document_id           # document_id → set[faiss_id]
    • ChunkRecord 自带 faiss_id，关系以记录为准；faiss_ids_by_* 为索引加速
    • 软删：将对应 ChunkRecord.deleted = true（可另维护 deleted: set[faiss_id] 做轻量判断，与 ChunkRecord 保持一致即可，二选一或双写以实现简单为准）
    • 删除文档：document_id → faiss_ids → 标记 chunk 删除，并更新文档列表可见性

    6.4 检索实现（第一期定死，无 candidate multiplier）

    无 document_ids：

    FAISS index.search(query, top_k)
  → 跳过 deleted
  → 若因 deleted 不足 top_k：对未删除集合补足或接受不足
     （无过滤场景 deleted 通常少；不足时以未删除向量精确补齐至 top_k）

    无过滤主路径充分使用 IndexFlatIP.search()。因软删导致结果空洞时，对未删除向量做补齐（仍不必引入配置化 multiplier）。

    有 document_ids：

    document_ids
  → 并集 faiss_ids_by_document_id
  → 排除 deleted
  → 取出对应 vectors（从侧车缓存或 reconstruct）
  → query 与允许向量做矩阵相似度（归一化后内积）
  → Top-K

    保证：

    • 有过滤时语义正确，不受全局 Top-K 截断影响
    • 不引入 RAG_RETRIEVE_CANDIDATE_MULTIPLIER（留给未来 HNSW/IVF）

    侧车缓存：入库时除 FAISS 外保留 faiss_id → vector（或等价结构），供过滤路径矩阵计算，避免依赖 reconstruct 的实现差异。

    6.5 Rebuild

    rebuild()  # 仅用未删除 chunk 重建 IndexFlatIP，重写 faiss_id 与各映射

    第一期不自动触发；可预留阈值配置但不在本期读取。长期运行删除多时由运维/后续任务调用。

    7. Retriever

    Query
  → Embedding
  → VectorStore.search(top_k=RAG_RETRIEVE_TOP_K, document_ids=...)
  → 若 Rerank 开启：Rerank → RAG_RERANK_TOP_N（已保证 ≤ retrieve top_k）
  → 返回 SearchHit[]

    空结果交 QueryService，不在此调 LLM。

    8. ContextBuilder 与 Session

    8.1 三分开

    概念 含义
    Query 用户本轮原话
    Context 本轮检索片段（编号）
    History 既往 user/assistant（不含历史资料整包）

    逻辑形态：

    [system]
[history...]
[query]
[context]

    映射到现有 Message：system + history + 一条（或有限条）user，user 正文内用明确分区（如 ## 资料 / ## 问题），拼装只在 ContextBuilder。

    8.2 长度

    • RAG_MAX_CONTEXT_CHARS：对 Context 片段按序装入，超额停止
    • 第一版用字符数近似，不做精确 token budget（文档注明）

    8.3 SessionStore

    • 进程内存；create / get / append / clear / delete
    • RAG_MAX_HISTORY_TURNS：超出丢弃最早非 system 轮次
    • History 追加的 user 仅为问题原文，不是「资料+问题」

    并发（开工收口）：

    SessionStore 保证单进程内并发访问安全（如锁保护 dict 读写）；不保证同一 session_id 上并发 /chat 严格串行。第一期不做 per-session 请求队列。

    同一 session 并行两次 chat 时，历史追加顺序可能交错；调用方应避免对同一 session 并发写，或接受该边界。

    8.4 QueryService

    取 History → Retriever → 无命中则直接说明
→ ContextBuilder → LLM → Session 追加(query, answer)
→ 返回 answer + citations + session_id

    每轮重新检索。

    9. HTTP API

    范围 路径
    公共 GET /health
    文档 POST/GET/DELETE /documents…
    会话 POST/DELETE /sessions…
    问答 POST /chat（session_id / document_ids / stream）

    统一错误：{"error": {"type", "message"}}；X-Trace-Id 可入可出。
    流式事件：session / citations / content / done / error。

    10. CLI

    serve / upload / ls / rm / ask / chat
    交互：/upload /ls /rm /clear /exit
    经 HTTP 访问服务；默认绑定一个 session。

    11. 关键配置一览

    配置 建议默认 备注
    RAG_RERANK_ENABLED true 可关以降延迟
    RAG_VECTOR_STORE faiss 本期唯一
    RAG_CHUNK_SIZE / OVERLAP 800 / 120 配置层校验
    RAG_EMBED_BATCH_SIZE 16
    RAG_RETRIEVE_TOP_K 20
    RAG_RERANK_TOP_N 5 ≤ retrieve top_k
    RAG_MAX_CONTEXT_CHARS 12000 字符近似
    RAG_MAX_HISTORY_TURNS 10
    RAG_MAX_UPLOAD_BYTES 20MB
    API_HOST / PORT / BASE_URL 本地 8000

    第一期不包含 RAG_RETRIEVE_CANDIDATE_MULTIPLIER。

    12. 技术栈

    Python ≥ 3.11，uv；httpx；FastAPI + uvicorn；typer；faiss-cpu；python-docx；pypdf；python-dotenv；pytest / respx。

    13. 文档与测试

    • README + docs/AGENT.md + docs/common|llm|rag/
    • 写清：过滤双路径、软删与 rebuild、字符近似、Rerank 默认开与延迟、Session 并发边界
    • 测试重点：配置校验（含 rerank ≤ retrieve）、有/无 document_ids 检索正确性、软删后无过滤路径结果、Context 三分开与 History 不含资料、多轮、API/CLI、无密钥泄露

    14. 落地顺序

    1. 公共配置（含校验）+ 基础类型 + 文档骨架
    2. Parser + Chunker
    3. Embedding Adapter + FaissVectorStore（双路径 search、软删、rebuild）
    4. IngestService
    5. Retriever + Rerank + ContextBuilder + QueryService
    6. SessionStore（含并发安全）
    7. src/api + RAG 路由
    8. CLI
    9. 完整测试 + README / docs 定稿

    先跑通进程内核心链路，再接 HTTP / CLI。
