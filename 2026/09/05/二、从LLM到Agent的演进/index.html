    Agent 不是一个更聪明的模型，而是模型周围那一整圈确定性的工程。 同一个基座模型，套上不同的工具、上下文管理、执行回路与验证机制，看起来就像两个人。

    你让一个团队把最新模型接进产品。它输出惊艳，步骤清晰，连该用哪个函数都替你写好了——然后它停住了。同一个模型给另一支团队，他们给它配上工具、记忆、运行时与验证回路，它就能自己跑上十几步，最后交出一个能通过的 PR。模型没变，能力差出一整个 Agent。

    过去两年发生的全部事，正落在这种落差里：**模型在持续变强，但强出来的那部分，很多还卡在工程瓶颈里，交付不出来。工程做的，不是制造智能，而是把模型本来就有、却没法稳定交付的能力释放出来。**每一层都在补前一层交付不出去的缺口；每一层都不抬高模型的智能上限，只是将它已有的能力稳定用出来。Agent 不是一次发明，而是一连串工程叠加得到的名字。

    因此，本文要回答两个问题：

    • LLM 是如何一步步演变成今天的 Agent 的？
    • 每增加一项能力，系统层面到底发生了什么变化？

    接下来的章节按能力栈展开，而不是按时间线。需要先把一件事说清楚：这条链不是一个取代一个的世代更替，而是一层层叠加的工程件。后面的层不会让前面的层消失，只会让前面的层被更强的约束包住。今天一个生产级 Agent 的代码里，从 Prompt 到 Harness 的每一层都同时存在。

    01、先纠正一个前提：这是能力栈，不是时间线

    常见的画法是上面这样一长串箭头，从 LLM 一路指到 Coding Agent。这个画法在传播上很有效，但作为工程地图会误导人，有三个地方需要修正。

    第一，同一层里往往并存多条路线。RAG 和 Tool Calling 都在解决“模型如何拿到外部信息”，区别只是一个走检索、一个走调用。今天它们不在同一个循环里竞争，而是分工协作：检索负责把相关资料放进上下文，工具调用负责去查、去改、去提交。

    第二，有些层不是“新增的能力”，而是贯穿始终的约束条件。Context 不是排在 Prompt 之后的某一步，它是从第一行系统提示开始就存在的资源边界。Prompt 只是 Context 的一个组成部分。

    第三，越靠近链条末端的名字，越接近工程实践而不是模型能力。MCP、Skill、Runtime、Harness 都不是模型变出来的新本事，而是工程师为了让模型的本事能稳定发挥而造出来的东西。

    一行话概括：LLM 是整条链上唯一的智能来源，其余全部是围绕它的工程。 理解了这一点，后面每一层的存在理由就都能自洽。

    顺着这条线，业界对这项工作的命名也经历了三次迁移：从提示词工程（Prompt Engineering），到上下文工程（Context Engineering），再到驾驭工程（Harness Engineering）。名字越换越大，本质是在做一件事——想清楚往上下文里放什么、想清楚给模型铺一个什么样的环境，比想清楚怎么把话说明白更重要。

    02、LLM：唯一的智能来源

    LLM 提供的是理解能力和生成能力。工程上它由 Transformer 架构支撑，本质是给定一段 token 序列，预测下一个 token 的概率分布。GPT-3 进一步确立了上下文学习（In-Context Learning）这条路径：不改一个权重，只靠提示里给的示例，模型就能完成新任务。

    这段定义里藏着三个决定后面一切的工程事实。

    • 模型是无状态的。 两次调用之间，模型不保留任何东西。会话里那些“它还记得”的效果，是把每一轮重新序列化再喂一遍换来的。所以“记忆”从来不在模型里，它在模型外面。
    • 模型是纯函数。 输入 tokens，输出 tokens。不改权重的前提下，输出质量的上限完全由输入决定。这解释了为什么后面所有的层都在做同一件事：让输入变得更好。
    • 模型不执行任何东西。 它只会生成文本。所有真实世界的动作——读文件、发请求、改数据库——都必须由模型外面的确定性代码来完成。

    三个事实指向同一个结论：模型的智能必须被外部系统承载，才能变成任务结果。整条演进链，就是这个承载系统逐步长出来的过程。

    03、Prompt：把通用模型变成定向执行者

    Prompt 要解决的问题很朴素：模型只会续写文本，但我们需要它执行任务。

    这个转折点来自指令微调。InstructGPT 用人类反馈训练模型遵循指令，配合对话格式的普及，模型的行为从“接着往下写”变成了“照着要求做”。提示工程的核心手段也随之成型：角色设定、任务描述、输出格式约束、少样本示例。

    Prompt 带来的第一次工程跃迁是：第一次出现了不改权重就能改行为的控制面。 这是整个 Agent 工程能够存在的前提。如果每次调整行为都要重训模型，后面所有的迭代效率都无从谈起。

    但 Prompt 有明确的边界。它是“说给模型听”，而不是“给模型条件”。当任务需要模型掌握它训练时没见过的事实、需要多步操作、需要真实执行并验证结果时，再精巧的措辞也无济于事。Prompt 的天花板，正是后面每一层要突破的地方。

    04、Context：从提示词工程到上下文工程

    上下文工程真正要回答的问题是：在有限的上下文窗口里，放什么、放多少、按什么顺序放。

    先明确 Context 的范围。任何进入上下文窗口的 token 都属于 Context：系统提示、工具定义与 Schema、检索到的文档、对话历史、记忆召回结果、工具返回值、错误信息。Prompt 只是其中一项。

    这里有一个关键认知转变：上下文窗口不是存储空间，而是注意力预算。 有三个来自实际工程的经验支撑它：

    • 第一，中间会丢。模型对位于长上下文首尾的信息利用率明显高于中段。这解释了为什么把关键目标写在上下文末尾，比写在开头更有效——Manus 的做法是持续重写一个 todo.md 文件，把全局计划“背诵”到上下文末尾，用自然语言把模型的注意力拉回任务目标。
    • 第二，越满越笨。有工程观察提出“聪明区／迟钝区”的概念：上下文使用量超过某个比例后，返回开始递减，模型更容易跑偏、忘记早先的指令、或者过拟合到错误的中间轨迹。换句话说，堆满上下文的 Agent 不会更聪明。
    • 第三，上下文是成本。它同时消耗钱和延迟。

    所以上下文工程的工程化目标可以概括为一句话：用最少的 token，把目标达成的概率做到最高。落到具体技术上，就是预算分配、裁剪、压缩、排序、以及缓存友好的组装方式。

    这里还有一条非常实在的经济账。Agent 的输入输出比极端失衡，Manus 的实测平均约 100:1，因此 KV 缓存命中率是生产环境的头号指标——以 Claude Sonnet 为例，命中缓存的输入 token 单价与未命中相差十倍。要提升命中率就必须保持提示前缀稳定、上下文只追加不修改、序列化保证确定性的键序。一个典型的反面案例是在系统提示开头放一个精确到秒的时间戳，它会让你从那一刻起的缓存全部失效。

    05、RAG：给模型接上外部知识

    RAG 解决的是参数化知识的三个硬伤：知识截止、无法溯源、装不下私有与海量数据。它的原始形式是把检索和生成拼在一起，让模型基于检索到的文档回答问题。

    完整的工程链路通常是这样：切分文档、建立索引、检索召回、重排、注入上下文、生成答案并附上引用来源。检索策略和重排对最终效果有着决定性的作用：只用向量相似度通常不够，混合检索（关键词 BM25 加向量召回）再叠加交叉编码重排是更稳的默认配置。

    有一处理解偏差需要纠正：RAG 不是让模型学会知识，而是在推理时把相关文本放进上下文。 从这个角度看，RAG 是上下文的一种自动化供给方式，它属于 Context 这一层的具体实现，而不是一个独立于 Context 的更高能力。

    RAG 的适用边界也很清楚：它擅长“读”，不擅长“做”。**它适合事实性检索，不适合需要实时数据加上写操作的任务。**当任务需要触达外部世界并产生副作用时，就必须引入下一层。

    06、Tool Calling：让模型能操作外部世界

    Tool Calling 是这条链条上性质变化最剧烈的一步。

    在此之前，模型输出的文本是给人看的。工具调用之后，模型输出的是一段符合 Schema 的结构化 JSON，它的读者变成了程序。这个切换之所以关键，是因为它第一次让模型具备了驱动外部世界的能力。

    机制本身并不复杂：宿主（比如某个Agent）应用把工具的 name、description 和 JSON Schema 放在上下文里；模型输出一个工具调用请求；宿主代码解析并执行；把执行结果作为新的一条消息写回上下文；模型基于新信息继续。这个模式的学术源头可以追溯到 Toolformer 用自监督方式教模型何时调用工具，以及 ReAct 把推理和行动交替起来的做法。工程化普及的转折点是主流模型 API 原生支持函数调用。

    这里必须破除一层神秘感：工具调用不是魔法，它就是结构化输出加代码执行。 模型自己不会执行任何东西，执行永远由确定性代码负责。把它看成一个返回 JSON 的纯函数，后面所有的设计都会变得清晰——因为一旦接受这个前提，你就不需要依赖框架的隐藏行为，可以自己掌控整个流程。

    工程落地时有几个必做项：参数必须按 Schema 严格校验后再执行；每个工具按最小权限原则授权，能读的不要给写；涉及副作用的调用要做幂等设计；超时和重试要有明确策略；工具报错要作为一条观察结果回灌给模型，而不是抛异常中断循环。最后一条尤其重要——失败是循环的一部分，不是循环的终止条件。

    07、MCP：把外部能力接入标准化

    工具调用解决了“模型能不能调用工具”，但没有解决“工具从哪里来、怎么接”。

    在没有标准之前，N 个模型客户端要对接 M 个工具服务，适配代码量是 N×M。MCP 做的事情是把这个乘积变成加法：客户端只实现一次协议，工具服务只实现一次协议，两边就能互通。它用 JSON-RPC 2.0 作为消息格式，定义了 Host、Client、Server 三层角色，把外部能力抽象成三类原语——工具（tools）、资源（resources）、提示模板（prompts），再补上采样（sampling）、根目录（roots）、引导输入（elicitation）等交互能力。

    MCP 不是比工具调用更高级的能力，它是工具调用的接入标准。 MCP 出现之后工具调用仍然存在，变化的是工具的发现方式——从写死在应用代码里，变成从 server 动态发现。它带来的是生态效应而非能力跃迁：工具可以独立分发、独立授权、独立升级。

    协议本身的迭代速度很快，这是理解 MCP 时最容易被忽略的现实。2024 年 11 月发布初始稳定版，随后经历 2025-03-26、2025-06-18、2025-11-25 数个修订。其中 2025-06-18 版引入了结构化工具输出、把 MCP server 正式定义为 OAuth 2.0 资源服务器、要求使用资源指示符绑定 token、并移除了 JSON-RPC 批处理；2025-11-25 版引入扩展框架，把 Tasks 作为实验特性放进去。

    真正需要留意的是 2026-07-28 这一版。它做了一次结构性改动：移除 initialize 握手，协议改为无状态。 协议版本、客户端身份、能力声明不再通过一次会话级的初始化协商确定，而是随每个请求以元数据携带；服务端必须实现 server/discover 用于能力与版本发现；版本不匹配时返回明确的错误并附上支持列表，由客户端挑选共同支持的版本重试。这一版还引入了 MCP Apps 扩展，让服务端可以下发在沙箱 iframe 中渲染的交互式界面，并把渲染界面上的每个动作都纳入与工具调用相同的审计与授权路径。

    对协议设计者来说，这次改动的意义是把 MCP 变成能跑在普通 HTTP 基础设施上的协议——可路由、可缓存、可追踪，负载均衡和限流器不必解析请求体就能按方法路由。对使用者的意义则是：会话状态不再藏在传输层，需要跨调用保留的状态要由工具显式返回一个 handle，再由模型把它作为普通参数传回来。

    最后要清楚 MCP 不负责什么。它不负责编排、不负责流程、不负责业务权限模型、不负责验证。装了一堆 MCP server 不等于有了 Agent，这一点在后面的层里会越来越明显。

    08、Skill：把“怎么做”变成可复用资产

    MCP 解决的是“能用什么能力”，Skill 解决的是“这件事该怎么做”。

    一个 Skill 就是一个目录，核心是一份 SKILL.md，带 YAML frontmatter 声明 name 和 description，目录里还可以带脚本、参考文档和模板资源。

    Skill 真正精巧的地方是它的加载机制——渐进式披露（progressive disclosure），分三级：

    • 第一级，元数据。启动时只把每个 Skill 的 name 和 description 预加载进系统提示，每个约 100 token。这意味着你可以装几十上百个 Skill，而它们在被触发前几乎不占上下文。
    • 第二级，指令。当任务与某个 Skill 的 description 匹配时，Agent 才去读 SKILL.md 正文，通常在 5k token 以内。
    • 第三级，资源与代码。正文里引用的参考文件按需读取；脚本直接执行，代码本身从不进入上下文，只有输出进入。

    这个设计的价值可以量化：一个 Skill 可以捆绑大量文档、数据集和示例，在被访问前这些内容零上下文成本。用一个脚本完成操作，比让模型现场生成等价代码要便宜和可靠得多。

    从工程视角看，Skill 是程序性知识的载体。通用 Agent 加上一个领域 Skill，就变成了这个领域的专家，不需要为每个场景重新造一个 Agent。而且 Skill 是文件系统里的目录，可以进版本控制、可以走代码评审、可以在团队里共享——这让“专家经验”第一次变成了可审计的工程资产。

    同时它也是新的风险面。Skill 能够指示模型调用工具、执行代码、访问数据，一个恶意 Skill 可以引导 Agent 做出与其声明用途完全不符的行为。官方的建议是像对待安装软件一样对待 Skill：审查其中捆绑的所有文件，警惕意外的网络调用和与声明不符的操作，对能接触敏感数据的 Skill 尤其谨慎。

    从上下文工程的角度看，Skill 还有一层意义：它是在回答“如何按需分发上下文”。它和组织指令文件（如 CLAUDE.md、AGENTS.md）一样，都是把上下文从“每轮都塞”改成“需要时才加载”。

    09、Agent Loop：让模型自己决定下一步

    到这里，所有零件都齐了，但还缺一个把它们串起来的机制。

    Agent Loop 就是那个循环：组装上下文、模型输出、判断是工具调用还是最终答案、执行工具、把结果写回上下文、继续。ReAct 提供了最基础的形态，把推理步骤和行动步骤交替进行；Reflexion 补上了关键的一块，让模型基于失败反馈进行自我修正。

    为什么需要循环？因为一次前向传播无法解决那些“必须与环境交互才能获得信息”的问题。循环的本质是：用多次推理换一次成功率。 模型不需要一次就做对，它只需要能看见上一次为什么错。

    循环的工程质量取决于几个设计决策：

    • 终止条件必须是结构性的。 循环在模型不再输出工具调用时结束，这是代码层面的判断，而不是靠提示词写一句“请你结束回答”。靠提示词的终止在长任务里基本不可靠。
    • 错误是观察，不是异常。 工具失败、命令报错、测试不通过，这些都要作为新的观察写回上下文，让模型看见并调整。这引出一个反直觉但被反复验证的结论：把走错的路留在上下文里，比清理掉更有效，因为抹掉失败就等于抹掉证据，模型无从适应。
    • 控制权必须在应用代码手里。 循环由应用拥有，意味着你可以设置步数上限、预算上限、审批门、以及在任何一步插入人类确认。框架替你管理循环很方便，但当你需要中断、恢复、压缩、或者在特定条件下切换策略时，会发现框架把路堵死了。

    循环的形态并不只有一种。从单次调用，到固定链路的工作流，到路由、并行、编排者与工作者、评估者与优化者，最后才是完全自主的 Agent。一条很实用的工程建议是：能用确定性的工作流解决，就不要上自主 Agent，因为可预测性本身就是一种质量属性。

    10、Memory：跨步骤、跨任务的信息保留

    Agent Loop 解决了“一次任务内不跑偏”，Memory 解决的是“任务之间不归零”。

    该需求来自三个约束的叠加：模型无状态、上下文窗口有限、会话总会结束。任何需要跨越这三者的信息，都必须落在模型外面的存储里。

    Memory 和 RAG 的分界点值得单独强调。RAG 是只读的检索，Memory 有写路径。 RAG 从外部知识库读，Agent 不改变知识库；Memory 是 Agent 自己决定记什么、什么时候更新、什么时候失效。难点因此不在读，而在写——记什么、怎么去重、冲突时以谁为准、过期了怎么办。

    目前有三条被验证过的技术路线。

    • 被动抽取路线（以 Mem0 为代表）：会话或文档进来，抽取管线自动提炼事实，存进向量库（进阶方案加知识图谱），检索时语义召回。优点是行为可预测、不占用模型推理预算；实测在 LOCOMO 上相对传统 RAG 有明显提升，同时把 P95 检索延迟从 17.12 秒降到 1.44 秒、token 消耗从 26031 降到 1764，降幅约 93%。代价是它无法判断什么在具体语境下才重要。
    • 模型自管理路线（以 MemGPT 及其商业化产物 Letta 为代表）：把记忆当成操作系统的内存来管理，分成核心记忆（类似 RAM，常驻上下文）、召回记忆、档案记忆（类似磁盘，长期持久），由模型自己通过工具调用决定信息的换入换出，甚至包括主动遗忘。优点是灵活，能处理长周期自主任务；代价是每次记忆操作都消耗推理 token，且质量高度依赖模型判断。
    • 时序知识图谱路线（以 Zep／Graphiti 为代表）：每个事实带时间戳和来源，因此能回答“这个偏好是什么时候形成的、现在还成立吗”这类问题，在时间推理类任务上表现突出。

    落到工程上，有几条经验是通用的：把记忆当作独立于会话的存储层来设计，不要和会话历史混在一起；写入侧必须有去重与失效策略，否则记忆库会迅速腐化；记忆应该对用户可见、可编辑、可导出，因为它最终是用户的资产。

    11、Runtime：让 Agent 跑得住

    到 Memory 为止，Agent 在功能上已经完整了。它能不能跑起来不是问题，能不能连续跑几个小时才是问题。

    Runtime 回答的不是“模型能不能做”，而是“长任务怎么不丢”。它承担的职责包括：执行环境隔离（容器、沙箱、受限文件系统、网络出口控制）、进程与生命周期管理（启动、暂停、恢复）、状态持久化（会话、工具调用结果、中间产物）、重试与幂等、并发与调度、超时与预算控制、以及可观测性（链路追踪、指标、日志）。

    这里有一条容易踩坑的原则：Agent 的上下文只是草稿纸，不是事务存储。 真正需要跨进程存活的状态必须落到外部存储，并且系统要能从任意一步恢复。把状态藏在上下文里，你就永远无法安全地重启、扩缩容或迁移。

    这也是 12-Factor Agents 里权重最高的几条：统一执行状态与业务状态，不要维护两套需要同步的状态系统；提供简单的启动／暂停／恢复接口，把会话状态序列化成可持久化的对象；把 Agent 设计成无状态 reducer，即“状态加事件得到新状态”的纯函数，从而天然支持水平扩展和从任意事件重放。

    一个很实用的排查经验：绝大多数“Agent 跑到一半断了只能重来”的问题，本质上是 Runtime 问题而不是模型问题。模型只负责在每一步做判断，让这个判断链条能存活下来的，是 Runtime。

    12、Harness：Agent 真正的工作环境

    Harness 是围绕模型的那一整圈确定性程序。它包含但不限于：系统提示的组装方式、工具集与工具 Schema 的设计、上下文的压缩与裁剪策略、权限与沙箱、验证回路、子 Agent 与并行机制、钩子（hooks）、以及上一节的 Runtime。

    有一个内层与外层的划分方式很好用：内层 harness 是暴露给模型的工具与接口，外层 harness 是人类围绕模型搭建的环境。内层决定模型“怎么操作”，外层决定模型“在什么环境里操作”。

    为什么 Harness 值得单独成为一层？因为模型是概率的，Harness 是确定的。同一个模型放进两个不同的 Harness，表现可以差出很多。模型能力决定上限，Harness 决定这个上限有多少能真正兑现。有一句总结很到位：模型不是产品，模型周围的系统才是。

    工程上，Harness 里杠杆最大的几件事：

    • 验证是第一质量杠杆。 把测试、构建、静态检查接进循环，不通过就不算完成。这是把“看起来对”变成“确实对”的唯一办法。
    • 编辑机制要用约束式精确匹配替换，匹配失败要大声报错，不要用整文件重写。后者会静默损坏代码，或者让 diff 错位应用。
    • 上下文要有预算、压缩与隔离。 长任务需要多层压缩；探索性的子任务应该交给上下文隔离的子 Agent 去做，只把结论带回主上下文。
    • 权限与沙箱必须由确定性代码强制，不能靠系统提示里的“请不要执行危险操作”。路径白名单、网络出口限制、超时、危险操作前置拦截，都应该是代码。
    • 提示组装要缓存友好，静态部分在前、动态部分在后，最大化前缀缓存命中率。这是直接影响成本与延迟的工程细节。
    • 模型可以分层路由。推理密集的主循环用强模型，批量探索类的子任务用便宜的小模型。
    • 项目记忆文件是性价比最高的用户自定义入口。 一份简短、具体、有明确约束的项目指令文件（CLAUDE.md、AGENTS.md 之类），能显著改善 Agent 在本仓库里的行为。

    13、Coding Agent：能力栈的第一次大收敛

    为什么是编码 Agent 先跑通？因为它恰好满足 Harness 闭环所需要的全部条件：反馈可以自动验证（编译、测试、静态检查）、环境可以完整复制（代码库加容器就是一个自洽世界）、任务有明确的目标函数（测试通过或不过）。其他领域缺少其中任何一条，Harness 的闭环就做不起来。

    这条线的演进有很清晰的数据锚点：2023 年 10 月 SWE-bench 发布时，最强的现实基线用 Claude 2 加 BM25 检索只能解决 1.96% 的问题。2024 年 SWE-agent 通过专门为模型设计的“Agent-计算机接口”（搜索摘要、带行号的查看器、带回滚的编辑、执行反馈、受管历史）把这个数字提到 12.5%。这篇工作的核心结论比数字更重要：接口设计的贡献不亚于模型规模，语言模型 Agent 是一类有自己需求的“新用户”。到 2026 年，前沿系统在 SWE-bench Verified 上的解决率已经到 85%～90% 区间，基准本身接近饱和。

    但这个数字必须谨慎解读。2026 年的审计发现，相当一部分被判定为“已解决”的补丁之所以通过，是因为仓库自带的测试太弱，没能暴露一个实际上有细微错误的修复。也就是说，这个分数衡量的是“模型加 Harness 加验证器”的组合，而不是单纯的模型能力。

    更值得关注的是，整个领域已经收敛出一套可复用的工程原语：约束式编辑（唯一匹配替换、失败即报错）、结构性终止（无工具调用即停止）、沙箱化命令执行、检索式的上下文管理（精简的仓库地图加按需读取加工具输出截断）、接入循环的验证回路、上下文隔离的探索子 Agent、以及项目记忆文件。这些原语分布在 Claude Code、Codex、SWE-agent、OpenHands 等系统里，形态各异但内核一致。

    这套原语可以反推到其他领域，前提是那个领域能定义出“可自动验证的成功标准”。这也是判断一个垂直 Agent 能否成立的实用试金石：如果一件事做完之后没有办法自动判断做对没做对，那它就需要人来当验证器，Harness 的设计难度会陡增。

    14、一张总表：每一层在解决什么问题

    层 解决的问题 典型形态 缺失时的症状
    LLM 理解与生成 基座模型 没有智能来源
    Prompt 让模型知道要做什么 系统提示、指令、少样本示例 输出方向不可控
    Context 让模型拿到完成任务所需的信息 上下文窗口的预算、组装与排序 模型缺信息，只能猜
    RAG 外部知识供给 切分＋检索＋重排＋注入＋引用 知识过期、无法溯源、装不下私有数据
    Tool Calling 操作外部世界 JSON Schema＋宿主执行器 只能“说”，不能“做”
    MCP 外部能力接入标准化 Host／Client／Server＋JSON-RPC N×M 适配器困境，生态无法沉淀
    Skill 复用“怎么做” SKILL.md＋脚本＋参考文件 长提示词反复重写，经验无法积累
    Agent Loop 持续“判断→行动→观察” 循环＋结构性终止＋错误回灌 只能一问一答，做不完长任务
    Memory 跨步骤、跨任务信息保留 记忆存储＋写路径＋检索 每次都从零开始，重复犯同一个错
    Runtime 执行、状态、重试与恢复 沙箱＋状态持久化＋调度＋可观测 一断就要重来，无法长跑
    Harness 约束与增强 Agent 工具集＋权限＋验证回路＋上下文策略 能力有，可靠性不达标
    Coding Agent／Agent 产品 面向用户的完整形态 编码 Agent、垂直 Agent 停留在 demo，不是产品

    15、结论

    把整条链压缩成一组对应关系：

    • LLM ＝ 思考与生成能力
    • Context ＝ 当前可用的信息
    • Tool ＝ 行动能力
    • Skill ＝ 做事的方法
    • Agent Loop ＝ 持续行动机制
    • Runtime ＝ 执行基础设施
    • Harness ＝ Agent 的工作环境

    再补一条这次梳理中浮现出来的判断：Agent 不是一个突然出现的新技术，而是 LLM 能力不断向“自主完成任务”演进的结果。这个演进的方向其实非常一致——把不确定性收进模型，把确定性铺在模型外面。

    模型负责判断下一步做什么，这部分天生是概率的；其余的一切——输入什么信息、能碰什么资源、动作如何执行、结果如何验证、状态如何存活——都必须由确定性代码承担。每往链条上走一层，都是在把一块不确定性从系统里挪出去，固化成可测试、可复现、可回滚的工程件。

    由此可以得出一个实用的评价标准：判断一个 Agent 产品的成熟度，不要看它用了哪个模型，要看它的 Harness 和 Runtime。模型每隔几个月就会整体换代，而 Harness 和 Runtime 里积累的东西，是换代之后仍然留下来、并且继续决定成败的部分。
