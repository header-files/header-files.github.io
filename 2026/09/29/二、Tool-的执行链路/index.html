    模型说出“调用 get_order_status，参数是 ORD-2026-000123”这句话之后，到真正产生一次查询之间，还隔着三道它看不见的关口：放行、执行、回填。Tool 里几乎所有的工程细节，都是在回答这三道关口上的具体问题。

    上一篇讲的是模型如何提出调用，落点在声明与协议；这一篇讲这句话之后发生的事。全文按四段展开——决定、放行、执行、回填，每一段回答一个问题，答错的那一段就是故障发生的地方。后半篇再把这条线放大：一批调用同时走、走的时候会怎么坏、以及把它循环起来之后会变成什么。

    为了不把讨论悬在空中，后面统一用两个工具举例：get_order_status(order_id) 是读工具，cancel_order(order_id) 是写工具。读和写的差别会在好几处反复出现。

    注意：本文写作于 2026 年 9 月。文中把应用侧拆成“运行时”与“执行器”两段来讲，是本文为了方便讨论做的参考拆分，不是任何规范里的分层；实际实现里它们常常合成一层，也常常与业务代码混在一起，可以按需要合并、拆分或省略。凡涉及具体平台的字段名、错误分类与安全要求，以目标平台具体文档为准。

    01、模型交出的只是一份提议

    先看主链：

    User
↓
LLM
↓
Tool Call
↓
Tool Runtime
↓
Tool Executor
↓
External System
↓
Tool Result
↓
LLM
↓
Final Response

    比上一篇多出来三段：Tool Runtime、Tool Executor、External System。这三段有一个共同点——都发生在模型的盲区里，也正好构成本文的主线。

    1.1　四段：决定、放行、执行、回填

    把这条链按“谁在回答哪个问题”重新切开，就是四段：

    模型只负责第一段。它交出来的东西，准确地说是一份提议：调用哪个工具、传什么参数。提议之后还有三道关口——这次调用允不允许发生（放行）、怎么真正访问外部系统（执行）、结果以什么形态回到上下文（回填）。后三段都在应用侧，这就是本文把应用侧拆成“运行时”和“执行器”来讨论的原因：运行时对接模型，执行器对接真实系统。

    1.2　为什么按关口切，而不是按组件列职责

    按组件列职责——模型做什么、运行时做什么、执行器做什么——读起来像一份岗位表，读完记不住哪里会出事。按关口切的好处是每道关口都对应一个明确的问题，而这个问题的答案一旦答错，故障就固定发生在那个位置。第 06 节讲工程问题时用的就是这个分法。

    1.3　一次调用至少是两次模型请求

    主链末尾那个“回到 LLM”的箭头值得留意。工具结果不是被追加到服务端的某个会话里，而是由运行时拼成一条新消息、随下一次请求一起发回去（上一篇讲过的无状态约束）。所以一次带工具的问答至少包含两次模型请求：第一次得到提议，第二次带上结果得到回答；结果不足以作答就继续。

    更需要注意的是：回填进历史的东西，在之后每一轮请求里都会被重新发一遍。所以一条长结果不是付一次成本，而是付每一轮。这条约束在后面好几处都会出现——为什么结果要做归一化、为什么长结果必须处理、为什么循环的成本会越跑越高。

    明确了四段和各段的归属，下面按顺序走。第一段是模型自己的。

    02、第一段 · 决定：模型这一侧

    2.1　它做的四件事

    模型侧只做四件事：理解用户意图、在工具清单里选一个（或几个）、把参数填出来、根据回填的结果决定下一步。最后一件最容易被低估——它是整个闭环里唯一能判断“信息够不够了”的一环，应用做不到这个判断，因为只有模型知道它还缺什么。

    前三件的质量几乎完全由工具的声明决定：选得对不对取决于名字与描述的区分度，参数填得对不对取决于 schema 的表达能力。工具变多之后选择准确率会下降，因为每条定义都占上下文，而描述相近的工具彼此干扰。这件事在工具设计阶段就该解决，等到运行时报错再回头改描述，通常已经晚了。

    2.2　它决定不了的四件事，正好指向后面三段

    模型不执行任何东西，不做授权判断，不保证参数在业务上成立，也不知道外部系统的真实状态。这四条不是一份缺陷清单，而是后面几节的索引：

    • 它不做授权、不保证参数在业务上成立 → 第二段“放行”必须自己判断这两件事；
    • 它不执行 → 第三段“执行”必须由别的组件负责；
    • 它不知道外部状态 → 它只能靠第四段回填的信息来判断，所以回填什么、以什么形态回填，直接决定它下一步能不能做对。

    两条由此而来的错误设计，值得单独点出。第一条是把授权写进描述里——“只查询当前用户自己的订单”。模型通常会照做，但这不构成授权：描述是提示词，会被上下文里的其他内容影响，而模型的行为本身是概率性的。更要紧的是，“当前用户是谁”这件事模型并不知道，也不该由它判断。第二条是把重试写进描述里——“如果失败请重试”。模型会真的重发调用，而它对幂等一无所知，也看不到下游此刻正在限流。

    既然模型交出的只是一份提议，就需要有人判断这份提议允不允许发生。这是第二段。

    03、第二段与第三段 · 放行与执行

    放行和执行是两件事，但它们都落在应用侧，也都属于“模型看不见的处理”，所以放在同一节里按顺序讲。

    3.1　从“点名”到一个真实存在的工具

    接收这一步从响应里取出调用，有两个细节。一是模型可能一次给出多条，要按批次处理而不是只取第一条（留到第 05 节展开）。二是参数的形态并不统一——有的平台给的是序列化后的字符串，需要自行解析；有的平台给的已经是结构化对象。把这层差异挡在运行时内部，后面的逻辑就不必再关心它来自哪家 API。

    查找这一步把名字映射到实现。名字不存在时怎么处理，各家并不一致：有的实现把它当作工具执行失败，回传一个带错误标记的结果，让模型有机会改用别的工具；有的实现把它归为协议层错误，直接以错误响应结束。两种都说得通——前者照顾模型的自愈能力，后者更符合“调用根本没能成立”的语义——但无论选哪种，都不该让这个错误把整个循环打断。

    3.2　校验分三层，因为三层的出口不同

    校验不能只做一次。以 get_order_status(order_id = "ORD-2026-000123") 为例，它至少有三层，而且每层失败之后的正确出口都不一样。

    • 形状层问的是这句话能不能用：参数能不能解析成结构化数据，order_id 是不是字符串，必填项在不在，取值是否落在枚举里。这一层失败时模型是有能力自愈的——把“缺哪个字段、哪个取值不在允许范围内”明确回传，它下一轮通常能改对。

    • 语义层问的是这个值在系统里成不成立：ORD-2026-000123 真的存在吗。模型基本无法自愈——它编不出一个真实订单号，反复回传只会让它换着字符串继续试。

    • 授权层问的是发起这次调用的主体有没有权看这个订单。这一层失败尤其不能让模型反复试，因为每一次重试都是在撞权限边界。

    三层合并成一句“参数无效”，等于把能自愈的错误和不能自愈的错误混在了一起：该改的没改，该停的没停。正确的分法是形状层回传给模型让它改，语义层与授权层回传一句稳定的说明，并停止围绕同一个参数重试。

    3.3　执行：把参数翻译成真实调用

    这一步是模型盲区里最深的一段。要做的事包括取凭据、限流、设超时、翻页，以及把模型给的参数映射成上游真正接受的形状——模型说 order_id，订单服务可能叫 order_no。这一段的所有复杂性都不会出现在模型的上下文里，它看到的只有最后回填的那段内容。

    执行有一条不能破的原则：失败要变成结果，不要抛穿循环。抛出去的代价是三件事同时发生——模型失去纠错机会、用户看到一个技术栈报错、而这次调用之前已经完成的工作全部作废。

    3.4　放行段的最后一步：这条错误该不该让模型看见

    判断标准只有一条：模型看到这条错误之后，有没有可能做出正确的下一步。把 3.2 那三层放在一起看，这个问题在每层的答案并不相同：

    能自愈的那一类要回传，而且要说清楚到能照着改。不能自愈的那一类不该把内部细节交出去——它做不了任何有用的事，只会重试从而放大故障；而且内部错误信息本身可能泄漏实现细节。

    MCP 规范给了这组划分一个明确的版本：未知工具、参数不合法、服务端异常归为协议错误，用 JSON-RPC 错误响应表达；而 API 失败、输入数据不合法、业务逻辑错误归为工具执行错误，写在正常结果里并用错误标记标识。规范给出的理由很直接——只有把工具自身的失败放进结果，模型才能看到它并自我修正。需要注意的是，协议层的错误最终以什么形式呈现给模型，仍然由宿主实现决定。

    回到订单的例子：上游返回“订单 ORD-2026-000123 不存在”，要回传给模型，因为它可能改用别的订单号，或者转去问用户；上游返回“连接订单服务超时”，只回一句稳定文案，细节进日志和告警。

    放行、执行都完成之后，真正要交给下一轮的是第四段的产物。

    04、第四段 · 回填：结果以什么形态回到上下文

    4.1　两层结构，别混着看

    结果消息在两个层面都有结构：

    • 模型侧那一层，各家的字段名与形态并不一致（这是非完整枚举，以各家 API 参考为准）：

      部分 OpenAI 系常见形态 Anthropic 系常见形态
      关联字段 结果消息上的调用 id 结果块里的调用 id
      载荷 字符串，或文本内容块数组 字符串，或内容块数组
      错误标记 无专用字段，需在内容里自行表达 结果块上的错误布尔字段
      多结果组织 每个调用一条独立的结果消息 同一批结果放在同一条消息里的多个块
      顺序约束 靠调用 id 对应 必须紧跟对应的调用声明，位置另有要求

    • 另一层是客户端与工具服务之间的协议层：以 MCP 为例，一次工具调用的结果包含一个内容块数组、一个可选的结构化结果字段、以及一个错误标记；结构化结果的允许取值类型还随规范修订有过变化，以当期规范为准。这一层不会直接进入模型的上下文——宿主读完之后，再把它翻译成模型侧的格式。两层分开看，才不会以为工具返回的东西原样进了模型。

    4.2　回填的方式，以及它的两个代价

    回填本身很朴素：拼成一条消息、追加到历史末尾、重新发起请求。朴素之外有两个代价，而且两个都在 1.3 那条约束的下游。

    第一个是长度会累积。历史每轮都要重发，所以工具结果不是付一次成本，而是付每一轮。一个设计得不好的长结果，代价会随着循环轮次继续放大——这是“结果要归一化”最实际的理由。

    第二个是位置有约束。并行调用的多条结果通常要放在同一条消息里，位置也有明确规定；把它们拆成多条消息，轻则被拒绝，重则会明显削弱模型后续使用并行调用的倾向——因为它在历史里看到的模式就是“一条结果一条消息”。

    4.3　失败也要显式

    失败必须是一种正常结果，而不是异常路径。这里有一个具体的做法值得照做：用显式的标记字段区分“执行成功但结果为空”和“执行失败”。以订单为例，“查到了订单，但没有物流记录”和“查询本身失败”是两件该采取相反行动的事：前者应该换查询条件或者直接告诉用户没有数据，后者应该改参数或者放弃这个工具。两者用同一段文本表达时，模型只能猜。

    错误文案也要按“模型怎么用”来写。错误码 400 提供不了任何行动信息，缺少 order_id，或订单号格式应为 ORD- 开头 能直接告诉它该怎么改。文案的读者不是人，是下一轮的模型。

    4.4　结果太长时

    订单的例子再往前一步：一个订单可能有几百条物流记录。结果太长时有一组常见做法，各有代价：

    做法 具体做什么 主要代价
    截断并显式标注 只保留前若干条，并明确告知还有多少条未展示 模型可能基于不完整数据下结论
    分页 把翻页参数暴露成工具的输入，由模型自己决定下一页 多消耗一轮往返
    只回传需要的字段 在工具内部裁剪，不把上游响应的原始结构整个塞回去 需要提前知道模型需要哪些字段
    摘要 先用一次模型调用把长结果压缩 可能丢失细节、发生语义偏移，且多一次调用
    外部化 把完整结果存到文件或对象存储，只回传引用与摘要 模型需要有能力按引用再取回一次

    这张表里只有一条是硬要求：截断必须显式告知。静默截断最危险的地方在于，模型会认为自己看到了全部数据，然后基于这个错误前提给出确定性的结论——它不会说“数据可能不全”，因为它不知道。反过来，显式标注“以下为前 20 条，共 348 条，可用 offset 继续”，就把一个不完整的结果变成了可用的信息。

    到这里，一次调用的四段路走完了。但模型一次要求的不止一条时，这四段路要同时走好几条。

    05、一批调用：串行还是并行

    5.1　串行：依赖天然正确

    串行是最朴素的形态：执行一条、把结果回填、让模型决定下一步。它的轮次多、延迟高，因为每一轮都是一次完整的模型往返，而工具执行的收益要等到下一次往返才能被利用。代价换来的是天然正确——依赖关系永远不会出错，因为每一步都是基于上一步的结果规划的。

    5.2　并行：省下的是等待时间

    并行把一轮里的多条调用同时发出去，工具执行时间从相加变成取最大值，是把“等三次”压成“等一次”最直接的办法。代价落在两处。

    一处是结果必须一起回传。并行批次里的每一条都要有结果，包括失败的；把同一批的结果拆开回传，会被拒绝或者削弱后续的并行行为。另一处是适用范围的限制：并行只对彼此独立的调用安全，而且不同平台对并行的支持条件并不相同——有的允许关闭并行，有的在同时启用平台自带工具时会限制函数调用的并行。

    5.3　依赖：模型的规划里没有执行顺序

    并行最实际的麻烦是依赖。模型在给出调用时是在一次性生成文本，它并不“知道”这些调用会被怎样调度，也不会给它们排序。所以它完全可能在同一批里同时发出 get_order_status 和 cancel_order——而取消订单是需要先知道订单状态的。

    应用侧有两种处理方式。一是串行执行整个批次，按批次内的顺序逐条做；如果前置失败，把后面的标记为未执行。这里有一个容易漏的细节：“未执行”也必须作为结果回传（4.3 那条原则的应用），否则模型会以为那些调用已经跑过，基于不存在的结果继续推理。二是提前识别依赖并据此排序，但这要求应用真的理解工具之间的因果关系，工具一多就难以维护。相对务实的做法是在描述与系统提示两侧同时收口：描述里写清前置条件，提示里明确“只把彼此独立的调用放进同一批”。

    四段路能走通，不等于能走稳。接下来按段看它们各自会怎么坏。

    06、四段各自会怎么坏

    段 会怎么坏 对策
    决定 选错工具、参数编造 靠描述与 schema 治理；剩下的由放行段拦住
    放行 越权调用被放过去；内部异常抛穿循环 最小权限凭据；授权判断只在运行时做；错误分类后决定回传与否
    执行 卡住不动；重试放大故障；同一次意图产生两次副作用 分层超时；只对幂等操作自动重试；写操作要求幂等键
    回填 静默截断；把失败和空结果混为一谈 截断显式告知；用标记字段区分
    横切 出问题查不出坏在哪一段 每次调用作为一个可观测单元，串成一条链路

    异常分类已经在 3.4 讲过，它属于放行段，表里只占半格。下面展开三处最容易被忽略的。

    6.1　执行段：超时、重试、幂等是同一个问题的三个面

    超时要有层次：单次工具的超时、单轮处理的超时、整个任务的时间预算。只设一层的话，一次卡住的调用会把整个循环拖住，而模型那边还在等一个可能永远不会来的结果。

    超时之后不要抛异常，而要把它当成一种结果回传——但回传的内容要能阻止模型做出错误的补救。如果只回“连接超时”，模型很可能就再调一次；回“该操作在等待上限内未返回，可能已经生效，请勿重复提交”，它才会停下来。

    这就接到幂等。工具调用在现实里是“至少一次”的语义，原因有两个：超时之后调用可能已经在下游生效了，只是响应没回来；失败重试本身也会重发。所以写操作必须能承受同一个调用重复到达。常见做法是让调用方生成一个稳定的幂等键随参数传入，由被调方按这个键去重——模型可以重复提出同一个意图，但只应该产生一次副作用。

    读和写的差别在这里最明显。get_order_status 超时可以自动重试，因为它没有副作用；cancel_order 超时不能重试，因为你不知道那次取消生效没有，重试可能变成第二次取消，或者在下游产生一条互相矛盾的记录。重试是执行器按幂等性判断决定的动作，不能被提示词诱导，也不能由模型发起。

    6.2　放行段：权限与人工确认

    凭据要最小化，并且按调用主体隔离，而不是让一组工具共用一个高权限账号。授权判断只能在运行时做：模型提出的调用是一个提议，不是一个已获授权的动作（这也是 2.2 里那条“不要用描述代替授权”的工程落点）。

    高风险动作还需要人工确认。MCP 规范在这里给得比较明确：工具调用应当始终有人可以拒绝，应用应当明确展示哪些工具暴露给了模型、在调用时给出可视提示、并对敏感操作弹出确认。同一份规范的客户端侧建议里还包含几条与本节直接相关的——在把工具结果传给模型之前先做校验、为工具调用实现超时、以及记录工具调用用于审计；规范也建议把调用输入先展示给用户，理由是防止数据被恶意或意外地外发。这些不是可选的美化，而是这套机制里唯一能兜住“模型被外部内容操纵”的一层。回到订单的例子：get_order_status 可以静默执行，cancel_order 应该弹出确认。

    6.3　横切：日志与 Trace 要先能指认坏在哪一段

    一次工具调用应该是一个可观测单元：工具名、参数摘要、耗时、结果大小与状态、错误分类，以及它属于哪个会话、哪一轮、哪个主体。关键是把这次调用与同属一轮的模型请求挂在同一条链路上——否则你只能看到“某次调用慢了”，看不出是它在拖慢整轮，还是整轮里其他环节的问题。上一节那张表的分法在这里正好用得上：先定位是哪一段坏了，再去看那一段的日志。

    参数与结果里经常混着个人信息与凭据。日志需要的是摘要与指纹，不是原文：记录字段名与长度足够定位问题，记录完整参数值通常只是给自己制造合规负担。

    四段路走稳之后，剩下的事就是把它循环起来。

    07、循环起来：Tool 与 Agent Loop

    7.1　循环的形状

    把一次调用放进更大的循环里，四段路就变成了循环体的一圈：

    理解
↓
规划
↓
Tool Call
↓
执行
↓
观察 Tool Result
↓
继续规划

    这个形状不新鲜——ReAct 在 2022 年就把“推理与行动交替”固定成了这种结构，今天的工具调用机制只是把其中“行动”那一步从自然语言约定升级成了协议级的结构化声明。

    循环里有两个特征需要留意。一是每一圈都是一次完整的模型请求，而由于历史逐轮累加，上下文长度、延迟和成本都随轮次单调增长。二是循环体本身没有内建的退出机制：协议不限制轮次，模型也不会因为“跑太久了”而主动停下，它只会继续规划。

    7.2　停止条件由应用划

    既然循环不负责停止，停止就只能是应用侧的策略：模型不再发起调用（自然结束）、达到轮次上限、达到时间或成本预算、或者需要人工确认而挂起等待。这四个条件里只有第一个是“自然”的，其余三个都是应用主动划的线。

    7.3　四种失控模式

    实践中见到的失控大多落在这四种里：反复调用同一个工具、拿着同一批参数拿到同一个结果；对不可自愈的错误反复重试，比如下游已经限流，模型还换着参数继续撞（3.4 分类错误就会直接导致这一种）；上下文随轮次持续膨胀，直到触到窗口上限或成本失控；以及工具越调越多但目标悄悄漂移，最终交付的东西和用户最初要的东西已经不是一回事。

    对应的控制手段都不复杂：轮次与预算上限、对相同调用做结果去重或缓存、把连续失败的工具在后续轮次里降级或禁用、把“已经做过什么”显式写进上下文而不是指望模型从历史里自己推断，以及在写操作前留一个人工介入点。这些手段全部属于运行时，不属于提示词。

    08、小结

    模型交出的始终只是一份提议。它之后要过三道关口：放行决定这份提议允不允许发生，执行把它变成对真实系统的访问，回填决定结果以什么形态回到上下文。加上模型自己的决定，一共四段；四段里只有第一段发生在模型侧。

    按关口切而不是按组件列职责，好处是每道关口都对应一个明确的问题，答错的那一段就是故障发生的地方。参数校验要分三层，因为形状层回传给模型就能自愈，而语义层与授权层回传说明之后必须停止重试。一条错误该不该让模型看见，标准只有一条：它看到之后有没有可能做出正确的下一步。

    回填这一段有两个硬约束，都来自“历史每轮重发”：截断必须显式告知，否则模型会把不完整当完整；并行批次的结果必须一起回传，包括未执行的那些。而结果的长度不是一次性成本，是每一轮都要付的成本。

    最后，一次调用能走稳，靠的是执行段把超时、重试、幂等当成同一件事来设计——读工具可以重试，写工具不行，这个区别只能由执行器按幂等性判断，不能交给提示词。而循环本身不会停：轮次、预算、人工介入点，都要由应用提前划出来。
