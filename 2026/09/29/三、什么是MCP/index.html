    5. 05、小结

    前两篇讲的是同一条链上的事：模型怎么把一次调用说出来，应用怎么把这句话变成对真实系统的访问。它们都默认了一个前提——工具清单已经在手上了。可这份清单是从哪儿来的？

    MCP 全称 Model Context Protocol，是一个开放的协议，它规定 AI 应用和外部系统之间怎么通信。一个 AI 应用（比如一个编码助手或聊天机器人）想用外部的数据或功能时，不必自己为每个外部系统写一套对接代码，而是通过 MCP 去发现、去调用这些能力：连上一个服务器，问它“你有哪些工具、哪些数据、哪些提示模板”，然后按统一的方式去用。工具和数据的提供方也只需要实现一次 MCP 服务器，就能被任何支持 MCP 的应用接上。

    这里说的“工具、数据、提示模板”，正是 MCP 服务器提供的三类东西，名字里的 Context，可以理解为它不只是让 AI 应用调用外部工具，也标准化了外部数据和提示模板等上下文信息的获取与使用。换句话说，MCP 解决的是“怎么接”的问题，不是“提供什么能力”的问题。它本身不提供任何能力，也不替代任何工具；它只是一套让能力和应用之间的连接变得标准化的约定。下面要讲的，都是这句话的展开——它为什么出现、长什么样、以及它和 Tool、Function Calling 到底什么关系。

    工具只有三个、只服务一个应用时，这个问题不值得回答，直接在代码里写函数就行。等工具和应用同时变多，它就成了主要成本。这一篇往前退一步，先不碰消息格式，把更基础的问题说清楚：这些工具本身从哪里来，不同应用之间怎么共用它们——也就是 MCP 出现之前，到底哪里不舒服。

    注意：本文写作于 2026 年 9 月。MCP 是一个仍在演进的开放协议，它的版本用日期字符串标识，并且会按需把某些特性标记为 Deprecated 乃至移除。文中凡与版本相关的表述（功能清单、已废弃特性、发现方式），都以当期规范为准；涉及方法名与字段名的部分，请对照协议版本查阅官方规范。文中的产品名只作举例，不代表某种实现是唯一选择。

    01、工具变多之后，问题从“能不能调”变成“怎么管”

    1.1　什么时候不会出问题

    一个应用接三个工具，最自然的做法就是把函数写在代码里：定义 schema、随请求带上、拿到调用就去执行。这条路没有任何问题，前两篇讲的四段路也就是这么走的。

    问题出在工具和应用同时变多的时候。设想一家公司里有四个不同的终端需要访问外部能力——IDE 里的编码助手、桌面客户端、跑在服务器上的命令行 agent，以及给内部员工用的聊天机器人；而它们要访问的外部系统有 GitHub、数据库、日历、工单系统。接下来只盯住其中一个能力——查一下某个 issue 现在是什么状态——看它在四个终端里每走一步会遇到什么。

    1.2　一个工具的五道坎

    重复写。四个应用各写一遍，这是最直接的一道。要看清“重复”到底重复了什么，把一份适配拆开就明白了：

    每一份适配里都要有的东西
├── 请求拼装：URL、方法、分页参数
├── 认证：令牌从哪读、过期怎么刷新
├── 错误映射：404 / 403 / 限流分别报什么
├── 结果裁剪：返回多少条、超了怎么截断
└── 交给模型的声明：名字、描述、参数 schema

    五样东西乘四个应用，就是二十份。真正的问题还不是数量，而是这二十份不会一起更新：GitHub 把分页参数改了，四处各修一次；某个应用顺手给结果加了缓存，另外三个没有，同一个问题在四个地方的响应速度和新鲜度都不一样。再往下，“最多返回多少条”“拉不到时是报错还是返回空列表”这些细节没有共同的约定可依，最后往往是四个人的四种习惯。这就是重复实现最贵的部分——它把一份本可以统一维护的东西，变成了二十份各自漂移的副本。

    改不动。这些代码通常不是独立的一层，而是长在应用代码里。一个典型的实现会长成 searchIssues(ctx, log, user, query) 这样：前三个参数不是 GitHub 要的，是应用自己要的——配置对象、日志器、当前会话里的用户。于是改一个工具参数，链条是这样的：改工具实现 → 改四个调用点 → 改四份声明 → 四个应用各发一次版。Client 与 Tool 强耦合说的就是这个，而且它是双向的：应用依赖工具的形状，工具的实现依赖应用的上下文，两边谁都拆不开。更麻烦的是这种耦合是隐性的——从函数名和返回类型上看不出它依赖了应用的什么，只有真去动它的时候才会一样一样冒出来。

    搬不走。既然拆不开，复用就无从谈起。把“查 issue”这段代码复制到 B 应用，第一件事就会发现 AppContext、Logger、SessionUser 这三个类型在 B 里根本不存在。剩下的只有两条路：把 A 的配置、日志、会话三个模块一起拖过去，或者在 B 里重造三个适配壳。两条路都不是“复用一段函数”，而是在新应用里重建一小套环境。看起来是一段函数，实际上是一块焊死在应用上的零件——这就是 Tool 难以复用：它复用的门槛不在于代码写得好不好，而在于它从来不是为独立运行而写的。

    认不出。因为借不了，每个应用只能自己定义这个工具的样子交给模型——这就是“不同 AI 应用各自定义接口”。同一个能力，四份声明可以长成这样：

    应用 工具名 声明参数 返回形态
    IDE 助手 search_issues query 最多 10 条
    聊天机器人 listIssues filter、page（必填） 列表 + 总数
    命令行 agent get_issues q、limit 按行拼接的文本
    桌面客户端 issues.search keyword JSON 字符串

    四行描述的是同一件事。对写代码的人来说这只是命名习惯不同，但模型看到的就是这些名字和形状——它的选择准不准，取决于名字与描述的区分度；参数填得对不对，取决于 schema 的表达能力（这是上一篇讲过的）。同一个工具在四个应用里有四种描述，模型在四个地方的表现自然也不一样，而且这种差异会随着工具变多被放大：描述相近的工具彼此干扰，清单越长，选错的概率越高。

    管不了。最后一道坎出在控制面上：清单在哪儿、谁能用哪些工具，没有一个地方统一看得见——工具的发现和管理都卡在这里。工具清单通常是编译期写死的静态列表：新增一个要改代码、重新发布；想按用户或按场景只放开一部分，没有一个统一的位置去配置；某个工具临时出问题要下线，也只能发版。举两个具体的：新来的实习生应该只看到只读工具，这件事要在四个应用里各实现一遍；工单系统正在维护、需要先把相关工具摘掉，同样要在四个应用里各改一次、各发一次版。

    1.3　五道坎是一条链，根在同一个地方

    这五道坎不是五个并列的问题，它们互为因果。四份实现各自生长，任何一处改动都要四处同步（改不动）；长在应用里的代码只能引用应用自己的东西，所以这四份也互相借不了（搬不走）；借不了就只能各写各的声明，同一个能力于是有了四个名字和四种参数（认不出）；声明和控制散落在四个应用里，清单就只能写死、增减就只能发版（管不了）。起点是第一道坎——重复写决定了后面四道。

    而重复写本身也不是“懒得抽一层”，是没有地方可抽：缺一个独立于应用的、运行时的能力描述层。每个应用都得自己回答“工具长什么样、怎么调、能拿到什么”这三个问题，于是 N 个应用乘 M 个外部系统，最坏情况下就是 N × M 份适配代码。

    这张图说的是接入成本，不是能力本身。工具该有的功能一个都没少，只是每接一个新应用就要再写一遍。MCP 针对的正是这一层成本。

    02、MCP 想解决什么

    2.1　统一方式、发现、外部能力

    MCP 是一种让 AI 应用以统一方式发现和使用外部能力的协议。

    这句话里有三个点值得注意：统一方式、发现、外部能力。

    “统一方式”指的是它只定义协议——消息结构、方法名、语义——而不是某个 SDK 或某个产品的插件接口。两端实现同一份规范就能互通，谁写的应用都能连谁写的服务器。官方把它比作“AI 应用的 USB-C 端口”。USB-C 统一的是物理接口和供电协商，不保证插上去的设备好用；MCP 同样只统一接口和协商，工具本身的质量、语义、成本都不在范围内。这一点和“大家共用一套 SDK”也要分开。SDK 是代码，想复用就得所有人依赖同一份代码、同一个版本、同一套技术栈；协议是约定，用什么语言、什么框架、由谁维护都不影响互通。MCP 的生态里能同时长出许多互不相干的实现，原因就在这里。

    “发现”最容易滑过去，实际上最实质。工具清单不是编译期写死的，而是连接建立之后问出来的：客户端可以问服务器有哪些工具、资源和提示模板，也可以订阅清单变化。清单能在运行时变，“新增一个工具”就不必等于“所有客户端各发一次版”。

    “外部能力”不是只有函数。官方把服务端能力归纳成三个核心功能：可以执行的动作（Tools）、可以读取的上下文数据（Resources）、可复用的交互模板（Prompts）。第 04 节会展开；这里只需知道，MCP 覆盖的范围比“工具调用”宽，它同时管“能做什么”和“能看到什么”。

    2.2　它不解决什么

    MCP 不规定工具该怎么设计，不规定权限模型，不保证结果正确，也不管成本。它标准化的只是连接与发现这一层——这一层之上和之下的事，仍然由应用和服务器各自负责。把这个边界记在心里，才不会把“协议”读成“承诺”。

    03、MCP 长什么样

    整个结构是一条链：

    这一章把这条链上的每个部分都过一遍：先看链上的几个实体，再看协议本身拆成哪两层，然后是双方各自能提供什么，最后是版本这件事。

    3.1　三个角色

    整条链上的三个实体，规范给了三个名字：Host 是协调和管理一个或多个 Client 的 AI Application；MCP Client 是 Host 内负责与某个 Server 交互、为 Host 取回上下文的组件；MCP Server 是向 Client 提供上下文的程序。

    日常说的“客户端”和“服务端”，对应的是这条链的左右两半。Host 和 Client 都在发起请求的一侧，合起来是“客户端”——Host 是应用本身，Client 是它伸出去对接每个服务器的那只手脚；链的另一半是 Server，也就是“服务端”。中间的“MCP Protocol”是这两半之间约定的通信方式，它不属于任何一侧。

    链上有两处容易产生误解的地方：

    • 第一处是 AI Application 和 MCP Client 并不是同一个东西：应用（即 Host）负责管理和编排，它每连接一个服务器，就实例化一个 Client 对象。所以不是“应用开一条管道把消息发出去”，而是“应用对每个服务器各开一条”。官方文档的例子很直观：VS Code 连上 Sentry 的服务器时创建一个 Client，再连本地文件系统的服务器时，就再创建一个 Client。
    • 另一处是 Server 指的是“提供上下文的程序”，与它跑在哪无关。用 stdio 的服务器跑在本地，典型情况是一对一服务一个客户端；用 Streamable HTTP 的服务器跑在远端，典型情况是同时服务很多客户端。“本地服务器”和“远程服务器”不是两种服务器，是同一种服务器在两种传输下的部署形态。

    3.2　数据层与传输层

    MCP Protocol 也不是一个盒子，而是两层——数据层和传输层。

    数据层基于 JSON-RPC 2.0，管消息结构与语义：能力与版本发现、服务端与客户端功能、通知与进度，都在这一层。传输层管连接的建立、消息分帧和鉴权。目前规范给了两种传输方式：stdio 走标准输入输出，适合同一台机器上的本地进程之间，没有网络开销；Streamable HTTP 用 HTTP POST 承载客户端到服务器的消息，可选 Server-Sent Events 做流式，面向远程服务器，支持 bearer token、API key 和自定义请求头，规范建议用 OAuth 获取令牌。

    3.3　服务端功能

    MCP Server 不只是把一组函数暴露出来。一个 MCP Server 可以向客户端提供三类核心功能：Tools、Resources 和 Prompts。

    它们分别解决三种不同的问题：

    • Tool：提供可以执行的能力，让模型能够“做事”
    • Resource：提供可以读取的外部资源，让应用能够“拿资料”
    • Prompt：提供可复用的消息模板，让用户能够“选择一种做事方式”

    三者的区别，不只是提供的内容不同，还在于谁决定什么时候使用它们：Tool 通常由模型决定是否调用，Resource 通常由应用决定读取哪些，Prompt 通常由用户主动选择。

    3.3.1 Tools：让模型执行动作

    Tool 是 MCP 中最接近传统函数的原语。Server 可以把某项外部能力封装成 Tool，并提供名称、描述和参数 Schema，客户端发现之后，可以将这些 Tool 提供给模型。例如：

    @mcp.tool()
async def get_issue(issue_id: int) -> str:
    """获取 GitHub Issue 信息"""
    ...

    模型看到这个 Tool 后，可以根据用户的问题决定：

    get_issue(issue_id=123)

    然后由客户端通过 MCP 请求 Server 执行，Server 再去调用真正的 GitHub API。

    所以 Tool 解决的是：

    “模型需要执行某个动作时，应该调用什么能力？”

    例如查询订单、搜索文档、创建 Issue、执行 SQL，都属于这一类。

    3.3.2 Resources：让应用获取外部资料

    并不是所有外部信息都应该设计成 Tool。比如一个 GitHub Server 里有：

    github://repo/header-files/rag/README.md
github://repo/header-files/rag/src/retriever.py
github://repo/header-files/rag/ci/123/log

    这些东西本身不是“动作”，而是可以被读取的外部资源。MCP 用 Resource 来描述这类内容。Server 可以暴露一个固定 Resource：

    @mcp.resource("config://tags", mime_type="application/json")
async def get_tags() -> str:
    return '["科技", "金融", "医疗"]'

    也可以通过 Resource Template 暴露一类带参数的资源：

    @mcp.resource("github://repo/{owner}/{repo}/README.md")
async def get_readme(owner: str, repo: str) -> str:
    ...

    客户端发现 Resource 后，可以根据当前任务决定读取哪些资源：

    resources/list
        ↓
发现 README、代码文件、CI 日志
        ↓
resources/read
        ↓
获取具体内容

    需要注意，Resource 不会自动进入模型上下文。客户端读取 Resource 后，Host/Application 再决定如何使用这些内容，例如把相关内容放进模型的上下文中。所以 Resource 解决的是：

    “当前任务需要参考哪些外部资料？”

    它和 Tool 的区别可以简单理解为：

    Tool
    → 我要做一件事

Resource
    → 我要获取一份东西

    3.3.3 Prompts：提供可复用的消息模板

    还有一种东西既不是“动作”，也不是“资料”，而是：

    一套已经定义好的做事方式。

    例如 GitHub Server 可以提供一个 review_pull_request Prompt：

    @mcp.prompt()
async def review_pull_request(pr_number: int):
    return f"""
请审查 Pull Request #{pr_number}：

1. 检查代码逻辑
2. 检查潜在 Bug
3. 检查异常处理
4. 检查安全问题
5. 检查测试覆盖
"""

    客户端可以通过 prompts/list 发现这个 Prompt，用户选择后，再通过 prompts/get 获取对应的消息模板。因此 Prompt 解决的是：

    “用户希望按照什么方式开始一次任务？”

    它和 Tool、Resource 的区别可以理解为：

    Tool
    → 做什么

Resource
    → 看什么

Prompt
    → 怎么开始做

    Prompt 也不等于“直接把提示词发给 LLM”。它只是由 Server 提供的一套可复用消息模板，客户端获取后，由 Host/Application 将它加入当前会话，再交给模型处理。

    3.3.4 一个完整的例子

    假设我们实现了一个 GitHub MCP Server，同时提供：

    Tools
├── get_pull_request
├── create_issue
└── run_tests

Resources
├── github://repo/.../README.md
├── github://repo/.../src/main.py
└── github://repo/.../ci/123/log

Prompts
├── review_pull_request
└── explain_code

    用户现在说：

    帮我审查一下 PR #123。

    整个过程可能是这样的：

                        GitHub MCP Server
                           │
          ┌────────────────┼────────────────┐
          │                │                │
        Tools           Resources        Prompts
          │                │                │
    get_pull_request    PR代码/日志      review_pull_request
    create_issue
    run_tests
          │                │                │
          └────────────────┼────────────────┘
                           │
                      MCP Client
                           │
                     AI Application
                           │
                           ↓
                          LLM
    1. 首先，客户端发现 Server 提供的三类能力。
    2. 用户选择 review_pull_request，客户端获取对应的 Prompt 模板。
    3. 接着，应用根据任务读取相关 Resource，例如：
      PR #123 的代码
  CI 日志
  项目 README

    这些内容进入模型上下文。
    1. 模型阅读 Prompt 和这些上下文后，发现还需要获取 PR 的详细信息，于是决定调用：
      get_pull_request(123)
    1. 应用收到模型的 Tool Call 后，通过 MCP Client 请求 Server：
      tools/call
      ↓
  GitHub MCP Server
      ↓
  GitHub API
      ↓
  返回 PR 信息
    1. 结果再次进入模型上下文，模型最终生成代码审查结果。

    整个过程中，三类原语各司其职：

    Prompt: 告诉模型这次任务应该怎么做
    Resource: 给模型提供完成任务需要参考的资料
    Tool:让模型在任务过程中执行实际动作

    因此，MCP Server 可以看成是在统一暴露三类东西：

    Tool 提供能力，Resource 提供信息，Prompt 提供模板。

    这也是为什么 MCP 不只是一个“Tool 调用协议”：它把行动、外部资源和可复用消息模板统一纳入了同一套协议。

    3.3.5 发现机制

    三类的发现机制一致，都是“列表 + 取用”，但具体到每一类有差别：Tools 通过 tools/list、tools/call 发现和执行；Resources 通过资源列表或 URI 模板发现，再用 resources/read 读取；Prompts 通过 prompts/list、prompts/get 获取。方法名与用途列成一张表：

    功能 是什么 谁决定何时使用 典型方法
    Tools 可执行的动作，每个工具有输入输出的 schema 模型 tools/list、tools/call
    Resources 只读的上下文数据源，每个资源有唯一 URI 应用 resources/list、resources/read
    Prompts 可复用的指令模板，带参数与说明 用户 prompts/list、prompts/get

    触发权不在同一个地方：模型自己决定调哪个工具，应用决定把哪些资源放进上下文，用户显式选择用哪个模板。把三类混成一件事——比如让模型自己去挑资源，或者指望应用自动触发提示模板——就会走到协议没打算支持的用法上。

    Tools 还有一层约束，与第二篇直接相关。规范指出工具执行前可能需要用户同意，并给了应用侧几种常见做法：把可用工具展示在界面上、让用户决定某次交互里哪些可以被使用；对单次执行弹出确认；对确定安全的操作允许预先授权；记录每一次工具执行。放在第二篇的分工里，这些都落在“放行”那一段——协议提出要求，具体怎么落地，仍然是应用的判断。

    3.4　客户端侧功能

    客户端一侧也有一类与服务端相反的能力：服务器在处理请求的过程中，如果发现还缺少用户提供的信息，可以请求客户端向用户收集输入。目前这一侧主要是 Elicitation（信息收集），用于“参数不够了，先问用户”。

    Elicitation 有两种模式：

    • Form 模式：服务器提供输入 Schema，客户端根据 Schema 渲染表单，用户填写后由客户端将结果返回给服务器，适合普通信息的收集。
    • URL 模式：服务器提供一个 URL，用户在浏览器等带外环境中完成交互，适合凭据、令牌等敏感信息。敏感数据不会作为表单数据回传给 MCP Client。

    例如，客户端请求服务器创建一个 GitHub Issue：

    客户端 → MCP Server
        tools/call: create_issue

    服务器发现缺少仓库信息，于是在响应中表示：

    input_required
需要用户提供 repo

    客户端收到后向用户展示：

    请选择仓库：

○ header-files/rag
○ header-files/agent
○ header-files/mcp

    用户选择后，客户端带着这个输入重新发起原来的请求：

    客户端 → MCP Server
        tools/call: create_issue
        repo = "header-files/rag"

    服务器获得所需信息后继续执行。

    因此，Elicitation 可以理解为：

    Server 发现信息不足 → 请求 Client 向用户收集 → Client 获得输入 → 重新发起原请求 → Server 继续执行。

    需要注意，现代 MCP 中的 Elicitation 不是服务器主动建立一条 Server → Client 的请求通道。在 2026-07-28 之后的协议中，服务器处理客户端请求时，如果需要用户输入，会在当前响应中返回 input_required；客户端完成信息收集后，再重新发起原请求。这样整个交互仍然通过多轮的客户端请求 → 服务器响应完成。

    这一部分有明显的版本时效性。Roots、Sampling、Logging 已在 2026-07-28 协议版本中进入 Deprecated 周期，目前仍可用，但新实现不应再依赖它们。官方给出的迁移方向分别是：

    • Sampling：由应用直接调用模型提供商的 API。
    • Roots：通过工具参数、Resource URI 或服务器配置传递目录信息。
    • Logging：转向标准错误输出 stderr 或 OpenTelemetry 等日志机制。

    3.5　版本协商

    读 MCP 文档时最常见的困惑是“教程和规范对不上”，问题往往出现在版本上。协议版本用日期字符串标识（形如 2026-07-28），只有出现不向后兼容的改动才会递增。

    版本协商的机制本身也在换代。从 2026-07-28 起，MCP 进入新的 modern era：不再通过 initialize 做握手，而是可以先调用 server/discover，一次获取服务器支持的协议版本、能力等信息，之后版本信息随每次请求携带。对于 2025-11-25 及更早版本，则仍采用 initialize 握手，在建立连接时完成版本协商。这个换代带来一个附带影响：modern era 不再靠一条握手建立的会话承载状态，而是让每个请求自己带上上下文，Client 和 Server 之间也就不再有一个需要长期维护的 session。

    如果手上的示例代码里有一步显式的初始化握手，而新文档里找不到，多半是因为它来自旧版本：initialize 握手是 2025-11-25 及更早的写法，当前 SDK 或实现通常仍兼容它，但新代码已经改用 server/discover。

    04、MCP 与其他概念的关系

    前面几节都在讲 MCP 本身。这一章讲清它和两个最容易混在一起的概念是什么关系：一个是 Tool，一个是 Function Calling。最后再补一句，它也不是解决“工具变多”这件事的唯一答案。

    4.1　与 Tool：不是替代，是接入方式

    回到第 01 节那个问题：MCP 和 Tool 是什么关系。

    Tool
↓
一个具体的能力

MCP
↓
能力的标准化连接方式

    Tool 是一个具体的能力——查订单、发邮件、读文件。MCP 是让这些能力可以被统一发现和调用的一套约定。MCP 服务器里面装的仍然是 Tool：它照样要为每个工具写名字、描述和参数 schema，照样要处理参数校验和错误。协议没有让工具消失，也没有让写工具变省事；它让工具多了“用一个统一接口被问出来、被调用、被描述”的能力。所以替代关系不成立：MCP 不是 Tool 的替代品，而是让 Tool 这类能力可以被不同 AI 应用以统一方式发现和调用。两者根本不在同一个位置上——一个是能力本身，一个是能力的接入方式。

    落到具体场景里就清楚了。假设有人为 GitHub 写了一个 MCP 服务器，把“查 issue”“建 PR”“读仓库文件”都暴露成工具。IDE 里的编码助手可以连上它，聊天机器人也可以连上它；两个应用各自按自己的策略决定把哪些工具暴露给模型、哪些需要用户确认、哪些干脆不放开。这两个应用里，没有一个需要为 GitHub 写适配代码——写一次的活由那个服务器承担了。

    还要分清一点：MCP 省下的是接入成本，不是调用成本。工具调用该有的往返、超时、重试、错误分类、结果裁剪，这些一样都不少——只是这些工作在实现 MCP 客户端时写一次，而不是在每个应用里各写一次。这条界线决定你对 MCP 的期待会不会落空：它不会让一次调用更快、更省 token，只会让“接进来”这件事更省事。

    4.2　与 Function Calling：两段链上的两个机制

    MCP 和 Function Calling 看起来都在讲“让模型调用东西”，是不是一回事。它们在同一段链上：

    LLM
↓
Function / Tool Calling
↓
MCP Client
↓
MCP Server
↓
Tool

    差别在链上的位置：Function Calling 是模型与应用之间的调用机制；MCP 是应用与外部能力之间的标准协议。中间隔着应用本身。

    从模型这一侧看，MCP 几乎是隐身的。模型看到的始终是一份工具清单，它输出一个结构化的调用请求，然后等结果。它不知道、也不需要知道这个工具背后是一个本地函数，还是一个通过 MCP 发现的远程能力。对模型来说两者没有区别——这正是 MCP 能在模型侧隐身的原因，也是它不需要模型厂商配合就能用的原因。

    换到应用这一侧，两个机制的分工就显出来了。应用收到调用请求之后，要先判断这个工具是本地的还是外面来的；如果是通过 MCP 发现的，还要把参数翻译成协议要求的调用消息、发给对应的服务器、等结果、再把结果翻译回模型侧需要的形状。第二篇讲的三段关口——放行、执行、回填——两条路都要走，只是“执行”那一段的内容不同：本地函数是直接调用，MCP 工具是发一条协议消息。

    还有一个自然的问题：既然模型看不见 MCP，应用为什么不干脆自己把工具都实现一遍？因为它又回到了第 01 节那五道坎上——工具清单管不了、写好的适配搬不走，每接一个应用还要重复写一遍。所以 MCP 要解决的从来不是“模型能不能调用”，而是“这份清单从哪来、谁能共用”。

    关于两者的关系，有三句常见的错误说法，逐一澄清：

    “MCP 是 Function Calling 的升级版。”不是升级，是在另一段链上。Function Calling 作用在模型与应用之间，MCP 作用在应用与外部能力之间；MCP 不替代 Function Calling，因为模型根本看不见 MCP。

    “有了 MCP 就不用写工具 schema 了。”还是要写。schema 只是从“应用里写死的常量”变成了“服务器通过协议提供的描述”，应用取回来之后仍然要把它翻译成模型侧需要的形状。省下的是重复写的那部分，不是写本身。

    “模型直连 MCP Server。”不是。中间一定有应用，由它负责鉴权、权限判断、用户确认和结果裁剪。这些恰恰是协议没有替你做、也不该替你做的那部分。

    4.3　它不是唯一解法

    工具少、只服务一个应用时，直接在代码里写函数更简单，引入协议只会多一层。同一个“避免 N × M”的问题，也可以用共享 SDK、代码生成、内部网关等方式解决。MCP 的差别主要在两处：它是开放协议，两端不必来自同一个厂商；以及它把发现放到了运行时，清单可以不发版就变。

    方式 它解决了什么 代价或边界
    每个应用各写适配 没有额外抽象，上手最快 适配成本随应用数增长，且没法复用
    共享 SDK / 代码生成 同一批实现之间能复用同一份代码 要求所有调用方依赖同一份代码与版本
    内部网关 能集中做鉴权、限流与审计 通常只在组织内部成立，外部能力接不进来
    MCP 不同实现之间的互操作，加运行时发现

    05、小结

    工具变多之后，问题的重心会从“能不能调用”移到“怎么管”。MCP 针对的是后一半：一条开放协议统一了外部能力的发现与调用方式，N 个应用乘 M 个系统的适配由此变成 N 加 M。

    它和 Function Calling 不是竞争关系。一个管模型怎么把调用说出来，一个管应用怎么把调用发出去、怎么知道有哪些能力可用，中间是应用自己的运行时。这个系列的三篇，恰好把这条链的三个高度都讲了一遍：声明、执行、连接。

    三个服务端功能的差别不在“能不能读、能不能写”，而在谁决定什么时候用——模型、应用、用户，各管各的一类。
