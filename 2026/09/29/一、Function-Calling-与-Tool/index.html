    一个只输出 token 的模型，不可能真的“调用”任何东西。Function Calling 的全部设计，就是把这句话翻译成一个可用的接口约定：模型负责提出调用意图，应用负责让意图落地。

    模型的输出始终是一段文本或一段结构化数据——无论形状多规整，本质仍是字节。它没有网络、没有文件系统、没有数据库连接，也从不执行任何代码。让 LLM 接入外部世界的，不是模型内部长出了手脚，而是在模型与外部系统之间插入了一层由应用实现的执行层，并且为“模型想调用什么”这件事约定了一套机器可解析的表达格式。理解这套格式，比记住任何一家 API 的字段名都重要，因为字段名会变，格式要解决的问题不会。

    注意：本文写作于 2026 年 9 月，讨论的是这套机制中相对稳定的部分——请求骨架、响应骨架、消息序列、schema 的作用与边界。凡是与平台能力增长绑定、可能逐月变化的部分（严格模式的适用范围、内置工具的种类、工具的加载与发现方式），文中都会标注以目标平台文档为准。示例中的模型标识一律用占位符。

    01、为什么 LLM 需要外部能力

    1.1　模型的四类缺口

    模型的能力边界可以拆成四类，每一类都对应一种外部能力需求。

    • 第一类是知识的时间边界。模型对世界的认识来自训练语料，语料有截止时间；截止之后发生的事，它只能靠泛化去猜。参数里的知识是静态快照，不会随世界更新。
    • 第二类是数据的所有权边界。你的订单表、内部文档、客户工单、私有代码库从未进入公开语料，模型不可能“知道”它们，这类信息只能在运行时查询取回。
    • 第三类是动作的边界。模型生成的是 token 序列，它不能写数据库、不能发消息、不能改配置，任何对外部世界产生副作用的操作都必须由外部程序执行。
    • 第四类是精度的边界。语言模型是对下一个 token 的概率建模，算术、日期推算、精确字符串处理这类需要严格符号运算的任务，靠生成来完成并不可靠——把这类工作交给一段确定性代码，比让模型“算准”更划算。

    还有一条不属于模型能力、但同样决定架构的事实：传统的无状态对话 API 通常要求客户端在后续请求中携带必要的历史消息；即使平台提供服务端会话或状态能力，也不意味着模型本身因此获得了持久记忆。这个区别决定了“记住上一轮发生过什么”始终是应用的责任——附加机制（提示词缓存、服务端工具）解决的是别的问题。

    1.2　从“生成文本”到“调用能力”

    在 Function Calling 出现之前，让模型触发外部动作的做法是“约定文本格式再解析”：在提示词里要求模型输出 {"action": "search", "query": "..."}，然后用正则或 JSON 解析器去抓。这种做法能跑通，但脆弱——模型可能加解释性前缀、可能把字段名写错、可能把 JSON 包在代码块里、也可能编造一个不存在的 action。系统能不能稳定工作，取决于模型今天有多听话。

    Function Calling 做的是把这套“约定文本格式”从提示词层面提升到协议层面：调用声明有了固定的承载字段，参数有了 schema 描述和校验依据，结果有了送回模型的固定通道。模型不再需要自行设计一套约定格式，而是按照 API 提供的工具定义生成调用参数；是否能够进一步保证参数严格符合 schema，则取决于具体平台及其 schema 能力（见 2.3）。应用也不再需要写大量容错解析，而是拿到一个结构化对象。

    准确地说，这不是模型变强了，而是接口变清楚了。模型的职责被严格限定为“从工具清单里挑一个、把参数填对”，执行权始终留在调用方手里。这条边界划得越清楚，后面所有的权限、审计、幂等设计才有落点。

    02、什么是 Function Calling

    2.1　Function：一段被注册的可执行单元

    这里的 Function 指应用侧提供的一个可执行函数；在现代工具 API 中，它通常以 Function Tool 的形式暴露给模型——有自己的名字、参数、实现，以及可能产生副作用的执行过程。典型形态就是应用代码里的一个函数：查天气、查订单、发邮件、跑一条 SQL。

    Function Calling 不是让模型拥有这些函数，而是让模型获得指认它们并填充参数的表达能力。所以“模型调用了函数”这句话在工程上是省略主语的说法，完整表述是：模型输出了一段指认某个函数的声明，应用读了这段声明并执行了对应函数。

    2.2　Function Schema：把签名写成模型可读的声明

    模型怎么知道有哪些函数可选？靠应用在请求里附上的声明。这份声明在概念上至少包含名字、自然语言描述、参数 schema 三部分，但不同 API 对它们的承载方式并不相同：Anthropic 直接使用 name、description、input_schema，OpenAI 则把 function definition 包装在 type: "function" 与 function 对象里。Anthropic 风格的声明长这样：

    // Anthropic 风格示例
{
  "name": "get_order_status",
  "description": "按订单号查询当前状态与预计送达时间。不用于退款或修改收货地址，这两类操作有各自专用的工具。",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": { "type": "string", "description": "订单号，形如 ORD-2026-000123" }
    },
    "required": ["order_id"]
  }
}

    同样的语义，在不同 API 里的承载字段并不一致：

    部分 OpenAI 系常见形态 Anthropic 系常见形态
    声明容器 tools tools
    单个工具的外层结构 带 type 包装的对象 扁平对象，无外层包装
    工具名 function.name name
    自然语言描述 function.description description
    参数 schema 字段 function.parameters input_schema
    模型输出的调用声明 助手消息上的调用数组 助手消息 content 里的调用块
    参数形态 序列化后的字符串，需自行解析 已解析的对象
    结果消息 独立的工具角色消息 用户消息里的结果块

    表中列的是最常见、最重要的对应关系，不构成完整枚举；具体字段名务必以各家 API 参考为准。跨厂商迁移时最容易出错的恰恰是这几行——尤其是“参数到底是字符串还是对象”这一条，它决定你写不写那一次解析，而这类差异靠记忆去猜十有八九会错。

    2.3　一次调用的四个动作

    一次完整的 Function Calling 由四个动作串起来：模型生成调用声明、应用解析并校验参数、应用执行函数、应用把结果作为新消息回传。其中只有第一个动作发生在模型侧，后三个都在应用侧。

    校验这一步值得单独强调。默认情况下模型是“尽力而为”地填参数，可能出现字段缺失、类型不符、或者枚举外的取值。部分平台提供严格模式，可以进一步约束模型生成的参数符合指定 schema；但严格模式属于具体平台提供的能力，并不是 Function Calling 协议本身的组成部分——不同平台对支持的 JSON Schema 子集、必填字段以及可选字段的表达方式都有自己的限制，以目标平台文档为准。

    即便开了严格模式，应用侧仍应保留校验：schema 管得住形状，管不住语义——模型完全可能填一个格式正确、但在业务里并不存在的订单号。

    把这条链按“谁负责”再展开一层，就得到下面这张图。蓝色是模型侧的动作，橙色是应用侧的动作；两侧贴着一条虚线，跨越这条线的每一次都是“文本进、文本出”，没有任何执行权随之转移。

    3.1　关键分工：谁决定，谁执行

    整个机制可以压缩成一句话：

    模型负责决定调用什么、传什么参数；应用负责真正执行。

    模型侧做三件事：读工具定义、判断当前问题是否需要外部能力、生成调用声明。应用侧做五件事：解析参数、鉴权与校验、执行、处理错误、把结果回传。应用侧的执行过程对于模型来说是盲区——它看不到函数内部发生了什么，只能看到你回传给它的那段文本。这意味着结果的表述方式会直接影响模型下一步的决策：回一段结构化数据、回一句话总结、回一个错误码，模型接下来的行为会不一样。

    3.2　一次Function Calling是多次模型请求

    Function Calling 把一次问答拆成了至少两次模型请求：第一次请求得到调用声明，第二次请求带上工具结果得到最终回答；如果模型判断还需要继续调用，循环继续。第二轮的请求里，工具结果不是“追加到服务端”，而是由你拼进请求的一条新消息。

    这里有一个容易踩的约束：传统的无状态对话 API 不会替你保存历史，所以第二轮请求必须把第一轮的全部消息原样带上——用户输入、模型的调用声明、工具结果，一个都不能少。另一个约束是顺序：工具结果必须紧跟在产生它的那条调用声明之后。有的 API 要求同一批并行调用的多条结果放在同一条消息里，位置也有明确规定；有的 API 用独立的工具角色消息、靠调用 id 做对应。这些规则不统一，写跨平台代码时要按目标平台的文档处理，不要凭另一家的经验推断。

    3.3　循环终止条件必须由应用把住

    模型可能连续调用多轮，也可能在同一轮里发出多条并行调用。协议本身不限制轮次，所以“最多几轮”是应用的责任：设一个轮次上限，超出后强制把当前状态交回用户，比让循环自己停下来可靠。

    并行调用还引出一个顺序问题：如果两个工具之间存在依赖（第二个需要第一个的结果），并行执行就会失败。多数平台提供关闭并行的开关，但更稳的做法是在描述里写清依赖关系，或者干脆让调用方串行执行、遇到失败就停下。

    04、从 Function Calling 到 Tool Calling

    4.1　两个名字，同一套机制

    这套机制在 2023 年进入主流 API 时叫 Function Calling。随着模型 API 开始支持不止函数型工具，tool / tools 逐渐成为更宽泛的抽象，tool calling、tool use 等术语也随之出现。需要说明的是，这是概念范围的扩展与术语变化，而不是一条统一的版本升级路线——不同厂商的命名和 API 演进并不完全一致。各家文档今天的用词因此并不统一：

    平台 文档中的常见叫法 控制调用行为的参数
    OpenAI 文档中并列使用两个名称 工具选择与并行开关两组参数
    Anthropic 统一称 tool use 工具选择参数（可选值含强制某工具、强制至少一次、禁用等）

    这是非完整枚举，只列了最常见的一组；不同厂商、不同一代文档之间的措辞差异很大，以各家具体文档为准。值得注意的是，用词差异不等于机制差异：把工具定义放进请求、让模型输出结构化的调用声明、再把结果回传，这个骨架在主流 API 里大体一致；差别更多落在承载字段、执行方以及结果消息的组织方式上。

    4.2　真正变化的是工具的种类

    如果只是改个名字，这个演进不值得单列一节。真正变化的是**“工具”这个集合里现在装了什么**。

    最早只有一种工具：应用自己定义、自己执行的函数。今天至少有三种形态（非完整枚举）。

    • 第一种是客户端函数，也就是前面讲的那种，schema 由应用定义、执行也在应用侧。
    • 第二种是平台内置工具，由模型服务方提供并执行，例如联网搜索、代码执行、以及部分文件与浏览器操作；这类工具的定义通常使用版本化的类型标识，具体类型名与版本号随平台发布变化，写作时应以官方文档为准而不是照抄示例。
    • 第三种是通过标准协议发现的工具，例如 MCP（Model Context Protocol）一类的开放协议——它把工具的定义、发现与调用从单次请求中拆出来，由宿主应用接入之后再呈现给模型，从而把一个“每个客户端对每个工具”的适配问题变成“一方实现、多方复用”。MCP 规范本身仍在演进，实现细节以官方规范为准。

    三类工具的差别不只在“模型怎么调用它们”，也在“由谁执行、工具从哪里来”——托管工具的调用请求由平台自己执行，应用可能根本不参与执行过程。这也是理解术语演进的正确角度：扩张的是工具的范围与执行位置，而不是一套需要整体替换掉的新机制。

    05、什么是 Tool

    一个 Tool 由四个部分组成。前三部分随请求进入模型的上下文，第四部分留在应用侧，模型完全看不见。

    5.1　name：模型用来指认的标识符

    名字是模型在调用声明里引用的键。形式上通常要求简短、只含受限字符集、在单次请求内唯一（同名工具同时出现属于未定义行为，各平台实现可能不同）。工程上还要考虑可读性：模型区分工具靠的就是名字加描述，get_user 和 get_user_profile 摆在一起时，命名本身就在承担区分职责。工具数量增长后，常见做法是加前缀做命名空间（例如按业务域分组），减少相近名字带来的误选。

    5.2　description：最关键的提示词面

    描述写得好不好，直接决定模型什么时候用这个工具、什么时候不该用。它要承担的说明包括：这个工具做什么、什么情况下应该调用、什么情况下不要调用（有替代工具时尤其重要）、返回什么形态的数据、有没有副作用。

    一个实用的判断标准：如果两个人读了同一份描述会做出不同的调用决策，这份描述就不够清楚。描述不是函数文档的缩略版，它是给模型的选择依据——写 查询订单状态 远不如写 按订单号查询当前状态与预计送达时间。不用于退款或修改收货地址。 有用，因为后者的信息量恰好落在模型的决策点上。

    5.3　input schema：参数的契约

    参数用 JSON Schema 描述：类型、必填项、枚举取值、嵌套结构、字段级说明。Schema 同时决定两件事——模型能填什么，以及应用能校验到什么程度。

    两点工程注意。一是各平台实际支持的是 JSON Schema 的一个子集，外部引用、正则约束等特性可能不被支持，写复杂 schema 之前先确认支持范围。二是严格模式对 schema 有额外要求（见 2.3），同一个 schema 在严格与非严格模式下未必通用，跨模式切换时要单独验一遍。

    5.4　execution：协议之外的部分

    执行不在协议里。协议只约定“模型怎么说”和“结果怎么回”，至于这段代码跑在哪、怎么鉴权、超时多久、失败了怎么办，全部由实现者决定。执行位置有两种形态：客户端执行（模型只提出请求，应用跑代码）与服务端执行（平台内置工具由平台自己跑）。两者的差别是信任边界与运维责任——客户端执行意味着你要自己承担权限控制、沙箱、超时、重试与审计。

    工具执行出错不是协议异常，而是一种正常结果。把错误信息作为结果回传给模型，模型往往能据此调整参数重试、改用别的工具，或者直接把失败原因告诉用户。反过来，如果应用在工具报错时抛出异常中断流程，模型就失去了这些调整机会。部分平台的工具结果消息带有显式的错误标记字段，用它把“执行失败”和“执行成功但结果为空”区分开，比在文本里约定一串魔法字符串可靠得多。

    06、Tool 能做什么

    从能力形态上，工具大体可以归到几类，但真正决定设计的不是分类，而是“读还是写”以及“可不可逆”：

    类别 典型例子 读/写 主要风险
    查询与读取 查订单状态、读配置、取用户资料 读 越权访问、敏感信息泄漏
    搜索与检索 联网搜索、文档库检索、代码搜索 读 结果被投毒、间接注入
    HTTP 接口调用 调第三方接口、触发工作流 读或写 参数被模型或上游内容操纵
    数据库操作 执行查询、写记录、更新状态 读或写 破坏性写入、语句注入
    文件系统操作 读文件、列目录、改代码 读或写 越界访问、误删
    外部系统动作 发消息、建工单、部署、付款 写 不可逆副作用

    这是非完整枚举，同一工具也可能横跨多类。表格想说明的是：只读工具的风险主要是隐私与注入；写入工具的风险是副作用本身——一次错误的转账、一次误删的生产部署、一条发给全体用户的公告，都不是“再调用一次”能撤销的。工程上的对应做法很朴素：写入类工具配最小权限凭据而不是管理员账号；高风险动作加人工确认，把工具调用变成“提案”，批准后才执行；以及对可重复到达的写操作做幂等设计。

    还有一条容易被忽略：工具返回的内容是外部输入，默认不可信。检索到的网页、数据库里的用户留言、第三方接口的响应，都可能夹带“忽略之前的指令”这类注入文本。工具结果在应用的数据流中应被视为外部不可信数据，而不是新的系统指令；边界标记、结果裁剪和内容过滤可以降低混淆与注入风险，但它们都不是绝对的安全边界——模型看到一段被包在标记里的“忽略之前所有指令”，未必因此就把它当成纯数据。涉及敏感操作时，最终的权限控制和人工确认仍应由应用侧承担，而不是指望模型自己分辨。

    07、Tool 与 Function Calling 的关系

    把两层分开看，关系就清楚了。

    上面一层是能力层：工具集合里都有什么。这一层随平台与生态扩张——从只有客户端函数，到内置搜索与代码执行，再到通过协议发现的第三方工具。下面一层是调用机制：工具如何被声明、模型如何产生调用请求、调用由谁执行、结果如何回传。Function Calling 可以看作这一机制在函数型工具上的一种具体叫法，Tool Calling / Tool Use 则是更宽泛的称呼；不同平台对客户端工具、托管工具以及调用结果的处理方式并不完全相同。

    维度 Tool Function Calling
    层次 能力抽象：可被模型调用的能力 调用机制：工具如何声明、调用请求如何产生、由谁执行、结果如何回传
    出现位置 工具定义、工具生态、开放协议 请求与响应中的字段与消息序列
    谁提供 执行方（应用或平台） 模型服务方提供协议骨架，应用负责接入
    数量关系 一个集合 一套流程

    所以下面两句话可以同时成立：Function Tool 是 Tool 集合里最常见的一种类型；Function Calling 是让这类工具的调用得以发生的机制。把它当成“新旧两代”或“两个竞争方案”都会导致错误的设计判断——比如在需要接入外部工具生态时，误以为换一个调用参数就能解决发现问题，而实际要解决的是工具从哪里来。

    落到实务上，三条建议。第一，把工具当接口设计：先定 schema 和描述，再写实现，描述里要写清“不该用”的场景。第二，把执行当不可信边界：参数必校验、权限最小化、写入类动作要幂等、错误要作为结果回传而不是抛异常。第三，把工具集合当上下文预算：每一条工具定义都占用上下文，工具越多、描述越相近，选择的准确率越可能下降；工具规模增长后，按需加载或按任务分组会比继续往数组里塞更划算。
