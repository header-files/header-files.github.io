    没有评估，就没有优化，只有折腾。你以为自己在调 Prompt，其实只是在同一批样本上反复试探自己的直觉。

    这个系列走到最后一篇。前几篇解决了“Prompt 怎么写”“方法怎么用”“工程怎么落地”，但始终悬着一个问题：凭什么说改完之后变好了？靠肉眼看两条输出、靠“感觉更顺了”来判断，在原型阶段勉强够用，一旦进入持续迭代就完全不成立。这篇文章先补上评估这一环，然后讨论 Prompt Engineering 的天花板——以及越过天花板之后，注意力会迁移到哪里。

    01、为什么 Prompt 需要评估

    凭直觉调 Prompt 之所以不可靠，原因不是人不够聪明，而是反馈信号本身质量太差。具体有四点：

    • 改动的影响面不可预测。语言模型的输出是全局受条件影响的——你在系统提示词里加一句“回答要简洁”，可能修好了摘要场景，却让代码解释场景丢掉了必要细节。这类跨场景的连锁影响，靠人工抽查几乎不可能发现。
    • 输出本身有随机性。同一条 Prompt 连续调十次，可能八次都好、两次格式崩坏。你恰好看到的那一次，不能代表分布。
    • 模型在动。模型升级或参数调整会让同一份 Prompt 的表现发生位移，而这种位移不会主动通知你。
    • “变好”缺乏定义。什么算好？更准确、更符合格式、更短、更少幻觉？没有事先定义的评价标准，讨论就只是各人主观偏好的拉扯。

    评估的价值就在这里：它把“感觉”换成可复现、可比较、可累积的证据。评估集一旦建起来，你的每一次修改都能得到一个数字，改进可以被验证、失败可以被归因、经验可以被沉淀。

    需要提醒一个顺序问题：不要一开始就搭一套宏大评估体系。常见的建议是从二三十条真实、有代表性的样本起步，跑通“改—测—比”这个循环，再逐步扩规模。评估体系是长出来的，不是设计出来的。

    02、测试集与评价指标

    2.1　测试集怎么建

    样本来源：最优解是线上真实日志——真实的输入分布、真实的失败案例、真实的边界情况，全都免费躺在你的日志里。次优解是领域专家按业务理解编写的样本。最差的是让模型自己造样本，在这个过程中你会不自觉地写出模型很容易通过的题，从而高估效果。

    样本构成：一批能长期用的测试集，通常包含四类样本。高频主路径若干条，代表大多数真实流量；边界输入若干条，比如空输入、超长输入、含特殊字符或指令样式文字的输入；已知坑若干条，每一条对应一次真实事故，用于防止同一个问题重新出现；以及一组“不该被改变”的基线样本，用来探测副作用。

    规模与维护：起步 20 到 50 条，覆盖主要场景后扩到数百条即可，不必追求几千条——样本的质量和代表性远比数量重要。测试集要定期更新：把线上新出现的失败案例补进去，把已经不可能出现的场景删掉。

    留一手：留一小批 holdout 样本，只在最终验收时使用，用来检验改动是否真的泛化。

    2.2　指标怎么定

    指标要分层，因为不同层的指标回答不同问题：

    • 任务质量：准确率、关键要点覆盖率、抽取字段的正确率，这是最核心的一层。
    • 格式与合规：结构化输出校验通过率、必含字段完整率、长度是否在范围内、是否触犯禁止项。这层最容易自动化，适合做硬性门禁。
    • 行为稳定性：拒答率、兜底触发率、重试率、输出长度的波动幅度。
    • 成本与性能：延迟的分位数（不要只看平均，长尾延迟才是用户体验的杀手）、输入输出 token 用量、单次调用成本。
    • 线上业务指标：采纳率、人工改写率、任务完成率、留存。这是最终裁判，只是它反馈得慢。

    一个反复出现的教训是：单一指标会被优化出“假象”。只看长度会让模型越写越短，只看相似度会让模型学会套模板。所以至少要有一个质量指标配一个成本指标，再加上一条护栏（比如格式合规率必须不下降）。

    03、三种评估方式

    3.1　人工评估

    人工评估是基准，也是最贵的。它的质量取决于两件事：评分细则写得够不够具体（好/差分别对应什么可观察的特征，而不是“感觉不错”），以及标注者之间的一致性够不够（多人标同一批样本，看分歧有多大；分歧大的条目，通常说明你的评分标准本身有问题）。

    方法上，成对比较优于绝对打分。让人判断“A 和 B 哪个更好”比“给 A 打 1 到 5 分”稳定得多，因为人对相对差异的感知一致性远高于对绝对量级的感知一致性。

    人工评估的正确用法不是全量标注，而是：高风险场景的关键样本、以及定期校准自动评估方法。

    3.2　规则评估

    规则评估是可判定部分的自动化检查：格式是否合法、字段是否齐全、数值是否越界、必含词与禁用词、长度区间。它的好处是结果确定、可解释、可直接进 CI 和线上兜底。它的边界同样清晰：规则只能覆盖“能写下来”的要求，覆盖不了“回答得好不好”。所以规则评估在实践中通常不作为质量分数使用，而是作为门禁——格式不合规直接判定为失败，不需要再讨论质量。

    写规则时有个细节值得注意：规则要判定的应该是结果而不是表述形式。比如“必须包含免责声明”这条规则，判定的是有没有相应内容，而不是要求出现某个固定句子，否则模型换个说法就会被误判为失败，反过来也逼迫你把 Prompt 写死。

    3.3　LLM-as-a-Judge

    用模型当评委，是在成本和质量之间补上的中间层：可以规模化、能处理开放式质量判断、评分细则可以写得很细。但它带着已知的系统性偏差，用之前必须了解：

    • 位置偏差：成对比较时倾向于选前面的那个。缓解办法是把顺序随机化，或交换顺序各评一次再合并。
    • 自我偏好：评委模型倾向偏爱与自身风格相似的输出。换用与生成模型不同家族或不同版本的评委能缓解一部分。
    • 长度与格式偏好：更长、结构更整齐的回答容易得高分，即使信息量并没有增加。要在细则里显式压掉这项偏好。
    • 细则缺失时的不稳定：让评委“综合打分”会得到方差不小的结果。改成逐项检查清单式的细则，稳定性会明显提升。

    还有一条经验：给评委提供参考答案或判定要点，比让它自由评判可靠得多；能拆成多个二选一判断的，不要合成一个五档打分。最后，judge 的分数必须定期与人工标注做校准——它不是真理，只是一个便宜得多的近似。

    3.4　怎么组合

    三种方法不是竞争关系，而是一条成本递增的漏斗：

    规则评估做硬门禁（格式与合规一票否决）→ judge 评估做质量分层与批量筛选 → 高风险场景与 judge 结果存疑的样本交给人工复核 → 人工标注的结果反过来校准 judge 的细则。

    如此循环，你会得到一套“大部分时间自动化、关键时刻有人把关”的评估体系。

    04、A/B Test

    离线评估能回答“输出质量是否更好”，但回答不了“对产品是否更好”。用户可能更愿意采纳一个稍短、少一点细节的回答；也可能因为回答变长而更快完成任务。这些只有真实流量能告诉你。

    一次像样的 A/B 要提前定好几件事：单一变更（一次只比一个变量，否则无法归因）、稳定性分流（同一用户在实验期内始终落在同一版本，否则体验会抖动）、指标预设（主指标 + 护栏指标，防止为了主指标牺牲掉不该牺牲的东西）、样本量与时长估计（流量小、效应小的实验，跑不够时间就会得到噪声结论）。

    LLM 场景下 A/B 还有几个特有难点。输出的方差大，需要的样本量比常规 UI 实验更大；用户反馈稀疏且滞后，很多信号要过几天才显现；多轮对话场景存在溢出效应——用户对当前版本的体验会影响后续判断。这些都需要在实验设计阶段就考虑，而不是事后解释数据。

    另外要区分两种“灰度”：影子流量（新版本只处理流量、结果不返回给用户）适合观察输出差异、成本变化和异常率，不适合测用户体验；灰度发布（小比例真实用户使用新版本）才是有反馈信号的实验。别把前者当成后者。

    05、Prompt 优化与回归测试

    有了评估，优化才变成一个可管理的循环：建立基线（当前版本跑一遍全量评测）→ 定位失败（把失败样本归类，而不是笼统地说“效果不好”）→ 单变量修改 → 重跑评测（看总分，更看分项和长尾）→ 更新实验记录 → 发布并保留回滚点。

    失败样本的归类很重要，它决定了你该往哪个方向改。常见类别和对应动作大致是：

    • 指令歧义：模型理解成了另一件事 → 改措辞、补定义、拆任务。
    • 信息不足：模型没有依据只能编 → 这不是 Prompt 问题，需要接入检索或补充资料。
    • 格式问题：内容对但结构不对 → 收紧约束、给示例、上结构化输出。
    • 示例误导：模型套用了错误模式 → 检查示例的一致性与代表性。
    • 能力上限：要求和模型能力不匹配 → 换模型或换方案，继续调 Prompt 是浪费。

    优化手段本身也有一个性价比排序，通常按这个顺序试：先把指令写清楚，再补示例，再调结构与位置，然后上格式约束与结构化输出，然后考虑任务分解，最后才是换模型。每次只改一处，否则你永远不知道是哪个改动起了作用。每轮实验都值得留一条记录：改了什么、指标怎么变、结论是什么——这些记录累积起来，就是团队的 Prompt 经验库。

    最后是把回归测试接进流程：Prompt 文件变更时自动跑评测集，分数低于阈值就拦住合并。做到这一步，“改 Prompt”才和“改代码”享受同等待遇。

    06、Prompt Engineering 的局限

    评估做到位之后，你会更清楚地看到一件事：很多“Prompt 没调好”的问题，其实根本不是 Prompt 的问题：

    模型不知道的事，问不出来。内部知识、实时数据、私有数据库里的内容，无论怎么措辞都不会凭空出现。这类需求的方向是检索增强与知识注入，不是修辞。

    模型做不到的事，写不出来。精确计算、严格事务、可靠的外部动作，靠自然语言约束只能提高概率，不能提供保证。这些要靠工具调用与代码执行。

    状态问题不属于 Prompt 层。多轮对话中的历史管理、长期记忆、上下文预算分配，本质是上下文工程；把希望寄托在“写得更好的一句话”上，只会让 Prompt 越来越长、越来越脆弱。

    系统约束不是文本能解决的。并发、延迟、成本上限、权限与合规，全都超出 Prompt 的作用范围。

    Prompt 的收益会递减并趋于平台。当指令、示例、约束都写到位之后，继续微调措辞的边际收益会快速接近零——这时候真正的增量来自上下文组织方式、工具能力和模型选型。

    把这些摆清楚，不代表 Prompt 不重要，而是说明它在系统中的位置：它是接口层，负责把意图、资料和约束翻译成模型能消费的形式；但一个可靠的系统需要在它之外再叠三层——更好的上下文、更强的工具、更稳的编排。

    07、从 Prompt Engineering 到 Context Engineering

    从“怎么写一句话”变成“怎么为模型的每一步设计它看到的全部信息”，这个视角常被称为 Context Engineering（上下文工程）。

    它关注的不是一段提示词，而是每一次模型调用的完整输入构成：系统指令、检索到的资料、工具定义、工具返回结果、历史对话、记忆片段、少量示例、以及格式约束。核心问题也随之从“措辞”变成了分配与取舍：

    • 选什么进来：相关性、时效性、可信度如何权衡？宁缺毋滥还是宁多勿漏？多进来的噪声会挤掉真正重要的信号。
    • 怎么压缩：长材料是全文放进去，还是先摘要、先结构化抽取、或只放关键段落与引用指针？压缩本身会引入信息损失，需要有评估。
    • 放在哪里：位置会影响权重，长材料与关键指令的相对顺序需要按目标模型验证，而不是照抄结论。
    • 怎么验证：评估对象从“一条 Prompt 的质量”升级为“一套上下文组装策略的端到端任务成功率”，同时要监控 token 成本与延迟的变化。

    工程化的要求也随之平移：模板演进为上下文组装，版本管理要覆盖组装策略与检索配置，日志要记录“这一次实际拼进了哪些片段”，回归测试要能感知“换了一种召回策略”带来的影响。上下文工程不是一套新协议或新技术栈，它更多是关注点的迁移——当模型本身变强，把信息组织对，往往比把话说得漂亮更值钱。

    08、从 Prompt 到 Agent

    再往前一步，就是从单次问答走向多步自主执行。Agent 的形态是：模型自己决定下一步做什么（选工具、给参数），执行、观察结果，再决定下一步，直到任务完成或触发终止条件。ReAct 这类早期工作已经把“推理与行动交替进行”的范式讲清楚了，后续的工具调用范式（由模型声明调用工具及其参数，由外部执行并回填结果）把它变成了工程上的标准配置。

    在这个形态下，Prompt 的位置发生了什么变化？它没有消失，反而更关键了一层：系统指令仍然定义目标、边界与终止条件，工具说明的质量直接决定模型会不会正确使用工具，异常处理规则决定它卡住时是重试、换路径还是退出。

    但更大的变量已经转移到 Prompt 之外：

    • 工具设计。工具的数量、粒度与描述质量。工具太多会稀释选择准确率，描述含糊会让模型反复试错。工具是 Agent 的“API 文档”，也是它的能力边界。
    • 循环控制。步数上限、时间与成本预算、超时与死循环检测、何时强制收敛出结论。
    • 状态与上下文管理。多步执行会迅速吃满上下文，需要摘要、外置记忆、只保留必要观察结果的压缩策略。
    • 错误恢复。失败后的重试策略、反思与修正、降级路径，以及什么时候必须交给人。
    • 权限与安全。写操作、资金操作、对外发送这类动作必须有白名单、沙箱与人审批，而不能依赖模型“自觉”。

    评估方式同样要升级。从“这一次输出对不对”变成“这一条执行轨迹对不对”：过程是否合理、工具选择是否正确、参数是否恰当、步数与成本是否可接受、最终目标是否达成。A/B 也变得更难做——一条轨迹的成败由多个步骤共同决定，方差更大，需要的样本量更多，因此基于固定场景的轨迹评测集往往比线上 A/B 更实用。

    工程化的血脉则延续下来：日志从“一次调用”变成“一条轨迹”，每个步骤是一个可追踪的片段；版本管理同时要管提示词、工具定义和模型版本——这三者中任何一个变化，都可能让原来跑通的轨迹失效。

    回到这个系列最初的问题：Prompt 到底是什么。它是自然语言写给模型的程序，是意图与模型能力之间的接口。系列走到这里，可以补上后半句：随着系统变复杂，Prompt 从“全部”变成了“一部分”——但它是被最先写下的那一部分，也是所有上下文、工具与编排最终要服务于的那部分。
