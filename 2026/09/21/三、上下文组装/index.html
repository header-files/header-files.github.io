    三、上下文组装

    上一章拆开了上下文的组成，这一章要回答的是更实际的问题：这些东西是怎么在每一轮被拼装起来的？**从 Agent 的工程视角看，每一轮都需要重新确定“模型这一轮应该看到什么”。**即使上一轮已经存在完整上下文，下一轮仍然可能因为新增消息、工具结果、状态变化或上下文压缩而发生变化。在最简单的无状态 API 模式下，这通常表现为客户端重新组织所需的历史和上下文并发起下一次请求。

    01、核心循环：先看全局

    把 Agent 的一轮调用拉远看，它的形状是一个闭环：

    用户任务
   ↓
需要什么信息？
   ↓
RAG / Tool / Memory / Skill
   ↓
上下文组装
   ↓
LLM
   ↓
新的结果 / 状态
   ↓
重新构建 Context ──────┐
   ↑                  │
   └──────────────────┘

    这个环里有两个容易混为一谈的动作，值得先分开命名：

    • 上下文获取：去什么地方、用什么手段，把外部信息取回来。它回答“信息从哪来”。检索知识库、读记忆、调工具、加载技能、采集环境状态，都属于这一步。
    • 上下文组装：把取回来的原料，连同系统提示、历史记录，加工成这一次请求的完整配置。它回答“信息怎么摆”。

    02、上下文组装：五步流水线

    组装这件事，拆开看是五步。它不是什么框架规定的标准流程，而是把实际在做的事按顺序说清楚。

    2.1 收集：先划定候选范围

    第一步是把“可能用得到的东西”列出来：哪些工具可用、哪些技能相关、哪些文件可能有关、历史里哪几段还有效、记忆里有没有相关条目。

    这一步的判据是宽进——宁可多列一点，也不要漏掉关键项。但“宽进”有个前提：候选必须是可以被枚举的。如果你根本不知道信息在哪（不知道有哪个文件、哪张表、哪个接口），那就不是收集问题，而是要在组装阶段安排一次“探索”，让 agent 用工具去找。另外，**这里的“宽进”只针对候选集，不意味着把候选信息全部放进 Context。**候选集可以很大，但真正注入模型的 Context 仍应尽量保持高信号密度。

    2.2 选择：决定谁进来、谁留下指针

    第二步是把候选集收敛成“这次真的放进去”的那一份。判据不是“相关不相关”，而是更严格的一条：没有它，这一步能不能做对？

    这一步是整条流水线上最需要判断力、也最容易被做坏的地方。最常见的错误是“看起来相关就带上”：检索命中十份文档就都塞进去，其中八份就是纯干扰；工具返回一个大 JSON，字段一个不落地灌进去。选择的反面不是遗漏，而是稀释——放进去的东西越多，关键信号的相对权重越低。一个实用的判据是：如果内容体量较大、当前又不一定需要全文，优先保留指针；只有真正需要时再加载本体， 文件路径、查询语句、文档链接都是指针，成本极低；真需要内容时再取。

    2.3 组织：把信息切成有边界的块

    第三步是结构问题。同样一批信息，平铺成一大段文字，和分成若干带标题的区块，模型的理解难度差很多。Anthropic 在系统提示的写法上给过具体建议：拆成明确的分节（背景信息、指令、工具指引、输出格式等），用 XML 标签或 Markdown 标题把边界标出来。Cognition 从另一个角度说了同一件事：**对需要协作或交接的 Agent，不能只共享一个脱离上下文的最终结论；至少应该保留足以解释该结论的关键行动、观察和决策信息。**因为一个动作背后带着一串隐含决策，只给结论就等于让接收方重新猜一遍。

    组织这一步的核心是让每块信息的边界和身份都清楚：这是什么、谁写的、什么时候产生的、还算不算数。含糊的边界会直接变成后面的冲突——两块内容互相矛盾时，模型往往连它们属于哪个层面都分不清。

    2.4 格式化：适配模型的读取方式

    第四步是决定用什么格式呈现。结构化数据用 JSON、表格还是自然语言？长文档给全文还是给摘要？日志给多少行？代码给整个文件还是给片段？

    这里有个容易被忽略的判断：格式要迁就模型的处理方式，而不是迁就上游系统的输出方式。 直接透传一个嵌套五层的 API 响应，通常不如提取三个关键字段再列成表。格式化的核心目标，是让模型能够低成本地识别信息结构、提取关键信息，并按预期使用它。这也是工具设计里常说的原则——工具应当返回 token 效率高、无需二次加工的信息。

    2.5 排序：位置本身就是信息

    最后一步是摆放顺序。位置为什么重要，有两个原因：

    原因一：注意力分布不均匀。 “lost in the middle”的研究发现，长上下文里位于开头和结尾的信息更容易被模型准确利用，埋在中间的信息召回明显下降。所以在长上下文中，可以优先考虑把高优先级指令和关键结论放在模型更容易利用的位置。

    原因二：前缀缓存。 这一点在工程上更硬。多数模型的缓存是按前缀匹配的——从请求开头到缓存断点之间的内容完全一致，才能命中缓存；中间任何一处变化，都会让它之后的所有内容重新计算。这意味着顺序不只是注意力问题，还是成本与延迟问题。

    因此有一条被官方文档明确写出的排序原则：静态内容在前，动态内容在后。 以采用前缀缓存的 Agent 系统为例，一个常见的组织方式是：

    1. 静态系统提示与工具定义（全局缓存）
    2. 项目上下文，如指令文件、自动记忆（项目内缓存）
    3. 会话上下文（会话内缓存）
    4. 对话消息（每轮变化）

    顺序一旦被破坏，代价立刻体现——把精确到秒的时间戳写进静态系统提示、工具定义顺序随机抖动，都会让整段缓存失效。所以需要更新的信息（比如当前时间、刚改过的文件）更合适的做法是随下一轮消息带进去，而不是回头改系统提示。在一些 Agent 实现中，临时加载的技能、计划或阶段性指令会作为新的上下文块追加，而不是修改原有系统指令。这样可以减少对稳定前缀的影响。

    03、上下文获取：五种来源，五种代价

    组装流水线要往里面放的原料，来自五个地方。它们真正的差别不在“能拿到什么”，而在新鲜度、成本和可控性这三件事上。

    3.1 检索：向知识库要事实

    检索解决的是“从外部信息空间中找到与当前任务相关的信息”这一问题——产品文档、规范、历史邮件、代码库说明。它通常发生在调用之前，把相关资料预先召回并注入。

    它的主要风险是精度而非召回：召回太多会污染上下文，召回太旧会引入过时事实。所以检索环节真正需要设计的往往不是“怎么多拿”，而是“怎么少拿”和“怎么判断还算不算数”——重排序、时效过滤、版本与权限过滤，都属于这一层。

    3.2 记忆：向历史要连续性

    记忆解决的是“跨会话连续性”——用户偏好、项目背景、之前做过的决策。它的形态可以是文件、向量库或结构化存储，但机制一致：存在外面，按需回灌。

    记忆系统的难点不在读取，而在写入与失效。一条过时的结论一旦进了记忆，它会持续污染此后所有会话，而且因为“看起来是记忆”而显得格外可信。设计记忆时，写入规则和过期机制的重要性不低于检索质量。

    3.3 工具：向真实世界要当前状态

    工具解决的是“实时性”——当前订单状态、当前库存、当前分支、当前线上指标。对实时性要求高、且状态变化频繁的信息，应优先通过工具在运行时获取；对于允许一定延迟的数据，更新后的索引仍然可以通过 RAG 提供。

    这条原则有一个很实际的推论：凡是会变化的信息，都不该写进静态上下文。 把它写进系统提示，既会过期，又会破坏缓存；正确做法是留一个工具，让 agent 在需要时自己去问。

    3.4 SKILL：向过程性知识要方法（按需加载）

    技能解决的是“怎么做才对”——某个领域的标准流程、注意事项、脚本工具。它的加载方式上一章已经讲过：名称与描述常驻（元数据层），触发时才把正文读进上下文，引用的文件与脚本进一步按需加载，脚本甚至只回灌运行结果。

    从获取的角度看，技能是最“省”的一种：不带内容，只带入口。它的代价转移到另一个地方——描述必须准确，否则技能永远不会被触发。

    3.5 环境：向运行时要现场状态

    环境获取解决的是“我在哪儿干活”——工作目录、操作系统、当前时间、git 分支与改动、目录结构、项目说明文件。它让 agent 能写对路径、按平台差异行事、正确处理日期。

    需要注意两点。第一，环境信息可以以快照形式注入，也可以通过工具在运行时重新获取。 如果系统只在会话开始时建立环境快照，那么后续文件、Git 状态等变化不会自动反映到这份快照中，需要主动重新读取。第二，环境信息的采集成本往往被低估——把整个目录树塞进上下文，在大型仓库里可能直接吃掉可观的预算，通常更好的做法是给出摘要与导航入口。

    来源 典型获取时机 新鲜度 边际成本 主要风险
    检索 调用前预取 取决于索引更新 中（内容体积大） 信噪比低、可能过时
    记忆 按需回灌 跨会话累积，可能过时 低到中 过时结论持续污染
    工具 运行时主动调用 最高（当场为真） 延迟 + 结果不可控 结果体积失控
    技能 触发时加载正文 低（过程知识少变） 元数据极小 描述不准导致不触发
    环境 会话开始采集 快照，不自动更新 中到大 过期快照误导判断

    04、为什么不能一次性全塞进去

    既然信息都能拿到，为什么不干脆开局全放进去，省掉每一轮的取用决策？这是很多人的第一反应，但它行不通，即使模型拥有很大的 Context Window，也不意味着应该把所有可用信息一次性放进去。原因有四层，而且是叠加的。

    第一，相关性是随任务演化的，而预加载是静态的。 任务第 30 步真正需要的信息，第 1 步时未必存在——它可能是第 25 步的产物；也可能当时看起来无关，后来才变得关键。预加载逻辑写在第 1 步，注定要猜第 30 步的心思。

    第二，环境会变，索引会旧。 预先构建的索引、预先拉取的数据，在长任务里会逐渐偏离真实状态。官方文档在对比两种策略时点出过这一点：即时检索能绕开陈旧索引的问题。

    第三，注意力与预算都是有限的。 上下文越长，通常意味着模型一定表现越差，而且信息噪声、处理成本和延迟通常会上升，部分长上下文任务还可能出现有效信息利用率下降的问题。把所有信息一次性塞进去，等于主动把自己的有效上下文压缩到最差状态。

    第四，也是最少被提到的一点：你不可能提前知道 agent 需要什么。 面对复杂任务，人也不知道下一步会撞上什么。预先穷举所有可能性，成本上不可行，而且会把上下文变成一份无人维护的档案库。

    所以主流方案不是二选一，而是混合：一部分信息预先注入（稳定、必然需要，如系统提示、项目约定文件），其余留轻量标识符，运行时按需加载。Claude Code 就是这种形态——项目说明文件在会话开始时直接放入上下文，而文件检索交给 glob、grep 这类工具即时完成。

    这个权衡有它的代价，得说清楚：运行时探索比预先检索更慢，而且它依赖两件事做到位——合适的工具，以及清晰的导航规则。工具不称手或规则不明确时，agent 会在上下文里浪费预算：误用工具、走进死胡同、或者干脆找不到关键信息。所以“让 agent 自己去查”不是省事，而是把工程量从数据准备挪到了工具与规则设计上。

    05、按任务动态构建

    动态构建的实操方法，可以总结成一句反推：先问这一步要产出什么，再问产出它需要什么信息。

    例如“修一个测试失败的 bug”，需要的是复现路径、报错信息、相关源码、近期改动；不需要的是整个代码库的架构文档。而“跨模块重构接口”，需要的是调用点清单、接口契约、约定规范，不需要某一次具体的报错堆栈。同一套系统面对这两类任务，正确的上下文配置完全不同：

    任务类型 主要信息来源 可以只留指针的 需要警惕的
    定点修 bug 报错输出、目标源码、近期改动 无关模块的代码 历史里已被推翻的旧结论
    跨模块重构 调用点清单、接口契约、项目约定 实现细节、测试夹具全文 局部改动带来的隐藏依赖
    数据分析 表结构、统计口径、抽样结果 全量数据集 大结果集直接灌入
    长文写作 大纲、素材片段、参考规范 素材全文 素材之间口径不一致
    线上排障 实时指标、日志摘要、变更记录 历史归档日志 用快照当实时状态

    这张表的价值不在具体条目，而在那个反推动作：从产出倒推输入。按这个顺序想，绝大多数“要不要放进去”的纠结会自动消失——凡是对本次产出没有贡献的，都不进来。

    06、渐进披露：让信息分层出现

    渐进披露是把“选择”这一步制度化的做法。技能机制是它最清晰的实现：元数据常驻、正文触发时加载、资源按需读取，脚本只回灌结果。三层各有各的 token 成本，未使用的那部分几乎不花钱。

    但这个原则的价值远不止于技能。它可以被提炼成通用的四句话：

    • 指针优先于内容：先给路径、查询、链接，需要时再取；
    • 摘要优先于全文：先给结构和结论，细节在追问时展开；
    • 索引优先于数据：先让 agent 知道“有什么、在哪”，而不是把东西全搬过来；
    • 入口优先于知识：过程性知识只保留入口（技能描述），不预载正文。

    支撑这一切的前提条件常被忽略：按需加载要求 agent 有办法“找到”信息。 文件系统的价值因此不止是存储——目录层级、命名约定、时间戳本身就是信号，它们让 agent 能在不读内容的情况下判断该不该读：同名文件在 tests/ 下和 src/ 下意味着完全不同的用途，文件大小暗示复杂度，时间戳是相关性的agent指标。agent 就是这样一层层把理解拼起来，工作记忆里只保留当下必需的。

    隔离是渐进披露的另一种形态：把子任务交给独立上下文的子agent，让它自己去查、去试，只把结论带回来。这样调查过程不必占据主agent的历史，主agent的轨迹可以跑得更长。代价是子agent看不到全部背景，所以它适合回答边界清晰的问题，而不适合替主agent做需要全局信息的决策。

    07、多轮对话里，上下文如何不断变化

    回到开头的循环。单看一轮，组装是五步流水线；连起来看多轮，上下文其实一直在做四种动作：

    • 追加。 新消息、新工具结果、新的环境变化，都从尾部进入。这是最自然的增长方式，也是最容易失控的方式。
    • 外置。 把该记住但不必常驻的东西写到上下文之外：任务清单、进展笔记、关键决策。Anthropic 把这套做法称为结构化笔记，也直接叫 agentic memory；它的价值在于上下文重置之后还能恢复连续性——agent 读回自己的笔记，接着往下做。这里有一个关键细节：外置的不只是数据，更是决策的上下文。写“改了 A 文件”没用，写“因为 B 约束所以选择 A 而不是 C”才有用。
    • 压缩。 接近预算上限时，把历史总结成精炼版本，用压缩后的上下文开启新窗口。压缩的取舍很讲究：保留架构决策、未解决的 bug、实现细节，丢掉重复的工具输出和寒暄。压得太狠会丢掉当时看不出重要、后来才关键的细节，所以压缩提示通常需要专门调校，先保证召回率再收紧。Cognition 对此的判断很直接：把行动与对话历史压缩成关键细节是一件极难做对的事，值得专门投入，甚至为此训练专门的小模型。
    • 重置与回灌。 任务之间清空上下文（换一个不相干的任务时），或者从压缩点重新开始，然后按需把记忆、笔记、必要文件读回来。Claude Code 的做法是压缩后带上最近访问的若干文件继续——连续性由“摘要 + 少量新鲜文件”维持，而不是靠保留全部历史。

    这四种动作合起来，构成了 Agent 长期工作的基本节奏：追加 → 积累 → 压缩 → 重置 → 回灌。而决定每一次动作取舍的判据，回到最上面那句话——这一步需要什么信息。

    最后还有一个常被忽视的工程约束：**上下文的大幅改动可能影响缓存复用。**对采用前缀缓存的系统，如果缓存前缀中的内容发生变化，变化点之后的内容通常无法继续复用原缓存。因此，压缩、重载项目上下文、调整工具集合等可能影响前缀的操作，最好在任务的自然断点进行。具体哪些参数会导致缓存失效，则取决于模型提供商和缓存机制，不能一概而论。
