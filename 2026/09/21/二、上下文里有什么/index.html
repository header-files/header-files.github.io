    二、上下文里有什么

    很多人以为自己在跟一个“读过很多东西的模型”对话。事实是：每次调用，模型只知道这一次塞进去的那几万到几十万个 token——你在下一轮问题里少放一段历史，它就真的不记得；你没声明的工具，它就真的不知道存在。所以理解上下文的组成，是理解 Agent 行为的第一步。

    01、先别急着列清单

    要回答“上下文由什么组成”，最容易的写法是列一张清单，逐个名词解释一遍。但那不太有用——清单只能告诉你有哪些角色出场，不能告诉你它们在什么条件下出场、谁和谁抢地方、哪一个该被丢掉。Context Engineering 关注的不是“上下文里有哪些东西”，而是“从所有可用信息中，如何构造当前这一轮真正应该给模型看的 Context”。

    先建立一个更准确的视角。围绕“信息能否进入上下文”，其实存在三层：

    1. 可注入的全集：从系统状态到外部世界，所有理论上可以被搬进上下文的东西——文件系统、数据库、API、会话历史、环境变量。
    2. 本轮的候选集：根据当前这一步的目标，被判断为“可能相关”的那部分。检索、筛选、工具调用都在这一层发生。
    3. 实际注入的集：在 token 预算和注意力预算之内，最终真的写进这次请求的那部分配置。

    后面要讲的十个组成部分，描述的是第一层——全集里有哪些可选项。而工程的实质工作发生在第二层和第三层：从全集里挑出最小的高信号子集。所以在读下面的分类时，请始终保持一个意识：这里列的每一项，都是“可以进来”，不是“应该进来”。

    02、指令信息：约束行为的稳定层

    第一根支干是指令信息，即“模型应该怎么做”的约束。它的特点是相对稳定：写一次，多轮生效。

    2.1 System Prompt

    系统提示词是上下文中用于约束模型行为的一类稳定信息。不同 API 对它的承载方式不同：有的提供独立字段，有的将其作为消息序列中的特殊角色或指令层级处理。

    关于系统提示有个常见误区：写得越长越保险。Anthropic 的建议恰好相反——追求“最小的、足以完整描述期望行为的信息集合”，并且用分节、XML 标签或 Markdown 标题把内容组织成可导航的区块（背景信息、指令、工具说明、输出格式等）。注意“最小”不等于“短”：如果 agent 必须知道某条规则才能正确工作，那这条规则再长也该写进去。此外，在一些 Coding Agent 中，项目级或用户级规则文件（例如各类 AGENT.md、规则目录）会在启动或特定阶段被加载，并最终作为模型可见的指令上下文使用；有的实现会将其拼接到系统提示词中，有的则采用其他注入方式。

    2.2 SKILL：被拆出来的过程性知识

    Skill解决的是“系统提示装不下大量专业知识”的问题。一个 Skill 本质是一个目录，核心是 SKILL.md：YAML 头部写名字和描述，正文写流程、最佳实践和示例，目录里还可以附带参考文档和可执行脚本。

    它进入上下文的方式是渐进披露，分三级：

    • 第一级：元数据，始终在。启动时，所有已安装 Skill 的名字和描述被预加载进系统提示，单个约百 token 量级。它只够让模型判断“这个 Skill 该不该用”。
    • 第二级：指令，触发时才读。当请求匹配上某个 Skill 的描述，agent 通过读取文件的方式把 SKILL.md 正文载入上下文（官方文档给出的量级是 5K token 以内）。
    • 第三级：资源与代码，按需加载。附带的参考文档只有被打开时才进入上下文；脚本则由执行环境运行，通常只有运行结果进入上下文，源码本身不进入。

    这套设计的价值在于：你可以装几十个 Skill，而不常用的那些只付元数据的成本。也正因为如此，Skill 的作者必须把“描述”当成检索入口来写——描述写得含糊，整个 Skill 可能永远不会被触发。

    顺带澄清一个高频混淆：Skill 与 MCP 不是竞品。MCP 是连接标准，解决“agent 如何访问外部工具和系统”；Skill 是知识打包标准，解决“agent 知道该按什么流程办事”。一个 Skill 的正文里完全可以指示模型去调用某个 MCP 工具。

    2.3 工具描述与工具结果：能力声明与执行回执

    工具描述是“我能做什么”的描述：名称、用途描述、入参 schema。它和 Skill 的区别是职责不同——Skill 教流程，工具给能力。工具定义的常见失败模式是臃肿：功能重叠、边界模糊，导致模型在决策点上犹豫。如果人类工程师都说不清某个场景该用哪个工具，模型更不可能说清。

    工具结果则是“我做了什么”的回执：API 响应、命令输出、代码执行结果、文件内容。严格说，它的性质和历史消息一样是动态增长的——每调一次工具就多一块。这里要如实说明一个规范细节：在多数 API 设计里，工具结果并不是一种独立消息类型，而是以特定形式回灌进消息序列的（例如作为 user 消息中的工具结果块，或使用专门的工具角色），具体形式以各家 API 文档为准。也就是说，工具结果其实同时属于“工具契约的延伸”和“对话历史的一部分”。

    它在后面结构图上挂在提示词支干末端、却直接通向 LLM，原因就在这里：它是一个跨界的组件——身世属于工具，形态属于历史，内容属于外部世界。

    03、任务信息：任务自己的轨迹

    第二根支干是任务信息，即“当前这个任务进行到哪儿了”。它的特点是随每一轮增长，是上下文里体积最不可控的部分。

    3.1 用户输入

    用户当前输入是整次调用中最“显式”的上下文：本轮的问题、附件、@ 引用的文件。它通常还承担一个隐含角色——注意力锚点。上下文中的信息很多，但当前这一步到底要解决什么，主要靠它来指认。这也是为什么在多轮长任务里，把目标重新表述一遍，往往比补充更多背景资料更有效。

    3.2 对话历史

    对话历史是前序所有轮次的用户消息、模型回复和工具调用的累积。它的地位可以用一句话概括：从工程视角看，对话历史承担了当前会话的短期记忆作用：如果上一轮的重要信息没有以某种形式保留下来，后续推理就无法直接利用它。——不是“参考材料”，而是它唯一能知道“刚才发生了什么”的途径。

    对话历史带来两个结构性麻烦。一是它单调增长，在最简单的无状态 API 调用模式下，每一轮通常需要重新提供模型所需的历史信息；随着历史增长，这部分输入成本和上下文占用也会增加；二是它一旦被写进去就很难撤销——一条错误结论留在历史里，会被后续步骤反复引用，成为后续判断的事实基础。所以压缩、总结、截断这些手段的主战场都在这里。

    3.3 任务状态：计划、待办与进度

    任务状态是任务自己的结构化状态：当前目标、已完成步骤、待办清单、已知结论、未解决的问题。Anthropic 把它称作结构化笔记（structured note-taking），也直接叫 agentic memory——agent 把笔记写到上下文之外的文件里，需要时再取回来。Claude Code 的待办清单、自定义 agent 维护的 NOTES.md 都是这个模式：任务跨越几十次工具调用、甚至经历几轮上下文重置之后，agent 靠读自己的笔记恢复连续性。

    这里必须说明一个术语边界：Anthropic 用 memory 指代这套机制，而本系列把 Task State（任务内）和 Memory（跨任务）分开讨论。这只是工程视角的划分，不是官方分类。 区分它们的实用价值在于判断生命周期：任务结束就该清理的是 Task State，需要长期沉淀的是 Memory。

    04、外部信息：上下文之外的世界

    第三根支干是外部信息，即“模型世界之外的知识”。它的特点是默认不在上下文里，需要主动搬运——而搬运方式决定了成本。

    4.1 RAG / External Knowledge：按需检索的事实

    RAG 等检索机制，负责把领域资料、文档、数据库内容按需拉进上下文。这里的核心工程判断不是“怎么检索到”，而是“检索到多少”：召回十个片段、只有两个真正相关，那八个就是纯粹的干扰项。检索环节的精度直接决定上下文的信噪比。

    Anthropic 提出的“即时（just in time）上下文”是另一个方向：与其预先把所有相关数据都塞进去，不如只保留轻量标识符——文件路径、存储的查询语句、网页链接——在需要时通过工具动态加载。Claude Code 处理大数据库时就是这么做的：让模型写针对性查询、抽样查看，而不是把整个数据对象装进上下文。

    4.2 Memory：跨会话的持久沉淀

    Memory 是跨会话、跨任务保留的信息：用户偏好、项目背景、历史决策、踩过的坑。它的实现形态多样——文件式（Anthropic 在 Sonnet 4.5 发布时公开了基于文件系统的 memory tool 公测）、向量库、结构化数据库——但共同点是：存储在外，按需回灌。

    Memory 的坑不在“记不记得住”，而在“记的是不是还对”。写进记忆的结论如果已经过时，就会变成一条持续误导后续所有会话的错误事实。所以记忆系统真正需要设计的不仅是检索，还需要设计写入规则和失效机制。

    4.3 运行时环境快照

    最后一类是环境信息：当前工作目录、操作系统与平台、当前日期、git 分支与状态、目录结构、项目说明文件等。它让 agent 能正确使用绝对路径、按平台差异行事、在提交信息里写对日期。 例如在 Coding Agent 中，它的系统提示里包含环境块（工作目录、是否为 git 仓库、平台、当天日期、当前模型）、目录结构树、git 状态以及 README 内容。

    环境信息里藏着一个很典型的陷阱：它是会话开始时的静态快照，且明确说明不会在会话中更新。agent 自己新建了文件、提交了代码，快照里都看不到。于是模型可能基于过期的环境认知做判断——除非它主动用工具去重新读取真实状态。这里将运行时环境单独列出，是因为它与任务状态的生命周期不同：任务状态描述 Agent 对任务的内部认知，而环境信息描述 agent 所处外部环境的当前状态。

    05、四个维度看清它们的差别

    把上面十项放在一起，用同一套坐标去比，结构会清楚很多。下面这张表只是常见实现的归纳，不是规范定义：

    组件 谁产生 何时进入 变更频率 典型体量
    系统提示词 开发者 每次调用 极低 中
    Skill Skill 作者 元数据常驻，正文按需 低 元数据小，正文中
    工具描述 开发者 每次调用 低 中
    工具结果 外部系统 每次工具调用后 每轮增长 大且不可控
    用户输入 用户 本轮 每轮 小
    对话历史 双方累积 每次调用（或压缩后） 每轮增长 最大
    任务状态 Agent 自己 按需写入与取回 每轮 小到中
    RAG 外部知识库 检索命中时 按需 中到大
    Memory 用户 / Agent 按需回灌 跨会话累积 小到中
    运行时环境快照 运行时采集 会话开始时 极低（且不自动更新） 中到大

    四个维度里，最有指导意义的是变更频率，这决定了哪些该外置、哪些必须每轮精算，在后面几章讲压缩、隔离与冲突处理时会反复用到。

    06、合起来是什么样子

    三个支干合起来，就是一张 Agent 单轮调用的上下文全景图：

                          Context
                         │
     ┌───────────────────┼───────────────────┐
     │                   │                   │
  指令信息             任务信息              外部信息
     │                   │                   │
提示词 / Skill         用户输入           RAG / Knowledge
工具描述               对话历史           Memory
工具结果               任务状态           运行时环境快照
     │                   │                   │
     └───────────────────┼───────────────────┘
                         ▼
                        LLM

    这张图的划分逻辑是“这块信息是干什么用的”：

    • 指令信息 回答“该怎么做”，是行为约束，稳定优先；
    • 任务信息 回答“做到哪了”，是任务轨迹，增量最大；
    • 外部信息 回答“世界是什么样”，是外部事实，按需加载。

    最后一点需要说清楚：这类结构图是工程组织的产物，不是协议规定。Anthropic 官方文档在系统提示的组织上给过具体建议（用 XML 标签或 Markdown 标题分节），但并没有规定全部上下文组件必须按某个固定顺序排列。各家实现在顺序、边界和命名上都有差异——比如任务信息与 Memory 的界线，在很多实现里是模糊的。把它当作思考地图，而不是交接规范。

    07、由这张图引出的三个实践判断

    第一，稳定层要薄，动态层要管。 上面每一块“每次调用都会重发”的内容（系统提示、指令文件、工具定义）都是常驻成本。能外置的要外置：流程知识放进 Skill、参考资料放进可检索的存储、状态写进文件，让每轮固定重发的部分尽量小。Skill 的渐进披露就是这条原则最直接的体现。

    第二，上下文管理的主战场在“结果”和“历史”上。 十项里增长最快、最不可控的就是工具结果和对话历史——它们由 agent 自己的行为产生，无法预先写死。压缩、总结、外置、隔离这些手段几乎都是冲着它们去的。

    第三，同一个事实出现在多条支干上，是风险而不是冗余的保险。 项目说明可能同时出现在环境快照、RAG 命中和记忆里；工具结果可能和历史中某条更早的结论矛盾。一旦出现，模型不会报错，它只会行为摇摆。所以上下文治理的一条基本要求是：关键事实应尽量明确权威来源，并避免在多个上下文位置维护彼此独立的副本 这正好把话题交回上一章的问题——冲突是上下文的头号敌人之一，而它的根源往往不在模型，在信息架构。
