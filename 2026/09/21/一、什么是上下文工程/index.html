    一、什么是上下文工程

    同一个大模型，换个上下文，表现可以判若两“人”。2023 年我们拼命打磨提示词的措辞，2025 年之后，真正拉开差距的，是谁能把“模型在每一步能看到什么”设计好。这门手艺有一个新名字：上下文工程（Context Engineering）。

    01、从 Prompt Engineering 到 Context Engineering

    大模型应用早期，工程工作的核心确实是“写提示词”。想让模型输出更好的结果，就去琢磨措辞：加一句 “Let’s think step by step”，前面垫一句 “你是一位资深专家”，给几个 few-shot 示例，甚至有人总结出各种“咒语”。这些技巧有效，但脆弱——很多措辞层面的窍门，换一代模型就失效了，行业里戏称这是“提示词考古学”。

    2025 年年中，Context Engineering 这个说法开始快速流行。2025 年 6 月，Shopify CEO Tobi Lütke 发推表示，他更喜欢 “context engineering” 这个说法，因为它“更准确地描述了核心技能：为任务提供全部上下文，让 LLM 有可能完成任务”。几天后，Andrej Karpathy 跟进写道：

    “People associate prompts with short task descriptions you’d give an LLM in your day-to-day use. When in every industrial-strength LLM app, context engineering is the delicate art and science of filling the context window with just the right information for the next step.”

    大意是：人们把 prompt 理解成日常给模型的一小段任务描述，但在每个工业级 LLM 应用里，真正的工作是“用恰到好处的信息填满上下文窗口”这门精细的艺术与科学。Simon Willison 也指出，“prompt engineering” 在大众语境里已经退化成“跟聊天机器人打字聊天”，需要一个新词把其中真正不平凡的工作捞回来。

    这不是一次简单的改名，而是一次“升级”：工作的重心，从一条消息的措辞，迁移到了“模型能看到的一切东西”的架构设计上。Anthropic 在其工程博客中把 context engineering 定义为 prompt engineering 的自然演进——提示工程关注“怎么写好一段提示”，上下文工程关注“在模型推理的每一轮，如何策划并维护最优的信息集合”。

    02、Context 是什么

    先给一个可操作的定义：Context 是模型在某次推理时能看到的全部 token 的集合。

    这里的关键词是“全部”和“那一次”。很多人把 context 理解成“用户输入的那段话”，这远远不够。一次典型的 LLM 调用中，进入上下文的内容至少包括：

    • 系统提示（System Prompt）：角色、规则、输出格式等固定指令；
    • 工具定义（Tools）：工具名称、描述、参数 schema，以及通过 MCP 等机制提供给模型的工具信息；
    • 检索到的资料：RAG 命中的文档片段、数据库查询结果；
    • 对话历史：之前所有轮次的用户消息、模型回复；
    • 工具输出：上一步工具调用返回的 JSON、代码执行结果、网页内容；
    • 长期记忆：从外部存储注入的摘要或偏好信息；
    • 用户当前输入：本轮的问题和附件。

    理解 context 还有一个更根本的角度：从 API 调用的角度看，模型不会自动继承上一轮调用的对话状态；如果上一轮的信息没有被重新放入当前请求的上下文，当前这次推理就无法直接利用这些信息。它不是“知道得少”，而是“除了上下文，什么都不知道”。这就决定了：模型能力决定了它“能做什么”，上下文很大程度决定了它“这一次能做到什么”。

    另外要区分两个容易混淆的概念：context（这次调用里实际放进去的信息）是内容，context window（上下文窗口，能容纳的最大 token 数）是容器。容器大小是模型的技术规格，容器里装什么，才是工程问题。

    03、Context Engineering 是什么

    有了 context 的定义，context engineering 可以概括为一句话：在每一次推理之前，决定哪些信息进入上下文、以什么形式进入、以什么顺序摆放，并持续维护这个信息环境的系统化工程。

    几个有代表性的定义可以互相印证。Karpathy 强调“为下一步填入恰到好处的信息”——注意“下一步”，说明这是一个逐步推进的过程；LangChain 给过一个流传很广的类比：LLM 是 CPU，上下文窗口是 RAM，上下文工程扮演的是操作系统的角色——决定什么时候把哪些数据加载进内存，什么时候换出去；Anthropic 则称它是“在不断演变的信息宇宙中，策划哪些内容进入有限上下文窗口的艺术与科学”。

    从这个定义出发，上下文工程包含四类基本操作（LangChain 归纳为 Write、Select、Compress、Isolate 四个支柱）：

    1. 写入（Write）：把状态外置。把未来可能需要的信息写到上下文之外，例如文件、笔记、数据库或状态存储，使其可以在后续按需重新加载，而不是始终占据当前上下文；
    2. 选择（Select）：精确检索。基于相关性、时效、权限过滤，决定哪些外部信息值得进入本轮上下文；
    3. 压缩（Compress）：历史太长时做摘要，只保留关键决策、未完成事项和核心发现，丢弃冗余的工具输出；
    4. 隔离（Isolate）：把不同子任务分给不同的上下文（如子agent），各自只看到完成自己任务所需的最小信息。

    它和“写一段好提示词”的最大区别在于迭代性：提示词是一次性写就的静态产物，而上下文是每一轮推理都要重新决策的动态配置——智能体每跑一步，环境就产生新的信息，哪些保留、哪些丢弃、哪些外置，全部要在下一轮之前重新审视。这也意味着，上下文工程本质上是一个系统设计问题，而不是文案问题。

    04、Context 与 Prompt 的关系

    Prompt 和 Context 不是对立关系，而是包含关系：Prompt 是 Context 的一个组成部分。

    具体来说，系统提示词是上下文里最稳定、优先级最高的一块，few-shot 示例、用户消息也都属于上下文。Prompt engineering 解决的是“这一小块怎么写得好”；Context engineering 解决的是“整块内存怎么组织”。用前面 CPU/RAM 的类比：提示词工程像是优化一条指令的写法，上下文工程像是设计整个内存管理体系。

    两者的分野可以用一个客服场景说清楚。只做提示词工程，你可以写“当客户询问物流时，按以下流程解释查询状态的方法”——客户问一句通用问题没问题；但客户报出一个具体订单号时，模型给不出实时状态，因为订单数据根本不在上下文里。上下文工程的解法则完全不同：接入订单系统，检测到订单号时自动调用 API，把实时物流数据注入上下文，再配合提示词规定回复格式。提示词工程设计“响应的逻辑”，上下文工程设计“信息的环境”。

    所以“上下文工程取代提示词工程”这个说法并不准确。提示词工程没有死，它降级成了更大系统里的一部分——一个运行良好的 Agent，依然需要精心打磨的系统提示词，只不过决定成败的变量变多了。

    05、为什么 Agent 需要 Context Engineering

    如果只是单轮问答，提示词工程勉强够用。但 Agent 改变了游戏规则。Anthropic 对 Agent 有一个简洁的定义：在循环中自主使用工具的 LLM。正是“循环”和“工具”这两个词，让上下文从“背景信息”变成了系统的核心问题。

    第一，信息量爆炸。Agent 每调用一次工具，工具输出就进入上下文；每完成一轮对话，历史就变长。跑几十步之后，一次调用的上下文轻松达到几十甚至上百 K token，而其中“提示词”可能只占很小一部分。Karpathy 说过，在工业级应用里提示词大概只占问题的很小比例，其余全是上下文管理。

    第二，无状态叠加长时程。模型本身不记得任何事，Agent 却经常要执行跨越几十分钟甚至数小时的长任务。第 47 步的决策质量，取决于第 1 到 46 步的“残余物”有没有被恰当地保留、压缩或清除。Anthropic 针对需要长期运行的任务给出三个经典手段：压缩（compaction，接近窗口上限时总结历史并开新窗口）、结构化笔记（把关键状态写到外部记事本，随时取回）、子agent架构（每个子任务在干净的独立上下文中完成，只给主agent返回精炼摘要）。

    第三，上下文会自我污染。Agent 循环中产生的错误信息，如果留在上下文里，会被后续步骤当作事实反复引用；无关信息堆积，会稀释模型对关键信号的注意力。LangChain 总结过四类典型失败：上下文投毒（错误信息传播）、上下文分心（大量无关数据淹没关键证据）、上下文混淆（冗余信息遮蔽要点）、上下文冲突（相互矛盾的指令并存）。这些问题在单轮应用中同样存在，但在 Agent 的多轮循环中会不断累积，并进一步影响后续决策。

    一句话总结：Chatbot 时代，我们更关注如何写好 Prompt；Agent 时代，我们还必须关注 Prompt 之外的整个 Context。

    06、Context Window 与有效上下文

    很多人有一个直觉假设：上下文窗口越大，问题越小——200K、1M token 的窗口不是都出来了吗，还需要什么工程？

    这里要引入一个关键区分：窗口大小（context window）是容器的标称容量，有效上下文（effective context）是模型在这个容器里真正能可靠利用的部分。

    早在 2023 年，论文 “Lost in the Middle” 就发现：当相关信息位于长上下文的开头或结尾时，模型表现较好；一旦被埋在中间，多文档问答的性能显著下降。2025 年 7 月，Chroma 的 “Context Rot” 研究测试了 18 个前沿模型，结论是：在他们测试的 18 个模型中，都观察到了随着输入长度增加而出现的性能退化，而且退化往往出现在远未达到标称上限的位置。

    为什么窗口标称很大，有效上下文却打折扣？Anthropic 把根因归结为“注意力预算”：

    • Transformer 的注意力机制要求每个 token 与上下文中所有 token 建立两两关系，n 个 token 就是 n² 对关系，长度增长时这种能力被“摊薄”；
    • 训练数据中短序列远多于长序列，模型对跨越超长距离的依赖本来就经验不足；
    • 位置编码插值等技术让模型能处理超出训练长度的序列，但代价是位置理解的精度损失。

    这些因素叠加的效果是一个性能梯度，而非硬性悬崖：模型在长上下文下依然可用，但信息检索的精度、长程推理的可靠性会随长度下降。换句话说，窗口是“能装下”，有效上下文才是“装下还能用好”。上下文工程的第一性原则由此而来：把上下文当作一种边际收益递减的稀缺资源，追求的是最小的高信号 token 集合，而不是最大的信息量。

    07、长上下文的三个问题：过长、噪声、冲突

    落到工程实践里，上下文管理的敌人主要就三个。

    **第一个是过长。**上下文太长的危害是复合的：性能上，前面说的 context rot 让检索和长程推理精度下降；成本上，LLM 按 token 计费，Agent 循环每一轮都重发全部历史，早期累积的垃圾信息相当于复利计息；延迟上，更长的输入意味着更慢的响应。治法是压缩与外置——历史做摘要、大块数据放外部、上下文里只留轻量引用（文件路径、查询语句、链接），需要时再通过工具加载。Claude Code 分析大型数据库时，就是让模型写针对性查询、用 head/tail 之类命令抽样，而从不把整个数据对象装进上下文。

    **第二个是噪声。**不等于错误，而是“语义上相关但实际无关”的干扰项。检索器命中十个文档、其中只有两个真正相关，那八个就是八份稀释注意力的毒药；一个工具调用返回五千 token 的 JSON，而真正需要的只有三个字段。有研究显示，语义连贯但无关的信息足以大幅拉低模型表现。治法是选择与修剪：检索后重排序、过滤，工具设计上尽量返回精炼结果，工具集本身也要克制——如果人类工程师都说不清该用哪个工具，就别指望模型能分清。

    **第三个是冲突。**上下文里同时存在相互矛盾的信息：系统提示说“输出必须是 JSON”，对话历史里模型已经输出过纯文本并被用户接受；旧版本的文档和新版本的并存；早期一次错误判断留下的结论，被后续步骤继续引用。冲突的危害在于它不报错——模型只是行为变得摇摆、不可预测。治法是隔离与治理：一个模型调用只看到完成当前任务所需的最小上下文，过时的信息要及时清除而不是层层堆积，关键事实外置到单一可信源，而不是散落在对话历史的多个角落。

    这三个问题指向同一个结论：上下文不是越多越好，“该让模型看到什么、不该看到什么”是每一步都要做的分配决策。在固定预算下做资源分配，这正是它被称作“工程”而不是“写作”的原因。
